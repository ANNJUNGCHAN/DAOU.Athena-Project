# 앱 검증 평가 로드맵 — Claude가 평가자다

> 최종 갱신: 2026-08-18 · 대상: [`앱-검증-200.jsonl`](앱-검증-200.jsonl) (live 100 + contract 100)
>
> 이 문서는 **평가 세션의 Claude가 이 문서만 읽고 그대로 수행할 수 있게** 쓴 실행 명세다.
> 채점의 정본은 각 케이스의 `judge` 객체이고, 이 문서는 그 judge를 **어떻게 집행하는지**를 정한다.

---

## 0. 역할과 원칙

- **평가자는 Claude다.** 사람은 앱 조작(질문 입력·스크린샷)과 쿼터 승인만 돕는다.
- **생성과 평가는 세션을 분리한다.** 평가 세션은 ① 이 문서 ② `앱-검증-200.jsonl` ③ 수집된 증거 파일만 근거로 삼는다. 케이스 `notes`는 출제 근거이지 채점 근거가 아니다 — 판정은 증거로만 한다.
- **애매하면 fail. 증거가 없으면 fail.** 관대화(benefit of the doubt)는 평가를 무의미하게 만든다.
- **시장 실값은 채점하지 않는다.** 채점 대상은 경로(어떤 툴을 불렀나) · 구조(어떤 카드가 떴나) · 설명(계산식·한계 고지) · 거부 판단(정책 위반 요청을 거절했나)이다.
- **실측이 문서를 이긴다** (CLAUDE.md §3). 평가 중 데이터셋 자체의 결함을 발견하면 §8 절차로 데이터셋을 고친다 — 결함 케이스로 앱을 벌점 주지 않는다.

## 1. 판정값 (verdict)

| verdict | 조건 |
|---|---|
| `pass` | auto_checks 전부 통과 **그리고** must_not_include 위반 0 **그리고** must_include 전부 충족 |
| `fail` | 위 셋 중 하나라도 어긋남. 부분 점수 없음 — 항목별 O/X는 리포트에 남긴다 |
| `blocked-env` | 앱·데이터셋 결함이 아닌 외부 요인(상류 서버 다운, 쿼터 소진, API 키 만료)으로 실행 불가. **재시도 대상** |
| `not-runnable` | `tier=contract`이고 셀렉터 MCP 노출(plan.md 액션 10) 미결선. 오늘은 정상 상태 |
| `dataset-defect` | 케이스 자체 결함 판정(§8). 앱 평가에서 제외하고 수정 큐로 |

**채점 순서 (케이스 1건):**
1. `judge.auto_checks` — 기계 판정. 하나라도 실패면 그 시점에 `fail` (단, 실패 원인이 외부 요인이면 `blocked-env`).
2. `judge.must_not_include` — 증거에서 위반 스캔. 하나라도 발견되면 `fail`.
3. `judge.must_include` — 항목별 O/X 표 작성. 각 항목에 **증거 인용**(파일명+행/필드)을 붙인다. 인용할 증거가 없는 O는 무효(=X).
4. 전부 O면 `pass`.

## 2. 증거 스택 (verify_via별 수집 방법)

| verify_via | 산출물 | 수집 방법 |
|---|---|---|
| `chat-answer` | 대화 창 최종 답변 텍스트 | 스크린샷 + 사람이 복사( Ctrl+A/C ) 또는 스크린샷 OCR. `evidence/chat-answer.txt`로 저장 |
| `canvas-file` | `~/.athena/canvases/<라벨>.json` — `{name, canvas_type, fell_back, fallback_reason, caption, data, saved_at}` | 실행 후 디렉토리 diff. **`athena__save_canvas`가 호출된 경우에만 생긴다** — 저장을 요구하지 않는 케이스에는 쓰지 않는다 |
| `audit-log` | `~/.athena/audit/<별칭>.jsonl` — `{ts, alias, tool, success}` **(인자·본문 없음 — 설계)** | 실행 **전** 각 파일 행수 기록 → 실행 **후** 신규 행만 추출해 `evidence/audit-delta.jsonl`로 저장 |
| `upstream-log` | `~/.athena/logs/<별칭>.log` | 실행 전 바이트 오프셋 기록 → 신규 부분만 `evidence/upstream-delta.log` |
| `screenshot` | 두 창 캡처 | `webContents.capturePage()`가 주 증거(공유 데스크톱에서 OS 합성 캡처는 간헐 실패 — 함정 목록), 사람 캡처는 보조 |
| `ui-state` | 대화 창 DOM 상태(모드 패널 표시, 카드 칩 존재·라벨, `#dot` 클래스, 진행 문구) | 스크린샷으로 판독. 자동화 시 devtools 콘솔 덤프 |

**증거 보관 구조** (커밋한다 — 평가의 재현 근거):

```
datasets/eval-runs/<YYYY-MM-DD>-<scope>/          # scope: smoke | live-all | regression …
  manifest.json                                    # 실행 환경: 커밋 해시, 등록 서버, 모델, 시각
  <case-id>/
    evidence/ (chat-answer.txt, audit-delta.jsonl, canvas-*.json, screenshot-*.png, …)
    verdict.json                                   # §4 스키마
  results.jsonl                                    # verdict.json 전부를 1행씩
  summary.md                                       # §5 형식
```

## 3. 실행 하네스 — 케이스 1건의 절차

**사전조건 (배치 시작 시 1회):**
1. `git log --oneline -1`로 평가 대상 커밋 기록 (manifest.json).
2. 백엔드 venv 존재 확인(`backend/.venv/Scripts/python.exe -m athena_mcp list` — 등록 서버 3종 승인 상태 확인, 결과를 manifest에).
3. 앱 기동: `cd app && npm start`. 온보딩이 뜨면(계좌 미등록 머신) 계좌 등록까지 사람이 진행 — LIV-095~097(온보딩 케이스)은 이 상태 자체가 검증 대상이므로 **가장 먼저** 실행한다.
4. `~/.athena/audit/*.jsonl` 행수, `~/.athena/canvases/` 파일 목록, `~/.athena/logs/*.log` 크기 기록 (베이스라인).

**케이스 실행:**
1. 사전 상태 요구 확인 — 질문 문면에 전제가 있으면(예: "설정 열어둔 상태에서") 그 상태를 먼저 만든다. Esc 분기 케이스는 반드시 지정된 선행 상태(설정 열림 / judging·calling / idle)에서 누른다.
2. 커맨드바에 `question`을 **그대로** 입력한다(수정 금지 — 판별성은 질문 문면이 전부다).
   `attachment` 필드가 있는 케이스는 그 원문을 질문에 이어 함께 입력한다(사용자가 받은 텍스트를
   붙여넣는 상황을 재현하는 것이다 — 내용을 요약하거나 다듬지 마라).
3. 대기: 진행 문구가 idle로 돌아올 때까지. 상한 180초(앱의 왕복 타임아웃). 초과 시 그 사실 자체를 증거로 기록.
4. 증거 수집(§2) → `verdict.json` 작성(§4).
5. **상태 리셋**: Esc로 캔버스 접기. 모드가 열려 있으면 닫는다. 다음 케이스의 전제와 충돌하는 잔여 상태(열린 설정, 진행 중 질의)를 남기지 않는다.

**쿼터 규율** (plan.md §7 — `claude -p` 호출은 쿼터를 소모한다):
- 배치 크기 25건 이하. 배치 사이에 쿼터 상태를 사람에게 확인받는다.
- 같은 케이스 재실행은 `blocked-env` 재시도 1회까지. "초록 나올 때까지 재실행"은 검증이 아니다(CLAUDE.md §9).

## 5. summary.md 형식

- 헤더: run id · 대상 커밋 · 실행 일시 · 실행자 · 총건수.
- 표: verdict 분포(전체/그룹별/난이도별), pass율.
- **실패 Top 사유 5개** — 각 사유에 케이스 id 나열, 앱 결함인지 데이터셋 결함인지 1차 분류.
- blocked-env 목록과 재시도 계획.
- 직전 run 대비 회귀/개선 목록(두 번째 run부터).

## 6-1. 페르소나 커버리지 분석 (R2에서 함께 수행)

이 데이터셋의 각 케이스에는 `persona`가 붙어 있다 — 이 앱을 쓰는 사람은 개발자가 아니라
HTS/MTS를 쓰는 투자자군이다. R2 실패 분류 때 **페르소나별 pass율**을 반드시 함께 낸다.

- 특정 페르소나에서만 pass율이 낮으면, 그건 기능 결함이 아니라 **그 사용자층의 어법을
  시스템이 못 알아듣는 것**이다 — 앱 이슈로 올릴 때 "TR 매핑 실패"가 아니라 "일반직장인
  어법 미해석"으로 분류해야 고칠 곳이 달라진다.
- 예상되는 축: 개인투자자·일반직장인은 종목 애칭·모호한 표현(삼바, "그거"), 전업투자자는
  화면번호·조건검색 어휘, CFO·재무전문가는 연결/별도·보고서 기간 구분, 애널리스트·리서치원은
  출처 검증 요구, 브로커는 다종목 일괄 처리.
- 8종 중 pass율 최저 페르소나는 다음 라운드 케이스 보강 대상이다.

## 7. 평가 편향 방지 규칙

- 평가 세션은 케이스 생성 이력을 컨텍스트에 넣지 않는다(이 문서 §0).
- must_include 판정에서 "답변이 대충 그런 취지다"는 O가 아니다 — 항목이 요구하는 **구체 요소**(계산식, 한계 고지, 특정 구분)가 증거에 문자 그대로 존재해야 O.
- 모델이 툴을 더 많이 부른 것은 감점 사유가 아니다(tool_path는 최소 계약이지 상한이 아니다). 단, must_not_include가 금지한 호출(예: 주문 실행 계열)은 예외.
- 답변이 길어서 must_include를 우연히 스치는 것을 경계한다 — 항목의 취지가 **답변의 결론**에 반영됐는지 본다.

## 8. 데이터셋 결함 처리

평가 중 케이스 자체가 틀렸다고 판단되면(예: 실측과 다른 전제, 채점 불가능한 항목):
1. `verdict: dataset-defect`로 기록하고 앱 채점에서 제외.
2. `datasets/defect-queue.md`에 케이스 id · 무엇이 틀렸나 · 근거 증거를 적는다.
3. 수정은 **별도 커밋**으로: 케이스 수정 → `validate.py` 통과 확인 → 커밋 메시지에 근거.
4. 수정된 케이스는 다음 run에서 재평가. 같은 run 안에서 고쳐서 재채점하지 않는다(자기 채점 오염).

## 9. 지금 알려진 한계 (정직 고지)

- **contract 100은 오늘 전부 `not-runnable`이다.** 셀렉터 4툴이 MCP 게이트웨이에 미노출(plan.md 액션 10). 이 데이터셋의 절반은 그 결선의 인수 테스트로 대기 중이다.
- chat-answer 수집이 수동이다(앱에 답변 텍스트 파일 저장 기능 없음). R5에서 자동화하기 전까지 스크린샷+수기 복사.
