# 캔버스 우선 응답 지시문

아래 지시를 현재 진행 중인 작업에 **최신 사용자 결정**으로 적용하라. 기존의
“캔버스 우선 구성 → 필요 정보만 뽑아 채팅으로 답변” 계약 중 후반부를 다음과 같이
개정한다.

> **캔버스가 성공적으로 렌더되면 캔버스 자체가 기본 답이다. 채팅은 캔버스 데이터를
> 다시 설명하는 두 번째 출력이 아니라, 완료 상태·중요 예외·명시적으로 요청된 분석만
> 전달한다.**

## 1. 적용 범위

- 이 정책은 조회 결과가 차트·표·facts·compound 등 카드로 캔버스에 표시되는 모든
  성공 경로에 적용한다.
- 일반 대화, 캔버스가 필요 없는 질문, 사용자가 명시적으로 요청한 분석·요약·비교·설명은
  정상적인 자연어 응답 범위로 남긴다.
- mock 계좌 전용, 주문 기본 비활성, selector visibility gate 등 기존 보안 경계는 변경하지
  않는다.

## 2. 키움 REST API 완전 사전결정 계약

키움 REST API에 한해서는 모델이나 런타임 휴리스틱이 “무엇을 읽고 어떻게 보여줄지”를
결정해서는 안 된다. 모든 operation의 데이터 선택, 정렬, 범위, 카드, 화면 상태, 후속 질문을
manifest와 Paper 화면설계서에서 **실행 전에 완전히 정한다.**

### 2.1 범위와 완전성

현재 canonical inventory의 기준은 다음과 같다.

- routable mapping 301개
  - read/display 264개
  - WebSocket workflow 23개
  - order workflow 12개
  - OAuth workflow 2개
- split-derived route 115개
- 명시적으로 제외한 split-original query ID 22개

이 숫자는 현재 권위 데이터의 검증값이다. 키움 공식 inventory가 개정되면 generator와 manifest를
함께 갱신하고 새로운 총수를 다시 검증한다. 코드에서 누락된 operation을 숨기거나 기존 숫자를
맞추기 위해 임의로 제외하지 않는다.

- 264개 read/display mapping은 모두 데이터 읽기 계약과 화면 표시 계약을 가진다.
- 23개 WebSocket, 12개 order, 2개 OAuth mapping도 각각 Paper의 lifecycle·상태·오류·복구
  화면에 연결한다. 이들을 일반 조회 결과 카드로 가장하지 않는다.
- 22개 제외 ID는 제외 사유와 provenance를 유지하며 selector나 화면 coverage로 다시 들어오지
  못하게 테스트한다.
- 모든 routable mapping은 정확히 하나의 정상 화면 또는 guarded workflow 정의로 귀결되어야
  한다. orphan mapping과 orphan screen을 허용하지 않는다.

### 2.2 권위 있는 소재지와 파생 순서

다음 순서를 단일 source chain으로 사용한다.

```text
kiwoom-tr-inventory.json
+ kiwoom-output-profile.json
+ response-projections.json
        │
        ▼ generate_api.py
kiwoom-common-screen-manifest.json
        │
        ├─ operation·request/response field·classification·presentation
        ▼
kiwoom-screen-definitions.json
        │ Paper 화면설계서의 screen/artboard/state/template 연결
        ▼
generated registry / operation manifest
        ▼
canvas_transform.py
        ▼
Paper에 정의된 카드·화면 renderer
```

- 생성물은 손으로 고치지 않는다. 원본 ref 또는 generator를 수정한 뒤 재생성한다.
- `kiwoom-common-screen-manifest.json`은 모든 301 mapping과 22 exclusion의 기계적 coverage
  권위다.
- `kiwoom-screen-definitions.json`은 Paper 화면설계서에서 확정된 화면, 상태, template case,
  component slot, control을 기계가 읽을 수 있게 연결하는 권위 파일이어야 한다.
- 현재 `kiwoom-screen-definitions.json`이 없어서 fit-dissonance 검사가 provisional로 동작하는
  상태라면 이것은 완료가 아니다. Paper 정의를 materialize하고 provisional 상태를 제거한다.
- `ui/`의 soul·palette·motion·two-window 규범은 시각 언어와 상호작용 구현의 권위로 유지하고,
  Paper는 화면 구성·정보 위계·배치·상태의 권위로 사용한다. 둘이 충돌하면 런타임에서 임의로
  절충하지 말고 불일치를 기록한 뒤 권위 문서 중 하나를 명시적으로 개정한다.

### 2.3 operation별 필수 데이터 계약

모든 키움 read/display mapping은 최소한 다음 항목을 machine-readable하게 가져야 한다.

1. **식별과 소유권**
   - `mapping_id`, `operation_ref`, `tr_id`, base/detail 소유 family
   - route path·method·operation ID
   - request/response model과 source provenance
2. **입력 계약**
   - 필수·선택 인자, alias, 타입, 허용값, 기본값
   - continuation/pagination 입력과 계좌·종목·날짜 binding
   - read-only 여부와 order/WebSocket/OAuth 경계
3. **읽을 데이터 계약**
   - 응답에서 읽을 정확한 container path와 field allowlist
   - field priority와 표시 여부
   - label, 단위, formatter, 부호·백분율·통화·수량 처리
   - null, sentinel, 빈 문자열, 누락 field 처리
   - 민감 field·transport envelope·return code처럼 화면에 표시하지 않을 field
4. **시간·정렬·범위 계약**
   - 권위 있는 date/time field와 timezone
   - sort key·방향·동률 tie-breaker
   - 최신 record, 최신 N개, 전체 page 중 어느 기본 범위를 사용할지
   - page size, screen budget, 최대 행·봉 수, continuation 정책
   - 기간별 chart의 기본 period와 허용 period
5. **표현 계약**
   - `shape`, `layout`, card/template ID, Paper screen/artboard ID
   - facts section, table column, compound group, chart axis/series의 정확한 배치
   - column fold·priority·고정 열·헤더·행 밀도
   - loading, empty, partial, truncated, stale, fallback, error 상태
6. **상호작용 계약**
   - 허용 control과 초기 control 상태
   - pagination·period·detail group 전환
   - 허용된 후속 질문 ID와 target intent
   - 접근성 label·읽기 순서·키보드 동작

필드가 실제 응답에 존재한다는 이유만으로 표시하지 않는다. allowlist에 없는 field는 카드,
채팅, 모델 context에서 제외한다. 반대로 필수 field가 없으면 다른 field를 비슷한 의미로 추측해
대체하지 말고 명시적인 contract 오류로 처리한다.

### 2.4 Paper 화면설계서 고정 규칙

- 현재 manifest의 mapping들은 Paper에서 승인된 공통 template case와 guarded workflow
  화면으로만 렌더한다. 현재 기록된 13개 공통화면 경우의 수를 런타임 휴리스틱으로 늘리거나
  Paper에 없는 14번째 화면을 즉석 생성하지 않는다.
- 각 mapping은 `screen_id` 또는 동등한 안정 ID로 Paper artboard·상태·template case에 연결한다.
- Paper가 정한 정보 위계, slot, 열 배치, 밀도, control 위치, empty/error/loading 상태를 코드가
  재해석하지 않는다.
- 화면 크기 변화는 승인된 responsive/fold 규칙 안에서만 처리한다. JSON 크기나 모델 판단으로
  임의 레이아웃을 만든다거나 카드 종류를 바꾸지 않는다.
- Paper 화면에 없는 새로운 시각 상태가 필요하면 먼저 화면설계서를 개정하고 안정 ID와 검증
  기준을 등록한 뒤 구현한다.
- Paper와 실제 앱의 픽셀 또는 동작 차이가 있으면 “비슷하다”로 통과시키지 않는다. 의도적
  차이는 근거와 함께 문서에 등록하고, 그 외 차이는 회귀로 취급한다.

### 2.5 런타임 금지사항

키움 REST `plan_token` 경로에서는 다음을 금지한다.

- 모델이 `canvas_type`, 열, field, sort, page size, 최신 날짜 키, chart period를 자유 선택
- payload의 key 이름이나 크기를 보고 facts/table/chart/compound를 추측
- response description이나 자연어 summary로 화면을 구성
- mapping이 없을 때 generic/free 카드로 조용히 강등
- Paper에 없는 동적 component·레이아웃·색상·control 생성
- 전체 JSON을 모델에 주고 “중요한 것만 골라 달라”고 요청
- 예상하지 못한 field를 디버그 편의로 화면 또는 채팅에 노출

`operation_ref → manifest presentation → Paper screen definition`이 유일한 정상 결정 경로다.
사용자나 모델이 보낸 `canvas_type`은 키움 `plan_token` 경로의 권위가 아니며, manifest가 정한
결과를 덮어쓸 수 없다.

mapping 또는 screen definition이 없으면 이는 자유 카드 fallback 대상이 아니라 **coverage
결함**이다. 실행을 fail-closed하고 mapping ID와 누락된 계약 종류만 비민감 오류로 기록한다.
legacy `render_canvas(data)`나 비키움 MCP 데이터의 자유 카드 fallback과 이 규칙을 섞지 않는다.

## 3. 데이터 경로 불변조건

1. 조회 결과의 전체 구조화 데이터는 백엔드 사이드 채널
   `POST /api/v1/canvas/push → /api/v1/ws/canvas`로 캔버스 렌더러에 직접 전달한다.
2. 성공한 캔버스 payload의 행·셀·봉·가격·거래량·기간·종목 데이터 본문을 모델
   stream이나 채팅 응답으로 복제하지 않는다.
3. 자연어 생성을 위해 캔버스를 스크린샷으로 캡처하거나 OCR·vision 입력으로 되돌리지
   않는다. 자연어 분석이 필요할 때도 렌더링에 사용한 동일한 구조화 JSON을 원본으로
   사용한다.
4. 캔버스가 그려진 뒤 같은 데이터를 요약하기 위한 추가 모델 호출을 만들지 않는다.
5. 캐시 경로도 판정만 재사용하고 데이터는 매번 새로 조회한다. 캐시 적중 여부가 캔버스
   데이터 본문을 채팅으로 보내는 이유가 되어서는 안 된다.

## 4. WebSocket 응답 계약

WebSocket 호출은 단발성 JSON 결과가 아니라 화면에서 계속 갱신되는 실시간 상태다. 따라서
WebSocket frame을 JSON 문자열로 채팅에 출력하거나 모델 응답으로 복제하지 않는다.

1. 구독 성공 후 수신 frame은 구조화된 상태로 캔버스 렌더러에 직접 전달한다.
2. 최초 frame, 최신 frame, 누적 frame을 채팅에 JSON으로 dump하지 않는다.
3. 캔버스가 숨겨져 있으면 기존 창 확장 동작으로 캔버스를 보이게 하고, 채팅은 사용자가
   화면을 보도록 한 줄로 안내한다.
4. 연결 중·수신 중·재연결 중·중지됨 같은 lifecycle 상태는 캔버스의 상태 표시 또는 짧은
   receipt로 표현한다. protocol payload 전체를 상태 설명에 포함하지 않는다.
5. 구독 해지와 연결 종료도 JSON 응답 대신 상태 영수증으로 알린다.
6. 인증 실패, 연결 실패, 재연결 한도 초과, frame 변환 실패는 예외이므로 오류 종류와 사용자가
   알아야 할 조치만 자연어로 알린다. 원문 frame이나 민감한 연결 정보를 노출하지 않는다.

기본 문구는 다음으로 고정한다.

```text
실시간 데이터 수신을 시작했습니다. 캔버스에서 확인하세요.
```

구독 해지 시에는 다음처럼 답한다.

```text
실시간 데이터 수신을 중지했습니다.
```

다음과 같은 출력은 금지한다.

```json
{"type":"0B","data":{"10":"73500","15":"1200"}}
```

WebSocket 데이터가 화면에 정상 반영되고 있다면 채팅에서 가격·체결·호가·순위 값을 다시
말하지 않는다. 사용자가 실시간 데이터의 해석을 명시적으로 요청한 경우에만 별도의 분석
경로를 사용하며, 그 경우에도 frame JSON을 그대로 출력하지 않고 필요한 관측만 해석한다.

## 5. 성공 응답 계약

캔버스 push가 성공하면 모델 또는 fast-path에 필요한 것은 데이터 요약이 아니라
**display receipt**다. 성공 receipt는 다음과 같은 제어 메타데이터만 가질 수 있다.

- `pushed`
- `canvas_type`
- `fell_back`와 `fallback_reason`
- 데이터 잘림·부분 표시 여부
- 판정 캐시 재사용 여부
- 렌더 성공을 식별하는 비민감 ID 또는 시각

가격, 종가, 행 수, 봉 범위, 열 이름, 순위, 개별 레코드 등 캔버스 내용을 다시 말하기 위한
`summary`는 성공 채팅 생성의 입력으로 사용하지 않는다.

기본 채팅 응답은 한 줄의 완료 영수증으로 제한한다.

```text
캔버스에 표시했습니다.
```

판정 캐시를 사용한 경우에도 데이터 내용은 반복하지 않고 무결성 고지만 추가한다.

```text
캔버스에 표시했습니다. 이전 해석을 재사용했고 데이터는 새로 조회했습니다.
```

다음과 같은 응답은 금지한다.

```text
삼성전자 차트를 캔버스에 띄웠습니다. 최근 240봉이며 최근 종가는 73,500원입니다.
```

위 정보가 카드에 이미 보이면 채팅으로 다시 출력하지 않는다.

## 6. 대용량 JSON 최소 추출 계약

JSON이 크다는 이유로 전체 payload를 모델·채팅·tool result에 그대로 싣지 않는다. 먼저 사용자
질문의 의도를 기준으로 화면에 필요한 최소 범위를 결정론적으로 추출하고, 그 결과만 카드로
렌더한다.

### 기본 원칙

1. **의도가 먼저다.** 현재값 질문은 최신 snapshot, 기간 차트는 최신 bounded window, 순위
   질문은 정렬 기준의 상위 N건, 명시적 전체 내역 요청은 pagination으로 처리한다. 모든 큰
   JSON에 무조건 “최신 1건”을 적용하지 않는다.
2. 날짜형 record에서 사용자가 기간·건수를 지정하지 않았다면 해당 operation manifest가
   미리 정한 최신 record 또는 최신 bounded window를 사용한다.
3. “최신”은 배열의 첫 항목이나 마지막 항목으로 추측하지 않는다. 키움 REST에서는 operation별
   manifest가 지정한 날짜·시각 필드만 파싱해 비교하며, 런타임이 날짜처럼 보이는 key를 찾아
   사용하지 않는다.
4. 타임존을 보존하고, 같은 최신 시각이 여러 건이면 서버 sequence·원본 순서·안정적인 ID처럼
   계약에 정의된 보조 키로 완전 결정론적으로 정렬한다.
5. 날짜가 없거나 파싱할 수 없는 경우 임의의 항목을 최신으로 선언하지 않는다. 날짜 기준을
   판단할 수 없다고 표시하고 안전한 bounded preview 또는 명시적 범위 선택으로 전환한다.
6. 추출 후에도 `rows_total`, `rows_kept`, 적용한 정렬 기준, 최신 관측 시각, 잘림 여부를 제어
   메타데이터로 보존한다. 이 메타데이터는 카드 범위 표시와 정확성 검증에 사용하며 데이터
   본문을 채팅으로 낭독하는 용도로 사용하지 않는다.
7. 원본 대용량 JSON은 필요한 변환이 끝난 뒤 모델 context에 남기지 않는다. 모델이 필요한
   경우에도 선택된 최소 record·필드와 범위 메타데이터만 제공한다.

### 먼저 보여주고 그다음 묻기

범위가 명시되지 않은 대용량 결과는 사용자에게 선택을 다시 묻느라 렌더를 막지 않는다.
가장 유용한 기본 범위를 먼저 캔버스에 표시한 뒤, 채팅에서 범위와 확장 가능성만 짧게 묻는다.

날짜형 데이터에서 최신 record를 표시한 경우:

```text
가장 최신 기준으로 캔버스에 표시했습니다. 이전 기간이나 추가 항목도 볼까요?
```

최신 N개 구간을 표시한 경우:

```text
최신 구간을 캔버스에 표시했습니다. 더 이전 데이터도 볼까요?
```

이 질문은 전체 JSON의 내용을 다시 설명하지 않는다. 사용자가 “최근 30일”, “전체”, “상위
20개”처럼 범위를 이미 지정했다면 같은 질문을 반복하지 말고 지정 범위를 그대로 처리한다.

추가 정보 요청에 사용자가 동의하면 기존 payload 전체를 한꺼번에 보내지 않고 다음 page,
이전 기간, 추가 field group처럼 bounded 단위로 확장한다.

## 7. 후속 질문 추천 시스템

캔버스 렌더가 끝난 뒤 사용자가 다음 탐색을 바로 선택할 수 있도록 **약 3개의 후속 질문**을
추천한다. 추천은 캔버스 데이터를 다시 설명하는 답변이 아니라 다음 행동의 제안이며, 사용자가
선택하기 전에는 어떤 조회나 상태 변경도 실행하지 않는다.

### 추천 입력

추천기는 대용량 데이터 본문이나 화면 캡처를 읽지 않고 다음의 구조화된 context만 사용한다.

- 사용자의 원래 질문과 discovery intent
- canonical `operation_ref`와 카드 종류
- subject/entity kind와 비민감 표시 이름
- 현재 시간 범위와 결과 범위 메타데이터
- `rows_total`, `rows_kept`, `trimmed`, 최신 관측 시각
- selector가 공개한 허용 operation과 detail group
- WebSocket 구독 lifecycle 상태

계좌번호, token, 원문 WebSocket frame, 전체 표·차트 payload를 추천 입력으로 사용하지 않는다.

### 추천 구성

가능하면 서로 중복되지 않는 다음 세 축에서 한 개씩 제안한다.

1. **범위 확장 또는 축소**: 이전 기간, 다음 page, 추가 field group, 더 짧은 최신 구간
2. **비교**: 이전 기간, 같은 업종, 다른 지표, 기준값과 비교
3. **해석 또는 세부 탐색**: 흐름 요약, 특정 행 상세, 변동 원인에 필요한 추가 근거

예를 들어 최신 record 하나만 표시했다면 다음과 같이 제안할 수 있다.

```text
- 이전 기간도 볼까요?
- 다른 주요 항목도 함께 볼까요?
- 직전 관측값과 비교할까요?
```

실시간 WebSocket 카드라면 JSON을 보여주지 않고 다음처럼 제안할 수 있다.

```text
- 최근 구간의 흐름도 볼까요?
- 체결과 거래량을 함께 비교할까요?
- 실시간 수신을 중지할까요?
```

### 생성 규칙

1. 기본 목표는 3개지만, 안전하고 실행 가능한 질문이 3개보다 적으면 억지로 채우지 않는다.
2. 추천은 현재 selector/catalog에서 실제로 접근 가능한 operation과 detail group으로 처리할 수
   있어야 한다. 존재하지 않는 기능을 자연스러운 문장으로 꾸며내지 않는다.
3. 기본 추천은 read-only 조회다. 주문, 자동매매, 계좌 상태 변경, 숨은 OAuth operation을 추천하지
   않는다. WebSocket 해지는 현재 활성 구독을 중지하는 명시적 제안으로만 허용한다.
4. 같은 의미의 표현만 다른 질문, 현재 카드가 이미 답한 질문, 사용자가 방금 거절한 질문은
   제거한다.
5. 대용량 JSON이 잘렸다면 범위 확장 질문을 우선한다. 사용자가 범위를 이미 명시했다면 동일한
   범위 확인 질문을 반복하지 않는다.
6. 추천 문구에 캔버스의 가격·행 값·봉 값이나 원문 JSON을 복사하지 않는다. 필요한 경우 비민감
   종목 표시 이름과 기간 표현만 사용한다.
7. 추천 생성 때문에 모델을 한 번 더 호출하지 않는다. 우선 순위가 고정된 결정론 템플릿과
   operation/card metadata로 생성한다.
8. 추천 context가 부족하거나 모든 후보가 안전 규칙에 걸리면 추천 영역을 숨긴다.
9. 키움 REST 결과의 추천 후보는 각 mapping/screen definition에 사전 등록된
   `follow_up_id`, label template, target intent, 허용 operation family, parameter binding,
   precondition에서만 고른다. 일반 언어 모델이나 공통 휴리스틱이 새 질문 종류를 만들지 않는다.
10. mapping별 추천 allowlist가 없으면 generic 추천을 만들어 채우지 않는다. 이는 추천 0개 또는
    coverage 결함으로 처리한다.

### 표현과 실행

- 후속 질문은 채팅 본문과 분리된 0~3개의 버튼 또는 chip으로 표시한다.
- 화면에는 자연어 label만 보이고 내부 JSON이나 `operation_ref`는 노출하지 않는다.
- 키보드 탐색, focus 표시, screen reader label을 제공한다.
- 사용자가 chip을 누르면 해당 질문을 기존 사용자 질의 진입점으로 보낸다. 추천기가
  `resolve`, `call`, 주문 또는 WebSocket 상태 변경을 직접 실행해서는 안 된다.
- 새 결과가 나오면 이전 추천을 폐기하고 새 context로 교체한다. 로딩 중에는 중복 실행을 막고,
  원본 카드가 교체되거나 구독이 끝나면 오래된 추천을 비활성화한다.

## 8. 자연어를 허용하는 예외

다음 경우에만 캔버스와 별도의 자연어를 생성한다.

1. 사용자가 “요약해줘”, “분석해줘”, “왜 그런지 설명해줘”, “비교해줘”처럼 자연어
   해석을 명시적으로 요청했다.
2. push 실패, 조회 실패, 인증 실패, fallback, 부분 데이터, 잘림, 오래된 데이터처럼
   사용자가 결과를 오해할 수 있는 상태가 발생했다.
3. 캔버스 자체에 표시되지 않은 출처·기준 시점·제약을 반드시 고지해야 한다.
4. 접근성 모드 또는 사용자의 명시적인 대체 텍스트 요청이 활성화됐다.

예외 응답도 전체 데이터를 낭독하지 않는다. 필요한 사실과 한계만 짧게 설명한다. 사용자가
분석을 요청한 경우에는 구조화 데이터에서 근거가 되는 지표만 선택해 해석하고, 관측 사실과
추론을 구분한다.

## 9. 실패와 강등 처리

- side-channel push가 실패했으면 성공한 것처럼 “캔버스에 표시했습니다”라고 답하지 않는다.
- 기존 인라인 fallback을 사용한다면 `push_failed`와 fallback 사실을 명시하고, payload가
  잘릴 수 있다는 한계를 숨기지 않는다.
- 데이터가 잘렸다면 “전체 중 일부만 표시” 같은 범위 경고는 허용한다. 단, 카드가 이미 같은
  경고를 눈에 보이게 제공한다면 채팅에서 다시 반복하지 않는다.
- 알 수 없는 카드 종류가 `free`로 강등된 경우 그 사실과 이유를 짧게 알린다.
- 오류·경고가 없으면 채팅에 데이터 내용을 추가하지 않는다.

## 10. 현재 코드에 적용할 지점

- `backend/athena_mcp/server.py`
  - push 성공 시 모델로 반환하는 `summary`를 데이터 요약이 아닌 display receipt로 축소한다.
  - 전체 payload는 계속 사이드 채널로만 보낸다.
- `backend/athena_api/api/canvas_push.py`
  - render-plan 경로도 동일한 receipt 계약을 사용한다.
- `backend/athena_api/canvas_transform.py`
  - 대용량 날짜형 JSON은 schema/manifest의 시각 필드로 정렬하고 최신 record 또는 카드 종류에
    맞는 bounded window만 변환한다.
  - 배열 위치를 최신성의 근거로 사용하지 않고, invalid/missing timestamp를 명시적으로
    처리한다.
  - 키움 REST payload의 field·정렬·범위·layout을 추측하지 않고 mapping의 완전한 사전 계약만
    실행한다.
- `backend/ref/kiwoom-common-screen-manifest.json`
  - 301 mapping과 22 exclusion의 canonical coverage, request/response field, classification,
    provenance를 유지한다.
- `backend/ref/kiwoom-screen-definitions.json`
  - Paper screen/artboard/template/state와 모든 mapping의 안정적인 연결을 materialize한다.
  - 파일 부재 또는 provisional fit 판정을 완료 상태로 보고하지 않는다.
- `backend/scripts/generate_api.py`
  - operation별 데이터·presentation·screen reference의 완전성과 orphan 부재를 생성 단계에서
    검증한다.
- `app/lib/main/fast-path.js`
  - 차트·표의 가격, 행 수, 시간 범위를 말하는 결정론 템플릿을 제거한다.
  - 성공, 캐시 재사용, 예외 상태만 문장으로 만든다.
- `app/lib/main/live-prompt.js`
  - 성공한 캔버스 내용을 재서술하지 말라는 지시를 명시한다.
  - 사용자가 분석을 명시적으로 요청한 경우에만 구조화 데이터 기반 해석을 허용한다.
- WebSocket 구독·해지 처리 경로
  - 구독 frame을 채팅 JSON으로 직렬화하지 않고 캔버스 갱신으로만 소비한다.
  - 구독 성공 시 “실시간 데이터 수신을 시작했습니다. 캔버스에서 확인하세요”라는 receipt를
    사용하고, 해지·연결 실패·재연결 상태를 별도 lifecycle receipt로 표현한다.
- `app/lib/main/query-cache.js`
  - 캐시 판정과 데이터 신선도 계약은 유지하되, 캐시된 summary를 자연어 답변의 근거로
    사용하지 않는다.
- 후속 질문 추천 순수 모듈과 테스트
  - receipt·operation/card metadata를 입력받아 최대 3개의 중복 없는 질문을 만드는 순수
    함수를 둔다.
  - 데이터 본문, screenshot, 추가 모델 호출 없이 결과가 결정론적으로 같아야 한다.
- 대화 창 renderer
  - 추천 질문을 채팅 본문과 분리된 button/chip으로 렌더하고 기존 질의 진입점에 연결한다.
  - 새 결과·오류·구독 종료 시 이전 추천을 폐기하고 키보드·screen reader 접근성을 보장한다.

## 11. 회귀 테스트와 완료 조건

완료를 주장하기 전에 최소한 다음을 자동 테스트로 고정한다.

1. 성공한 WS push가 전체 구조화 데이터를 캔버스에 한 번만 렌더한다.
2. 성공 채팅 문자열에 fixture의 가격·행 값·봉 값·열 이름 등 캔버스 데이터 토큰이 들어가지
   않는다.
3. 성공 경로가 추가 모델 요약 호출을 만들지 않는다.
4. fast-path와 일반 live 경로가 같은 display-receipt 정책을 따른다.
5. 캐시 적중 시 “이전 해석 재사용·데이터 신규 조회” 고지는 유지된다.
6. push 실패·fallback·잘림은 사용자에게 보이고 성공으로 위장되지 않는다.
7. “요약해줘” 같은 명시적 요청에서는 구조화 데이터 기반 자연어 분석이 정상 동작한다.
8. 접근성 대체 설명은 기본 채팅과 분리되어 명시적으로 활성화된다.
9. WebSocket 구독 frame은 캔버스에 반영되지만 채팅에는 JSON·frame 필드·실시간 값이
   노출되지 않는다.
10. WebSocket 구독·해지·재연결·실패가 각각 올바른 lifecycle receipt로 표시된다.
11. 대용량 fixture 전체가 모델·채팅 결과에 들어가지 않고 카드 종류에 맞는 bounded 결과만
    전달된다.
12. 최신 record 선택은 배열 순서가 아니라 실제 timestamp 비교로 결정되며, 역순·동률·타임존·
    누락·잘못된 날짜 fixture에서도 결과가 결정론적이다.
13. 범위 미지정 대용량 결과는 최신 기본 범위를 먼저 렌더한 뒤 추가 범위를 묻는다.
14. 사용자가 기간·건수·전체 범위를 이미 지정한 경우 불필요한 추가 질문 없이 그 범위를
    처리한다.
15. 추가 정보 요청은 전체 JSON 재전송이 아니라 page·기간·field group 단위의 bounded 확장으로
    이어진다.
16. 정상 결과마다 실행 가능한 후보가 충분하면 중복 없는 후속 질문 3개가 표시된다.
17. 추천 질문은 실제 공개 selector operation/detail로 처리 가능하며 주문·자동매매·숨은 OAuth
    기능을 포함하지 않는다.
18. 추천 생성 입력과 화면 출력에 전체 payload, WebSocket frame JSON, 계좌번호, token이 들어가지
    않는다.
19. 같은 context는 같은 추천을 만들며 추천 생성을 위한 추가 모델 호출이 없다.
20. 추천 chip 클릭은 기존 사용자 질의 경로만 호출하고, 클릭 전에는 조회·주문·구독 상태 변경이
    발생하지 않는다.
21. 새 결과·로딩·오류·구독 종료에서 오래된 추천이 교체 또는 비활성화된다.
22. 추천 chip을 키보드로 탐색·실행할 수 있고 screen reader가 질문 label을 읽는다.
23. canonical inventory의 현재 301 mapping과 22 exclusion, 264/23/12/2 category partition이
    정확하며 누락·중복·orphan이 없다.
24. 264개 키움 read/display mapping 모두가 exact field allowlist, 시간·정렬·범위 계약,
    presentation, Paper screen ID, 후속 질문 allowlist를 갖는다.
25. 23개 WebSocket, 12개 order, 2개 OAuth mapping이 일반 read 카드가 아니라 승인된 guarded
    workflow 화면과 lifecycle 상태로 연결된다.
26. 모든 mapping은 승인된 Paper template case 중 정확히 하나로 귀결되고 Paper에 없는 동적
    화면이 생성되지 않는다.
27. 키움 `plan_token` 경로에서 모델·payload 휴리스틱·요청 `canvas_type`이 field 또는 화면을
    바꿀 수 없다.
28. allowlist 밖의 응답 field와 transport envelope가 캔버스·채팅·모델 context에 노출되지
    않는다.
29. 누락된 mapping, screen definition, 필수 field, date field는 generic/free 카드로 조용히
    강등되지 않고 명시적 coverage/contract 오류가 된다.
30. `kiwoom-screen-definitions.json` 기반 fit-dissonance 검사가 provisional이 아닌 완전 게이트로
    통과한다.
31. 각 Paper case의 대표 fixture를 실제 renderer에 주입한 screenshot·DOM·레이아웃 검증이
    화면설계서의 정보 위계·배치·control·상태와 일치한다.
