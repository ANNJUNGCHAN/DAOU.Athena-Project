# 카드 분류 체계 (초안)

> **용어 (2026-08-17 확정).** 여기서 분류하는 것은 **카드**다. "캔버스"는 캔버스 창을 뜻하고
> 창 안에 뜨는 표현 단위가 카드다(`GLOSSARY.md` §2). 이 문서는 원래 내용물도 "캔버스"라
> 불렀다 — 아래 본문의 "캔버스"는 대부분 "카드"로 읽어라.
>
> **핵심 개념**: 카드는 데이터를 표현하는 **공통 UI**다. Power BI/Tableau의 시각화
> 컴포넌트와 같은 위치 — **들어오는 데이터가 달라진다고 UI가 달라지지 않는다.**
> 그래서 TR이 288개든 301개든 카드는 12종에 머문다. 새 카드가 필요해 보이면
> 먼저 12종 중 어디에 접히는지 본다.

목표: **키움 288화면을 카드 12종 + 자유 카드로 접는다.**
근거: [키움 REST API 개발 가이드 (국내주식)](https://openapi.kiwoom.com/m/guide/apiguide?jobTpCode=15) · [비공식 Python 래퍼 — 국내주식 207 엔드포인트 명시](https://github.com/younghwan91/kiwoom-rest-api) · [공식 GitHub](https://github.com/Kiwoom-Securities/Kiwoom-REST-API)

> **주의**: 공식 문서에 TR 총계가 명시되어 있지 않다. 아래 커버율은 총 220개 [추정] 기준의 개산치다.
> 구현 착수 전 Swagger/명세서로 TR별 응답 스키마를 확인해 **카드별 필드 매핑표**를 만들어야 한다. 이 문서는 UI 설계용 뼈대이지 구현 스펙이 아니다.

## 핵심 발상

TR을 **화면 단위가 아니라 데이터 형상 단위**로 접는다.
288개 화면이 실제로 말하는 문장 구조는 열몇 개뿐이다.

식별된 형상 원형:
시계열 1축 · 시계열 다축 · 랭킹 테이블 · 스냅샷 스칼라 묶음 · 호가 사다리(양방향 막대) · 이벤트 로그 · 2차원 히트맵/트리맵 · 분포 · 폼+상태 테이블

## 자유 카드로 보내는 것

자유 카드는 실패가 아니라 **설계된 탈출구**다 ([`ui/soul.md`](../ui/soul.md) §5-5).

1. **메타데이터/마스터 조회** — 업종코드리스트(ka10101), 회원사리스트(ka10102), 종목정보리스트(ka10099), 관심종목그룹(ka01300/01301).
   → 애초에 시각화 대상이 아니다. 다른 카드를 채우기 위한 **참조 데이터**. 드롭다운/설정 패널이면 충분.

2. **조건부 스캐너류** — 신고저가(ka10016), 상하한가(ka10017), 고저PER(ka10026), 거래량갱신(ka10024), VI발동(ka10054), 가격급등락(ka10019).
   → 형상은 랭킹 테이블과 비슷하지만 TR마다 컬럼 조합·정렬 기준·발동 조건이 미묘하게 다르다. 표준 템플릿에 강제로 밀어 넣으면 정보 손실이 크고, 사용 빈도 대비 전용 카드 ROI가 낮다.

3. **거래주체/창구 흐름** — 외국계창구매매상위, 당일주요거래원, 거래원별ELW순매매상위.
   → 관계망/Sankey 형상으로 볼 수도 있으나 실수요 검증 전엔 랭킹 테이블 임시 렌더 또는 자유 카드가 안전하다.

4. **복합 질의** — "삼성전자랑 SK하이닉스 외국인 순매수 vs PER 같이 보여줘".
   → TR 2개 이상을 조인하는 임시 산점도/이중축. **사전 정의가 원리적으로 불가능하다.** 자유 카드가 존재해야 하는 가장 근본적인 이유.

**금현물(kt50000~kt50092)**은 신규 카드 불필요. 국내주식과 형상이 같으므로 기존 카드에 자산군 라벨·단위 파라미터만 확장한다.

## 배치·생애주기 규칙 (2026-08-18 확정)

라운드 2로 미뤄뒀던 배치 규칙을 질의응답으로 확정했다(35쪽 장표 미해결 해소).
이 절이 규칙의 원본이다. **앱 반영 완료(2026-08-18)** — 폭 문법·도착순은
`app/canvas.css`(w-half/w-full) + `app/lib/canvas-layout.js`(순수 로직, node --test
9건), 힌트·큐레이션 계약은 `backend/athena_mcp/server.py`(`layout`·`drop_types`,
pytest 2건), 집행은 `app/canvas.js`. 증거는 `npm run verify` 검증 10(도착순·폭
문법·힌트 승격/폴백·drop_types·예산 집행 전부 초록, `app/captures/VERIFY-REPORT.json`
`cardLayout`). 실배선도 실측 완료(2026-08-18): 명시 지시 배관 통과 + `--resume`
2턴 자연어 체인에서 모델이 `drop_types`·`layout`을 자발 사용(N=1 일화 — 보장 아님,
`spike/cli-pipe/gateway/PROBE-LAYOUT-CURATION.json`).

1. **형상별 폭 문법 (기본, 결정적).** 컴팩트 형상(스트림·리더·스냅샷·이벤트 로그)은
   반폭 2열, 넓은 형상(테이블·시계열·호가·히트맵)은 전폭. 배치 순서는 도착순 위→아래.
   현행 구현(스트림·리더 반폭 2열 + 테이블 전폭)을 성문화한 것 — 실측이 문서를 이긴다.
2. **AI 개입은 폭 등급 승격·강등만.** 봉투의 layout 힌트로 반폭↔전폭 등급만 바꿀 수
   있다(예: 비교 질의면 스냅샷 2장을 나란히, 단건 집중이면 컴팩트 형상도 전폭 승격).
   배치 순서는 불가침. 힌트가 없거나 무효면 문법 기본값으로 폴백한다 — 배치는 힌트가
   있든 없든 항상 결정적이고 설명 가능하다.
3. **카드는 누적되지 않는다 — 턴별 큐레이션.** 매 턴 AI가 현재 질의와 무관해진 카드를
   제거하고 필요한 카드만 추가·갱신한다. 같은 타입 재요청 시 교체(현행 구현)는 그
   특수 사례다. 대화가 길어진다고 카드가 쌓이는 모델이 아니다.
4. **높이 예산 — 안전망.** 큐레이션 후에도 동시 카드 총높이 ≤ 캔버스 창 내부 높이의
   **2배**(스크롤 한 번 깊이). 초과하면 가장 오래된 카드부터 제거한다. 단 예산과
   무관하게 **최소 3장은 보장**(soul.md §5-2). 개수가 아니라 비율이라 해상도·창
   크기에 자동 적응한다. 큐레이션(3)이 먼저 돌므로 여기 닿는 경우는 드물어야 한다.
