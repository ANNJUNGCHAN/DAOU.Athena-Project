(`app/main.js:1094-1095,1139-1147`). 즉 지금 시스템은 "규칙이 아니라 이미 내린 LLM 판정의

### 1.2 차트 주기(D/W/M/Y) — 사용자가 예로 든 바로 그 결함이 실재한다

`app/lib/chart-card.js:140-149`가 카드 생성 시 주기를 **항상 하드코딩된 `'D'`**로 초기화한다.
`applyPeriod()`(`chart-card.js:638-648`)는 `resample()`(`app/lib/chart-resample.js:147-152`)로
**이미 받아온 일봉 배열을 로컬 재가공**할 뿐, 백엔드를 다시 부르지 않는다. render-plan 계약

항상 일봉 탭이 선택된 채 열린다** — 정확히 사용자가 지적한 문제가 코드로 확인된다.

부수 실측(부수 발견, §3 참조): `chart-resample.js:78-142`의 분봉/틱 재가공은 실제 틱 데이터가

소지 없음.

### 1.3 `presentation.layout`은 이미 있다 — 새로 설계할 필요가 없다

`generate_api.py:706-713`의 `base_layout()`이 kind+shape로부터 6종 중 정확히 하나를 함수적으로
산출하고, `build_common_screen_manifest()`(`generate_api.py:749-913`)가 이를 301개 매핑 전부에
부여한다. `render_screen_injection_map.py`(`plan/kiwoom-common-screen-injection-map.md` 생성)와
`render_screen_card_facts.py`(`kiwoom-common-screen-card-facts.json` 생성)는 **둘 다 이 manifest

어느 것도 "초기 옵션 상태"(주기 기본값 등)를 갖고 있지 않다 — manifest 705KB 전수 grep으로
`period`/`control`/`option_state`/`initial_state`/`default_option` 0건 확인됐다. **카드 *종류*
배정은 이미 결정론적으로 끝나 있고, 부족한 것은 (a) 런타임이 그것을 실제로 조회하도록 배선하는
것과 (b) 카드 종류를 넘어선 초기 옵션 상태(주기 등) 한 겹을 새로 생성하는 것 두 가지뿐이다.**

## 2. 설계 질문에 대한 답

### Q1. 두 카드 체계의 화해 — "공통 템플릿" = 무엇인가

사용자가 말한 "공통 템플릿"은 **6종 완전성 계층**(FactsCard/TableCard/CompoundCard/EventCard/
ActionCard/StatusCard)이다 — "TR이 호출되면 어떤 카드로 갈지 이미 정해져 있어야 한다"는 요구가
정확히 이 계층의 정의(`GLOSSARY.md` §2 "공통 API 카드 6종")와 일치한다. **카드 12종**(가격
시계열·랭킹 테이블·호가창 등, `canvas-taxonomy.md`)은 그 위에 선택적으로 얹는 **표현 계층
(렌즈)**로 spec §9가 이미 확정한 2계층 구조를 그대로 유지한다 — 이번 계획은 이 구조를 재론하지
않는다. 결론: **6종 배정을 결정론화하는 것이 이번 계획의 본체**이고, 12종 렌즈는 손대지 않는다
(차트 렌즈의 "주기"만 예외적으로 다룬다 — 이유는 Q2).

### Q2. TR→템플릿+옵션 상태 매핑의 SSOT

주입 맵(301개)은 이미 SSOT 체인 끝단의 **생성물**이다(`generate_api.py` → manifest →
`render_screen_injection_map.py`/`render_screen_card_facts.py`). 이 계획은 **재설계가 아니라
확장**이다 — `generate_api.py`의 `build_common_screen_manifest()`에 `presentation.controls`
(가칭, G002가 예정했던 "control hints" 개념) 필드를 추가해 **주기 도메인(CompoundCard 중
차트 12개)에 한해** 기본 주기를 TR 메타데이터(한글 TR명의 "일봉/주봉/월봉/년봉/분봉/틱" 키워드)
에서 결정론적으로 유도한다. 이 값은 손으로 채우지 않는다 — `ref/kiwoom-tr-inventory.json`의
기존 필드에서 유도하고, 매칭 실패는 추측하지 않고 명시적 실패로 남긴다(quirks.py의 "추측 금지"
원칙과 동형). SSOT는 그대로 `generate_api.py` + `ref/*.json`이고, injection-map.md·card-facts.json은
`--check` 게이트로 계속 재생성한다 — 손 편집 금지 원칙(CLAUDE.md §5)을 어기지 않는다.

### Q3. 런타임 결선 — 셀렉터부터 카드까지

`athena_resolve`가 발급하는 `plan_token`에는 이미 `operation_ref`가 서명 봉인돼 있다
(`GLOSSARY.md` §7 "실행 계획(plan token)"). `canvas_push.py`의 render-plan 라우트는 이
`plan_token`을 검증할 때 이미 `operation_ref`를 복호화한다(`selector.call()` 경로,
`canvas_push.py:99-107`) — **모델에게 다시 물어볼 필요가 없는 값이 이미 서버 손에 있다.**
이 계획은 `canvas_type`을 caller가 채우는 필수 필드에서 **서버가 `operation_ref`로 manifest를
조회해 결정하는 값**으로 뒤집는다. 모델이 보내는 `canvas_type`은 과도기 동안 감사용 힌트로만
남기고(불일치 시 로그, 신뢰하지 않음) 최종적으로는 스키마에서 제거한다(§Phase P5). **[r3]** 이
뒤집기는 캐시 리플레이 라우트(`canvas_push.py`)뿐 아니라 **모델이 실제로 매 최초 호출마다
부딪히는 콜드 경로**(`athena_mcp/canvas_data.py::render_with_plan()`)에도 동일하게 적용된다 —
하나만 고치면 사용자가 지적한 "런타임에 모델이 판단한다"가 콜드 경로에 그대로 남는다(§Phase P1b
Deliverable 1). AITS의
"카드가 주기 전환 시 백엔드를 직접 재호출"하는 인플레이스 패턴은 **이번 범위에 넣지 않는다** —
로컬 재가공(현재 구현)이 사용자가 예로 든 요구("일봉 호출 → 일봉 탭 선택 상태로 열림")를
충족하는 데 충분하고, 서버 재조회는 별도 최적화 라운드로 미룬다(이유: 지금 결함은 "탭이 틀리게
초기화된다"이지 "탭 전환이 느리다"가 아니다 — 문제를 정확히 좁혀서 고친다). **[r5·Critic 잔여]** 이때 `RenderPlanRequest.canvas_type`의 `pattern="^(chart|table)$"` 제약(canvas_push.py:75)을 먼저 완화해야 한다 — 안 하면 facts/compound 요청이 매니페스트 로직 도달 전에 FastAPI 파싱 단계에서 422로 죽는다(MCP enum 함정과 동형). 완화 후 실제 HTTP 왕복으로 facts 페이로드가 라우트 본문에 도달함을 증명하는 회귀 테스트를 수용 기준에 포함한다.

### Q4. Paper 작업의 실행 가능한 단위

301장을 그리지 않는다. 아트보드 26(API 주입 원장 · 도메인 × 카드 행렬)이 이미 301개 전부를
기계 생성 수치로 표에 담고 있다(`kiwoom-common-screen-spec.md` §10) — "모든 API 디자인 저장"
요구는 **이미 이 방식으로 충족돼 있다.** 이번 계획이 새로 만드는 유일한 열(column)은 §2가
생성할 "초기 옵션 상태"이므로, Paper 작업은 (a) 기존 25~34 실사(런타임 현실과 여전히 맞는지
교차 대조 — plan.md가 기록한 "장표와 구현 불일치" 전례가 있다) + (b) 보드 26에 새 열 1개
추가로 충분하다. 신규 보드 300여 장을 그리는 것은 과잉이며 GLOSSARY §2가 이미 "카드는 12종/6종
고정"이라 못박은 최소화 원칙과도 어긋난다.

### Q5. 기존 Ultragoal(G002~G007)과의 관계

이어받기다. `kiwoom-common-screen-handoff.md`는 G002(Normalized screen contracts and
generated control hints)에서 멈췄다(2026-08-15 기준). 그러나 G002가 원래 설계한 전체 계약
(`ScreenDefinition`/`ScreenDocument` + `listDefinitions/runRead/continueRead/...` renderer API,
§5)은 **2026-08-15 시점에는 존재하지 않았던 render-plan 파이프라인을 전제하지 않은 설계**다.
이 계획은 G002를 그 원래 큰 계약으로 완성하는 대신, **이미 동작 중이고 실측된 render-plan
파이프라인 위에 6카드 결정론만 얹는 좁은 부분집합**을 구현한다(RALPLAN-DR §Option A). G002는
"부분 완료"로 갱신하고, 전체 계약(특히 EventCard/ActionCard/StatusCard의 renderer API 통합)은
후속 라운드로 넘긴다 — 이유는 §4 RALPLAN-DR에서 상술한다.

### Q6. 지연 목표

이번 변경은 모델 왕복 횟수를 줄이지 않는다(여전히 `athena_resolve`가 필요) — 대신 **모델이
내리던 판단 하나(카드 종류)를 제거**해 판단 실패 가능성을 줄인다. 콜드 경로 목표는 현행 유지
(27.3s대, 병목은 모델 왕복이지 카드 결정이 아니다 — `latency-audit-2026-08-19.md` 결론 재확인).

## 4. RALPLAN-DR 요약

**모드: SHORT** (기존 검증 문화 — pytest/ruff/generate --check/npm verify — 가 이미 강한
회귀 방지 게이트이고, 주문·인증 등 고위험 표면은 이번 범위에서 명시적으로 제외돼 있음. 필요시
사용자가 `--deliberate`로 승격 가능).

### 원칙 (3~5개)

1. **실측이 문서를 이긴다** — 이미 동작 중인 render-plan(27.3s/222ms 실측)·manifest(301/301
   검증)를 재사용한다. 검증 안 된 가정 위에 새로 짓지 않는다.
2. **생성물은 손으로 고치지 않는다** — TR→카드/옵션 매핑의 SSOT는 `generate_api.py` 확장이지

3. **카드는 6종/12종 고정** — 신규 카드 종류를 만들지 않는다. 새 옵션 상태(주기 등)는 기존
   카드의 파라미터로 흡수한다.
4. **정보 정직성 > 미감** — 결정론적 배정이 실패하면 무음 오배정이 아니라 `free` 카드로
   안전 폴백하고 이유를 남긴다(§Phase P1b 수용 기준).
5. **병렬 대체 앱 금지·최소 침습** — 기존 `render-plan`/`canvas_transform.py`/`app/canvas.js`를
   확장한다. 새 파이프라인을 만들지 않는다.

### 결정 동인 (top 3)

1. **회귀 위험** — 이미 실사용 중인 캐시(222ms)·차트 경로(27.3s)를 건드리므로 무회귀 확장이
   최우선 제약이다.
2. **사용자의 문자 그대로의 요구** — "런타임에 모델이 카드 구성을 판단하지 않는다"(차트 주기
   예시)를 검증 가능한 형태로 충족해야 한다.
3. **기존 설계 자산의 재사용 가능성** — 6카드·301 매핑·Paper 아트보드가 이미 ~90% 존재하므로
   재설계가 아니라 결선(wiring)에 집중하는 것이 ROI가 높다.

### 옵션 (≥2, 장단점)

**Option A — 매니페스트 결선 (채택)**: `generate_api.py`의 기존 `presentation.layout`을 런타임
조회 테이블로 승격하고, `canvas_transform.py`/`canvas_push.py`가 caller의 `canvas_type` 대신
이 테이블을 신뢰하도록 바꾼다. 신규 "초기 옵션 상태"는 같은 생성기에 필드를 더한다.
- 장점: 기존 SSOT·검증 게이트(852+ 백엔드 테스트, generate --check) 재사용. 신규 코드 최소.
  회귀 위험 낮음(생성물은 이미 검증돼 있다). 3~6단계 계획 범위에 맞는다.
- 단점: EventCard(WS)·ActionCard(주문)·StatusCard(oauth) 37개는 이번 라운드에서 배선하지
  않는다(각기 다른 안전 게이트 소관이라 범위가 다르다) — 후속 라운드 필요.

**Option B — G002 전체 계약 신규 구현**: `kiwoom-common-screen-handoff.md` §5가 원래 설계한
`ScreenDefinition`/`ScreenDocument` 풀 계약과 `listDefinitions/runRead/prepareAction/...`
renderer API를 이번에 전부 구현해 6카드 전체(주문·WS·oauth 포함)를 한 번에 해결한다.
- 장점: 원래 Ultragoal 설계와 완전 정합. "한 번에 끝난다"는 심리적 완결성.
- 단점: 범위가 훨씬 크다(카드 6종 전체 × 상태 7종 × 3개의 서로 다른 안전 게이트). 이미 동작
  중인 render-plan 파이프라인과 병행 설계·충돌 위험. 검증 표면(852 backend + 220 app 테스트)
  전체에 대한 회귀 리스크 급증. 지금 당장 필요한 "차트 주기" 요구를 충족하는 데 필요 이상으로
  크고, 3~6단계 계획 범위를 초과한다.

**판정: Option A 채택.** Option B는 기각이 아니라 **후속 라운드로 순연**한다 — G002의 전체
계약은 EventCard/ActionCard/StatusCard를 다룰 다음 계획에서 재검토한다(§ADR Follow-ups).

### ADR

- **Decision**: `presentation.layout`(이미 존재하는 매니페스트 필드)을 render-plan 파이프라인의
  런타임 카드 결정 authority로 승격한다. 모델은 `operation_ref`(resolve 결과)만 넘기고, 카드
  종류·초기 옵션 상태는 백엔드가 조회해 결정한다.
- **Drivers**: 회귀 위험 최소화, 사용자의 문자 그대로 요구 충족, 기존 자산 재사용(§ 위 top3).
- **Alternatives considered**: Option B(G002 전체 계약 신규 구현) — 기각하지 않고 후속 라운드로
  순연. 재론 시점: EventCard/ActionCard/StatusCard 결선이 필요해지는 다음 계획.
- **Why chosen**: 이미 검증된 생성물(manifest)과 이미 실측된 런타임(render-plan)을 잇는 것이
  새 계약을 처음부터 짓는 것보다 검증 표면이 작고, 사용자가 준 구체적 예시(차트 주기)를 직접
  겨냥한다.
- **Consequences**: EventCard(23, WS)·ActionCard(12, 주문)·StatusCard(2, oauth) = 37개 매핑은
  이번 계획 종료 후에도 여전히 모델/기존 서브시스템(루틴·주문 티켓·oauth 내부 라우트) 소관으로
  남는다 — "301/301 런타임 결선 완료"라고 주장하면 안 된다. 264개 read/display 중 §1.3의
  P1a+P1b+P2a+P2b 범위(252+8+4=264) 전부가 카드 *종류* 결선의 대상이다. 단 12개 차트 CompoundCard
  중 **8개(P2a)만** 실제 `default_period` 배선을 받고, **4개(P2b, 분/틱)는 카드 종류만 배선되고
  기본 주기는 `null`+`'D'` 안전 폴백에 머문다** — "264/264 완전 배선"이라고 뭉뚱그리면 안 된다.
- **Follow-ups**: (1) EventCard/ActionCard/StatusCard 런타임 결선 계획(별도 라운드). (2) §3의
  부수 문제 2건 중 ka10007 title은 P0에서 흡수·수정한다. 합성 분봉/틱 UI 고지는 **[r3] 이미
  해결돼 있음이 확인됐다**(커밋 `ab877a42`, `chart-card.js:630` `updateNote()`) — 후속 태스크
  불필요, open-questions에서 제거한다. (3) AITS 인플레이스 재조회 패턴 채택 여부 재검토. (4)
  P2b가 유예한 분/틱 4개 TR 실배선 — 후속 라운드 필요조건: (a) `ka10079`/`ka10080` 응답 필드
  실측, (b) `chart-card.js`에 "진짜 분/틱 입력 모드" 신설(P2b 참조). (5) `presentation.controls`
  dict는 지금 `default_period` 키 하나만 담는 임시 형태다 — 향후 G002가 재추진되면 이 dict는
  "control hints" 분류 체계(주기·조정가·폼 등을 아우르는 온전한 taxonomy) 전체로 흡수될 수 있는
  **열린 확장점**이다. 지금 이 필드 하나로 그 taxonomy를 다 설계한 것처럼 취급하지 않는다.

### P2b — 분/틱 차트 배선 보류 (4/264, 이번 라운드 명시적 비배선)

**배경**: `ka10079`(주식틱차트조회요청) · `ka10080`(주식분봉차트조회요청) ·

129-131`의 계약("opts.ohlcv는 항상 일봉(D) 배열로 받는다 — 주/월/년/분/틱은 이 함수 안에서

**Deliverable**

  않는다** — 카드는 계속 하드코딩 `'D'` 안전 폴백으로 열린다(현행 유지, 회귀 아님).

  언제 다시 열지를 남긴다.

**후속 라운드 필요조건** (이번 계획은 착수하지 않는다 — ADR Follow-ups에도 동일 반영)

**수용 기준 (부정 테스트로 배제를 증명 — 조용히 제외하지 않는다)**

**검증**: `pytest`(신규 부정 테스트 포함), `generate_api.py --check`.

**리스크**: 이번 라운드에서 아무것도 배선하지 않는 것이 "리스크 0"은 아니다 — 사용자가 분봉/틱

- 264개 read/display 매핑 전부가 **`plan_token` 경로에서** 모델의 런타임 카드-종류 판단 없이

  P1a/P1b 게이트 분리 반영).
- **[r4, Architect 권고 4, 스코프 명문화]** 위 기준은 `plan_token` 경로에 한정된다 —
  `plan_token`이 없는 구경로 `_render_canvas()`는 이번 계획 이후에도 facts/compound를 포함해
  모델의 `canvas_type` 자유 선택을 계속 허용한다(P1b 항목 3). "모델의 카드 종류 판단 제거"는
