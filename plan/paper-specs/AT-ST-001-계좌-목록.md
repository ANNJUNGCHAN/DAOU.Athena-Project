## 무엇을 하는 화면인가

캔버스 창에 뜨는 제어 캔버스다. 대화 창에 "계좌 보여줘"라고 입력하면 열린다. Athena는 키움 모의투자 계좌만 다룬다. 등록된 계좌를 표(별칭·앱키·주문 API·연결 상태·마지막 검증)로 나열하고, 비활성 계좌를 클릭하면 그 계좌가 즉시 활성 계좌로 전환된다. 설정 창을 별도로 띄우지 않는, 캔버스 안에 뜨는 카드 하나짜리 화면이다(위치: 캔버스 창 › 제어 캔버스).

### Description

1. **캔버스 헤더**
   : 등록 계좌 수 요약
   – 캔버스 창 안의 카드다. 설정 창을 따로 띄우지 않는다

1.1. **계좌 등록 버튼**
   : 무채색 아웃라인 버튼 — 화면의 주 액션이 아니다
   – 누르면 AT-ST-002(계좌 등록)로 진입. 최초 등록 계좌는 자동 활성
   – 활성 계좌 삭제 시 남은 계좌 중 하나가 자동 승계. 마지막 하나는 삭제 불가

2. **계좌 행**
   : 별칭 · 앱키 · 주문 API · 연결 상태 · 마지막 검증
   – 별칭은 사용자가 붙이는 로컬 식별자다. 증권사 계좌번호가 아니다

2.1. **앱키 상태**
   : "등록됨 · 날짜"만 표시한다
   – 값도, 값의 일부도 표시하지 않는다

2.2. **주문 API 칩**
   : 기본 OFF
   – 켜는 것은 별도 게이트(AT-ST-003)에서만 가능하다

2.3. **상태 칩**
   : 활성 / 비활성 — 별칭 옆에 붙는다
   – 활성은 정확히 하나. 시세·잔고·주문이 이 계좌로만 나간다

3. **연결 상태**
   : 정상 / 검증 필요 / 실패 3종
   – 검증은 사용자가 명시적으로 실행한다. 자동 재검증 없음

4. **계좌 전환**
   : 비활성 행 클릭 시 즉시 전환된다
   – 확인 대화상자 없음. 직전 활성은 자동 비활성

## 데이터 계약

이 화면이 필요로 하는 데이터:
- 등록된 (모의투자) 계좌 배열, 각 항목: `별칭`(사용자 로컬 식별자, 증권사
  계좌번호 아님), `앱키 등록 상태`(등록일만, 값 아님), `주문 API 여부`(기본
  OFF, 이 화면에서는 읽기 전용 표시), `연결 상태`(정상/검증 필요/실패 중
  하나), `마지막 검증 시각`(있으면 타임스탬프, 없으면 "—"), `활성 여부`
  (정확히 하나만 true).

이 화면이 트리거하는 액션:
- **계좌 등록** — "+ 계좌 등록" 클릭 → AT-ST-002(계좌 등록) 화면으로 이동
  (이 화면 자체는 백엔드 호출 없음, 네비게이션만).
- **계좌 전환** — 비활성 행 클릭 → 클릭된 계좌를 활성으로, 직전 활성 계좌를
  비활성으로 전환. 확인 없이 즉시 반영.
- (암시적, 이 화면엔 트리거 UI 없음) **연결 상태 검증 실행** — 하단 스펙
  스트립의 "검증: 사용자가 실행" 문구가 있지만 실행 버튼이 이 목업에 없다.

백엔드 매핑 (evidence: `backend/athena_api/config.py`,
`backend/athena_api/kiwoom/auth.py`, `backend/athena_mcp/__main__.py`):

- **다중 계좌 목록 자체가 백엔드에 없다(핵심 갭)**. `backend/athena_api/config.py`의
  `Settings`는 `kiwoom_app_key: SecretStr | None`, `kiwoom_secret_key:
  SecretStr | None`을 **각각 한 개씩만** 담는 단일 전역 자격증명 모델이다
  (리스트도, 별칭도, 활성 플래그도 없음). 이 화면이 그리는 "별칭별 계좌
  2개, 그중 하나만 활성"이라는 구조를 채울 저장소/모델이 코드베이스에
  존재하지 않는다. `AT-CV-OAUTH-계좌-전환.md`가 이미 동일한 갭을 기록했다
  — 새로 설계해야 한다(계좌 레지스트리 + 계좌별 자격증명 보관 + 활성 플래그
  1개 강제).
- **연결 상태(정상/검증 필요/실패)** 개념도 백엔드에 없다.
  `backend/athena_api/kiwoom/auth.py`의 `KiwoomAuth`/`TokenManager`는 토큰
  발급 성공 여부(`is_ready`, `issue_token()`이 던지는 `KiwoomAuthError`)만
  가지고 있을 뿐, 계좌별로 "정상/검증 필요/실패" 3단계 상태를 저장하는
  필드나 "마지막 검증 시각"을 기록하는 로직이 없다.
- **"OS 자격증명 저장소"(앱키·시크릿 저장 위치) 주장은 아직 구현되지 않았다
  (갭)**. `kiwoom_app_key`/`kiwoom_secret_key`는 `pydantic-settings`의
  `SecretStr`로 `ATHENA_` 접두 환경변수/`.env`에서 읽힐 뿐이며, Windows
  Credential Manager/DPAPI나 `keyring` 같은 OS 자격증명 저장소 연동 코드는
  `backend/athena_api/` 어디에도 없다. `AT-ST-002-계좌-등록.md`,
  `AT-ST-007-비밀값-원칙.md`가 이미 동일한 갭을 각각 기록했다 — 이 화면도
  같은 미구현 저장 계층에 의존한다.
- **주문 API 칩(기본 OFF)**은 `Settings.enable_order_api: bool = False`
  (`config.py:27`)와 개념적으로 대응하나, 현재는 프로세스 전역 설정 하나
  뿐이라 "계좌별" OFF/ON을 표현하지 못한다. `AT-ST-003-주문API-활성화.md`가
  이미 이 갭(계좌별 게이트 부재)을 기록했다.
- **`backend/athena_mcp/__main__.py`의 register/list/rename 등은 무관하다**:
  이 CLI 서브커맨드들은 외부 MCP 서버 레지스트리(도구 서버 등록/승인/별칭)
  용이며, 이 화면의 "Kiwoom 계좌 별칭/목록"과는 완전히 다른 리소스다.
  어휘가 겹친다고(별칭·등록·목록) 재사용하면 안 된다.
- **계좌 전환 액션**: 이 화면의 "즉시 전환, 확인 없음" 문구가 실제로
  호출해야 할 백엔드 동작은 `AT-CV-OAUTH-계좌-전환.md`에 상세히 기록되어
  있다 — 토큰 폐기(`KiwoomAuth.revoke_token()` → `au10002`) → 자격증명
  교체 → 토큰 재발급(`KiwoomAuth.issue_token()` → `au10001`) 순서이며,
  `backend/athena_api/lifespan.py`가 시작 시 1회만 자격증명을 구성하고
  런타임 교체 경로가 없다는 점, `CredentialProcessLock`(`process_lock.py`)이
  머신당 자격증명 1개만 허용한다는 점도 동일하게 이 화면에 적용된다.

   추출 범위 밖이다.
7. **빈 목록(계좌 0개) 상태가 없다.** "2개 등록" 카운트와 두 행만 정적으로
   그려져 있어, 최초 진입 시(계좌가 하나도 없을 때) 카드가 어떻게 보이는지
   알 수 없다.
8. **다중 계좌 백엔드 모델 자체가 없다(구조적 갭, 이 화면 하나로는 범위를
   정할 수 없음).** `backend/athena_api/config.py`의 `Settings`는 앱키/
   시크릿 한 쌍만 담는 단일 전역 객체이고, 계좌 리스트·별칭·활성
   플래그·연결 상태·마지막 검증 시각을 담는 저장소가 어디에도 없다.
   `CredentialProcessLock`은 머신당 자격증명 1개만 허용해 "두 계좌가 동시에
   등록돼 있고 그중 하나만 활성"이라는 이 화면의 전제 자체가 현재 백엔드
   아키텍처와 얼마나 정합하는지도 확인이 필요하다(`AT-CV-OAUTH-계좌-전환.md`
   Open questions 5와 동일 계열의 질문).
