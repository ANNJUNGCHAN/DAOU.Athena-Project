# 04 · 공통 카드(MCP) — 기존 결정 대조

목적: "어떠한 MCP의 정보든 담을 수 있는 최소 공통 카드"를 새로 설계하기 전에, 이 저장소가 이미 같은 문제에 내린 결정을 대조한다. 새로 발명하지 않는다 — 이미 두 갈래가 각자 답을 냈고, 그 두 답이 서로 다르다.

---

## 1. 이미 결정된 것 — 이 설계를 구속하는 제약

### 1.1 캔버스 분류 원칙 (`plan/canvas-taxonomy.md`)

핵심 발상은 화면 단위가 아니라 **데이터 형상 단위**로 접는 것이다.

> "TR을 **화면 단위가 아니라 데이터 형상 단위**로 접는다. 288개 화면이 실제로 말하는 문장 구조는 열몇 개뿐이다." (`canvas-taxonomy.md` L13-14)

전용 캔버스가 정당화되는 조건과 자유 캔버스로 보내는 조건이 나뉘어 있다.

> "자유 캔버스는 실패가 아니라 **설계된 탈출구**다 (`ui/soul.md` §5-5)." (L48)
> "자유 캔버스가 얼마나 자주 열려야 '정상'인가의 임계치. **자주 열린다면 캔버스 체계가 틀린 것이다**" (L69)

즉 "범용 카드"를 만드는 이유가 "자유 캔버스가 너무 자주 열리는 것을 막기 위해서"라면, 이 저장소는 이미 그 문제의식을 갖고 있고 별도 중간 계층으로 답한 바 있다(§1.2).

### 1.2 공통 테이블 — "격상됨" (`plan/mcp-실행계획.md` §3, 신규 ④)

당초 초안은 공통 테이블을 "`#3 랭킹 테이블`의 일반화"로 적었으나, 뒤집혔다.

> "당초 '`#3 랭킹 테이블`의 일반화'로 적었으나 **방향이 반대였다. 공통 테이블이 부모고 랭킹 테이블이 자식이다.**" (`mcp-실행계획.md` L189)

그 결과로 만들어진 3단 계층이 정확히 "언제 전용 캔버스가 정당화되는가"에 대한 답이다.

```
자유 캔버스     ← 형상 자체를 모름               (최후의 탈출구)
공통 테이블     ← 레코드인 건 알되 스키마 모름    ★ 기본값
전용 캔버스     ← 형상·스키마 다 앎 (랭킹/호가/타임라인/체결로그)
```
(L192-195)

> "컬럼을 데이터에서 유도. 정렬·필터. **모든 테이블 형식의 기본 착지점**" (L201)
> "**자유 캔버스 열림 빈도를 크게 줄인다.** soul.md §5-5가 경고한 '자유 캔버스가 자주 열리면 캔버스 체계가 틀린 것'의 사이 층을 메운다" (L202)
> "단 **전부를 테이블로 밀지 않는다.** 호가(양방향 막대)·체결 로그(시간 흐름)·랭킹(순위 변동+스파크라인)은 테이블처럼 생겼지만 형상이 다르다. **기본값이되, 형상을 알면 승격한다**" (L203)

같은 문서, 별도로 기존 캔버스 #5(종목 스냅샷)도 일반화됐다.

> "`#5 종목 스냅샷` → **스칼라 카드 묶음** 일반화. 재무비율·감성점수도 들어감. **단, 파생 스코어는 근거 링크 없으면 렌더 거부**" (L208)

즉 갈래 A(MCP 게이트웨이 쪽)는 "임의 MCP 출력"을 **두 개의 이미 정의된 착지점**으로 나눠서 이미 답했다 — 레코드 배열이면 공통 테이블, 스칼라 묶음이면 스칼라 카드 묶음. "하나의 범용 카드"라는 발상 자체가 이 문서의 결정과 어긋난다: 이 문서는 형상별로 최소 2개의 서로 다른 기본 착지점을 이미 분리해 놓았다.

### 1.3 구현 상태 (`backend/athena_mcp/canvas.py`)

W1이 실제로 구현한 것은 신규 4종(스트림/리더/타임라인/테이블) + `free` 뿐이다. "스칼라 카드 묶음"은 **아직 코드화되지 않았다** — `CANVAS_SCHEMAS`에 `stream`/`reader`/`timeline`/`table` 4개만 있고 스칼라 카드 스키마는 없다(`canvas.py` L111-116). 문서 결정과 구현 사이에 갭이 있다.

## 2. 키움 "공통화면" 선례 — 공통이 되기 위해 무엇을 포기했나

`plan/kiwoom-common-screen-brief.md`와 `plan/kiwoom-common-screen-handoff.md`가 정의하는 공통화면은 **디자인 패턴이 아니라 매니페스트에서 결정적으로 생성되는 화면 계약**이다. 구체적으로:

- 권위 원본 3파일(`kiwoom-tr-inventory.json`, `kiwoom-output-profile.json`, `response-projections.json`)에서 `backend/scripts/generate_api.py`가 **결정적으로**(deterministic) `backend/ref/kiwoom-common-screen-manifest.json`을 생성한다(`handoff.md` §3).
- 이 매니페스트가 **301개 라우팅 매핑**(186 unsplit + 115 split-derived) 전부를 커버한다(brief.md "Scope and coverage").
- 264 read/display + 23 WebSocket + 12 order + 2 OAuth로 분류되고, 뒤 3개는 "guarded workflow"로 별도 취급된다(`handoff.md` §2).

**포기한 것 — 구체적으로:**

1. **전용 시각화를 기본값에서 제외했다.** 차트·호가·포트폴리오 같은 캔버스 분류 체계(`canvas-taxonomy.md`)의 결과물은 여기서 강등된다.
   > "기존 `plan/canvas-taxonomy.md`의 차트·호가·포트폴리오 등은 **선택적 semantic lens**다. 전수 커버리지 primitive가 아니며, **의미 정보가 부족한 route를 억지로 차트로 추론하지 않는다.**" (`handoff.md` §4, L102)
2. **최소 구성을 3개 재사용 프리미티브로 못박았다** — operation마다 화면 파일을 만들지 않는다.
   > "operation마다 별도 화면 파일을 만들지 않는다. 최소 구성은 하나의 공통 캔버스 shell과 세 개의 재사용 가능한 구성요소다: **Adaptive Record Canvas**(facts/table/mixed) · **Live Stream Canvas** · **Schema-driven Request Sheet**." (`handoff.md` §4, L88-100)
3. **숫자 강제 변환을 포기했다** — "손실 없는 셀"을 원칙으로 세웠다.
   > "lossless cell — `raw`와 `display`를 분리하고 **전역 숫자 강제 변환을 하지 않는다.**" (`handoff.md` §5, L116-117)
4. **자동 형상 추론을 포기했다** — projection이 항상 추론보다 우선한다.
   > "deterministic generator — 301개 definition을 G001 manifest에서 생성한다. **projection layout이 항상 일반 shape 추론보다 우선한다.**" (`handoff.md` §5, L121-123)

정리하면 키움 공통화면은 "예쁜 전용 렌더"를 포기하고 "결정적으로 생성 가능한 3-모드(facts/table/mixed) 최소 셸"을 택했다. 이건 정확히 사용자가 요청하는 "MCP 범용 카드"가 마주칠 트레이드다 — MCP는 서버마다 스키마가 제각각이므로(`mcp-실행계획.md` L109: "임의 스키마 레코드 | 서버마다 제각각") 전용 렌더를 기본값으로 못 쓴다는 점이 키움의 301개 라우팅과 구조적으로 동일하다.

**단, G002(ScreenDefinition/ScreenDocument)는 아직 미구현이다.** `handoff.md` §1: "G002 Normalized screen contracts and generated control hints — 진행 중, 미구현 · 다음 시작점." 즉 이 선례는 **설계는 확정, 코드는 없음** 상태다.

## 3. 신규 캔버스인가 / 공통 테이블의 일반화인가 / free의 재진술인가

세 갈래를 순서대로 검토한다.

### 3.1 `free`의 재진술인가 — 아니다

`canvas.py`의 `free`는 스키마가 없다. `validate_canvas_payload`는 `canvas_type`이 4종 중 하나가 아니거나 스키마 검증에 실패하면 무조건 `free`로 폴백하고, 그 사실을 `fell_back`/`fallback_reason`에 남긴다(`canvas.py` L127-164). `free`는 **형상 자체를 모를 때의 최후 착지점**이지(`mcp-실행계획.md` L192: "자유 캔버스 ← 형상 자체를 모름 (최후의 탈출구)"), 정의된 레이아웃이 없다. W4 계획은 `free`를 "자연어 → 캔버스 코드 생성 → 렌더" + 샌드박스로 그리고 있다(`mcp-실행계획.md` §4 W4, L272-277) — 즉 인스턴스마다 코드를 새로 생성해야 한다.

사용자가 요청하는 "최소 공통 카드"는 반대로 **한 번 정의하면 모든 MCP 출력에 재사용**되는 고정 셸을 뜻한다. 이는 `free`의 정의(형상 미상 + 코드 생성)와 정면으로 다르다. **`free`의 재진술이 아니다.**

### 3.2 공통 테이블(④)의 일반화인가 — 부분적으로 그렇다, 그러나 좁다

공통 테이블은 이미 "스키마는 모르지만 레코드인 건 아는" 데이터의 기본 착지점으로 **격상**됐다(§1.2). 사용자가 말하는 "어떠한 MCP의 정보든 담을 수 있는 카드"의 상당 부분 — 임의 MCP 툴이 뱉는 레코드 배열 — 은 이미 이 결정으로 커버된다.

그러나 `canvas.py`의 `TABLE_SCHEMA`는 `rows`(object 배열)를 **필수**로 요구한다(L97). 스칼라 하나짜리 응답, 키-값 프로필(예: DART `corp_code` 룩업), mixed 응답은 테이블 형상이 아니다. 갈래 A 문서는 이걸 별도로 "스칼라 카드 묶음"(구 #5, §1.2)에 배정했다 — **테이블과 스칼라 카드는 같은 캔버스가 아니라 형상별로 나뉜 두 개의 착지점**이다. 즉 "레코드면 테이블, 스칼라면 카드"이지 "MCP 출력이면 무조건 이 카드 하나"가 아니다.

### 3.3 신규 캔버스 유형인가 — 사실상 그렇다, 단 이미 유사물이 두 개 존재한다

사용자가 요청한 "형상 불문 단일 셸"은 갈래 A의 분리된 2-primitive(테이블/스칼라카드) 모델에는 없고, **갈래 B(Kiwoom)의 Adaptive Record Canvas**(facts/table/mixed 3-모드 단일 셸, §2)에 정확히 대응한다. Adaptive Record Canvas는 "형상을 안 나누고 모드로 흡수한다"는 점에서 사용자의 요청과 설계 철학이 같다.

**결론**: 이 요청은 (a) 갈래 A 기준으로는 "공통 테이블 + 스칼라 카드 묶음"이라는 **기존 2개 결정의 재조합**이고, (b) 갈래 B 기준으로는 **이미 설계된 Adaptive Record Canvas 그 자체**다. 어느 쪽으로도 "완전히 새로운 4번째 개념"은 아니다 — 두 개의 서로 다른 기존 답 중 하나를 고르는 문제다.

## 4. plan.md §5 action 1의 미해결 충돌과 이 카드의 관계

`plan/plan.md` §5는 정확히 이 지점을 미해결로 남겨 놓았다.

> "1 | **갈래 A·B 조율 — '공통 캔버스' 정의 통합** | A는 캔버스 16종, B는 301 라우팅 렌더. 상위 개념을 정하지 않으면 렌더러가 둘로 갈라진다 (`00-인수인계.md` §1 충돌 ①)" (`plan.md` §5, L173)

`plan.md`는 §9(아직 답 없는 질문)에서도 다시 같은 질문을 미결로 적는다.

> "**'공통 캔버스'의 상위 개념은 갈래 A인가 B인가** — §1 충돌 ①" (`plan.md` L267)

`00-인수인계.md` §1 충돌①의 원문:

> "**① '공통 캔버스' 개념이 양쪽에 따로 있다.**
> 갈래 A는 캔버스 16종(TR 12 + 신규 4)으로 접는다. 갈래 B는 **301개 라우팅 매핑을 'common canvas'로 렌더**한다고 쓴다.
> 같은 단어인데 스케일이 다르다. **어느 쪽이 상위 개념인지 정해야 한다. 안 정하면 렌더러가 둘로 갈라진다.**" (`00-인수인계.md` L33-35)

### 판정: 이 카드를 설계하는 것은 충돌을 해소하지 않는다 — 오히려 지금 당장 선택을 강제한다

"MCP 범용 카드"를 실제로 만들려면 §3에서 본 것처럼 갈래 A(테이블+스칼라카드 분리)와 갈래 B(Adaptive Record Canvas 단일 모델) 중 하나를 구현 기반으로 골라야 한다. 이건 독립된 신규 작업이 아니라 **plan.md §5 action 1이 말한 "상위 개념 미정" 문제의 한 인스턴스**다. 지금 이 카드를 설계·구현하면:

- 갈래 A 모델을 따르면: 이미 존재하는 `table`/(미구현) 스칼라 카드 스키마를 그대로 쓰게 되고, 충돌은 **여전히 미해결로 남지만 이 카드 자체는 완성된다.**
- 갈래 B 모델을 따르면: `canvas.py`에 없는 facts/table/mixed 3-모드 셸을 새로 만들게 되고, 이는 사실상 **G002 ScreenDefinition/ScreenDocument를 MCP 게이트웨이 쪽으로 끌어오는 것**과 같다 — 갈래 B의 미구현 부분(G002, `kiwoom-common-screen-handoff.md` §1)을 갈래 A 영역에서 먼저 구현하게 되는 셈이다.

어느 쪽을 고르든 "공통 캔버스가 A냐 B냐"라는 미해결 질문에 **암묵적으로 답하는 것**이 된다. 즉 이 카드 설계는 충돌을 **독립적으로 우회할 수 없다** — 설계자가 이 충돌을 명시적으로 재판정하거나, 최소한 "이번 카드는 어느 모델을 따른다"를 선언해야 한다. 선언 없이 만들면 `00-인수인계.md`가 경고한 "렌더러가 둘로 갈라진다"가 그대로 실현된다 — 이번엔 캔버스 종류가 아니라 **"MCP 정보를 담는 카드"라는 같은 목적의 두 구현**으로.

## 5. AT-ST-004는 이 요청과 다른 화면이다 (참고 대조)

`plan/paper-specs/AT-ST-004-MCP-서버목록.md`는 **등록된 MCP 서버 목록**을 보여준다 — 별칭·연결상태·허용툴수·protocol·실행명령이 행이다(스펙 Description 2번, L27-36). 이건 "MCP 서버라는 개체"에 대한 관리 화면이지, "MCP 툴 호출 결과(임의 데이터)"를 렌더하는 화면이 아니다.

행 클릭 시 이동할 상세 화면(툴 목록·감사 로그)은 이 보드에 **없다**.

> "AT-ST-005(승인 화면), 행 클릭 시 이동하는 상세 화면은 **이 보드에 없어 인터랙션의 종착점을 확인할 수 없다.**" (AT-ST-004 문서, Open questions #6, L225)

따라서 사용자가 요청한 "어떠한 MCP의 정보(=툴 호출 결과)든 담는 카드"는 AT-ST-004가 **커버하지 않는다.** AT-ST-004는 "MCP 서버 목록 카드"이고, 요청은 "MCP 툴 출력 카드"다 — 이름이 비슷해 보이지만 서로 다른 화면이며, 후자는 아직 어떤 Paper 문서에도 없다.

## 요약

| 질문 | 답 |
|---|---|
| 이미 결정된 것이 있는가 | 있다 — 공통 테이블(④, 격상됨) + 스칼라 카드 묶음(구 #5 일반화), 그리고 별개로 Adaptive Record Canvas(facts/table/mixed) |
| 두 답이 같은가 | **아니다.** 갈래 A는 형상별 2-primitive 분리, 갈래 B는 단일 3-모드 셸. plan.md §5 action 1이 이 불일치를 아직 미해결로 명시 |
| 신규 캔버스 유형인가 | 아니다 — 기존 두 결정 중 하나의 재사용/재조합이다 |
| free의 재진술인가 | 아니다 — free는 형상 미상 + 코드 생성이 전제. 이 카드는 고정 셸 재사용이 전제 |
| 설계하면 충돌이 풀리는가 | **아니다. 오히려 지금 당장 A/B 중 하나를 고르도록 강제한다.** 선언 없이 만들면 "렌더러가 둘로 갈라진다"는 기존 경고가 실현된다 |
| AT-ST-004가 이미 이 요청을 커버하는가 | 아니다 — AT-ST-004는 서버 목록 관리 화면이지 툴 출력 렌더 화면이 아니다. 후자는 어떤 Paper 문서에도 없다 |
