## 0. 화면 구조도가 이미 답하고 있는 것

`75-0`("05 · 화면 구조도")는 시스템(부팅, 온보딩)과 "상시 운영"(대화 창 계열, 캔버스 창
계열) 두 갈래만 그린다. **AT-ST-\* 계열은 이 다이어그램에 아예 등장하지 않는다.** 대화
창 하위에는 "기본(이력 3턴) · 확장(리사이즈) · 답변 3상태"만, 캔버스 창 하위에는
"시계열 · 호가 · 관측"만 있다(75-0 jsx 실제 텍스트). 이는 설계 스스로 설정 화면군을
"세 번째 창"이나 "상시 노출 상태"로 취급하지 않는다는 뜻이다 — 대화 창이 필요할 때
확장되거나, 캔버스 창 안에 카드 하나가 뜨는 식으로만 존재한다.

`8N-0`("06 · 화면 목록 · ID 체계")의 "화면 ID 체계" 패널은 타입 코드를 이렇게 정의한다:

> SY : 시스템 (부팅 · 온보딩)
> CH : 대화 창
> CV : 캔버스 창

**"ST"는 이 범례에 정의돼 있지 않다.** AT-ST-001~007이 7개나 있는데도 범례 문서(06)는
이를 언급하지 않는다 — §7 열린 질문 참고.

### 1.1 온보딩(AT-SY-002/003) — 대화 창

두 화면 모두 800×690 "Onboarding Window" 목업이지만, 이는 **대화 창이 최대 높이로
확장됐을 때의 콘텐츠**를 보여주는 스펙 시트 표기다. 실제 앱에는 세 번째 창이 없다 —
`app/main.js`가 만드는 창은 `chatWin`, `canvasWin` 둘뿐이고(`main.js:93-103`), 대화
창은 이미 `chatBaseH`(204)~`chatMaxH`(788) 사이에서 신축하도록 구현돼 있다
(`main.js:22-26`, `127-135`). 온보딩은 이 신축 범위 안에 콘텐츠를 새로 채우는 문제다.

### 1.2 계좌·MCP 목록(AT-ST-001/004) — 캔버스 창의 "제어 캔버스"

`QN-0` 캡션 원문: "캔버스 창에 뜨는 제어 캔버스다. 대화 창에 "계좌 보여줘"라고
입력하면 열린다." `QQ-0` 캡션 원문: "캔버스 창에 뜨는 제어 캔버스다. 대화 창에 "MCP
서버 보여줘"라고 입력하면 열린다. 별도 설정 창은 없다." 두 화면 모두 Description
1번 항목에 동일한 문구가 반복된다 — "캔버스 창 안의 카드다. 설정 창을 따로 띄우지
않는다"(QN-0 2V0-0 / QQ-0 유사 항목). `canvas.js`의 기존 `addCard(type)`(`canvas.js:112-116`)가
`stream`/`reader`/`table` 세 카드를 만드는 것과 정확히 같은 자리에 `accounts`/`mcp`
카드가 추가되는 모양이다.

### 1.3 등록·활성화·승인·probe(AT-ST-002/003/005/006) — 부모 카드 내부 시트

이 네 화면은 스스로 "위치"에 캔버스 창이나 대화 창을 쓰지 않고, **부모 화면 이름
자체**를 적었다("계좌 목록 › 등록 시트", "MCP 목록 › probe"). 즉 새 캔버스나 새 창이
아니라 AT-ST-001/004 카드가 내부적으로 여는 시트·게이트다. 진입 트리거도 이를
뒷받침한다:

- AT-ST-002 진입: QN-0 Description 1.1 — "누르면 AT-ST-002(계좌 등록)로 진입"(카드
  안 버튼 클릭)
- AT-ST-003 진입: QN-0 Description 2.2 — "켜는 것은 별도 게이트(AT-ST-003)에서만
  가능하다"(카드 안 칩 클릭)
- AT-ST-005 진입: QQ-0 캡션·Description(붙여넣기 텍스트박스가 카드 안에 있음, 별도
  네비게이션 언급 없음)
- AT-ST-006 진입: QR-0 Spec Note(VZ-0) — "붙여넣기만으로는 승인되지 않는다 →
  AT-ST-005", 그리고 QR-0(2OQ-0) — "승인은 "서버 시작"까지, 툴 호출은 AT-ST-006에서
  별도 확인한다"

넷 다 캔버스 창의 좌표계 안에서 일어나는 DOM 상태 전환이지 새 IPC 왕복 대상(새 창
띄우기)이 아니다.

### 1.4 AT-ST-007 "비밀값 저장 · 표시 원칙" — 화면이 아니라 정책

"위치" 필드가 유일하게 `부록`인 화면이다. 캡션 원문: "값은 입력 직후 메인
프로세스로 전달되어 OS 자격증명 저장소에 암호화된다 — 화면(렌더러)은 비밀값을 한
번도…"(1YN-0, 잘림). 이 내용은 AT-ST-002(QO-0 Description 3 "저장·표시 원칙")와
AT-ST-005(QR-0 "환경변수 : 키 이름만 · 값은 표시하지 않는다")가 이미 각자 인용하고
있다. **라우팅 목적지로 구현하지 않는다.** 모든 비밀값 입력·표시 지점이 지켜야 할
공통 규칙 문서로만 취급한다.

### 1.5 AT-CV-OAUTH 3건 — 대화 창, ID 접두사와 실제 배치가 어긋남

`1FC-0`("23 · AT-CV-OAUTH 인증 토큰 상태")의 Note(1J8-0/1J9-0) 원문: "인증 화면은
별도의 창이 아니라 대화 창이 확장된 상태다. 계좌 등록(AT-ST-002) 직후 한 번, 이후에는
대화 창에서 재진입한다." 목업 창 이름도 "Auth Window" 800×690으로 온보딩 창과 동일
치수·구조(Head/Body/Foot)다. **ID 접두사는 CV(캔버스)인데 실제 배치는 CH(대화)
계열이다** — §7-1에서 모순으로 별도 기록한다.

`1Q0-0`("24 · AT-CV-OAUTH 토큰 4상태")는 별도 화면이 아니라 위 화면의 **상태
4종(① 인증 필요 → ② 준비됨 → ③ 재발급 중 → ② 준비됨, ④ 만료)** 문서다: "계좌 등록
이후 토큰이 거치는 상태. 창 높이는 변하지 않고 숫자와 색만 바뀐다"(1Q7-0).

`2J8-0`("25 · AT-CV-OAUTH 계좌 전환")은 토큰 상태 화면 내부에서 파생되는 하위
뷰다: "계좌 전환은 목록에서 고르는 일이 아니라 인증을 다시 하는 일이다"(2RD-0,
잘림) — "위치"가 "토큰 상태 화면에서 계좌 선택"이라 AT-ST-001의 계좌 전환(비활성
행 클릭)과는 다른 화면임에 주의.

## 3. 파일 레이아웃 제안 — `app/` 아래, 기존 패턴을 그대로 늘린다

기존 구조는 **창마다 렌더러 한 벌**(`chat.*`/`canvas.*`) + `lib/`에 순수 렌더링
유틸(`sanitize.js`/`markdown.js`/`mockdata.js`)이다. 새 화면군은 이미 있는 두 렌더러의
연장선이지 새 렌더러가 아니므로, 아래처럼 같은 파일에 얹거나 같은 패턴의 `lib/` 모듈을
추가한다.

```
app/

  chat.js           # 온보딩 상태 머신(2/3→3/3), pickCanvasTypes()에 "계좌"/"MCP" 키워드 추가
  chat.css          # 온보딩 전용 클래스(.onboard-step, .cli-row, .account-form) — turn/history 톤 재사용
  canvas.js         # addCard() switch에 'accounts'/'mcp' 케이스 추가 (stream/reader/table과 동일한 자리, canvas.js:112-116)
  canvas.css         # .card.accounts / .card.mcp 카드 스타일 + 카드 내부 시트(.sheet) 오버레이 스타일

```

**왜 새 창이 아니라 이 자리인가**: `main.js`가 만드는 `BrowserWindow`는 정확히
`chatWin`·`canvasWin` 둘뿐이다(`main.js:93-103`). §1의 "위치" 필드 어디에도 세 번째
창을 요구하는 문구가 없고, `ui/soul.md` §8은 "창이 셋 이상이다"를 점수와 무관한
즉시 탈락 조건으로 명시한다. 새 `.html`/새 `BrowserWindow`를 추가하는 순간 이
탈락 조건에 걸린다.

**왜 `lib/`에 새 모듈을 두는가**: `sanitize.js`/`markdown.js`는 이미 "문자열을
`innerHTML`로 파싱시키지 않고 직접 DOM 노드를 만들어 붙인다"는 계약을 갖고 있다
(`markdown.js:3`, `AGENTS.md:34-35`). 온보딩·설정 화면은 비밀값(APP KEY/SECRET
KEY)과 사용자 식별자(별칭, 계정 이메일)를 다루므로 같은 계약이 반드시 적용돼야
한다 — `canvas.js`/`chat.js` 안에 인라인으로 늘리면 이 경계가 흐려진다.

## 4. IPC 계약 추가안

기존 채널은 전부 `athena:*`(창 제어·이벤트) 아니면 `athena__render_canvas`(미래 MCP
툴 호출과 같은 모양, `main.js:199-205`) 두 갈래다(`main.js`/`chat.js`/`canvas.js`
전수 조사 — `athena:init`, `athena:set-chat-height`, `athena:collapse-canvas`,
`athena:highlight-canvas`, `athena:add-canvas`, `athena:clear-canvases`,
`prime-clip`/`primed`/`run-animation`/`animation-done`(창 내부 애니메이션 핸드셰이크),
`athena__render_canvas`). 아래 제안은 이 두 규칙을 그대로 따른다. **이름은 제안이다
— 스펙 문서 자체는 와이어 이름을 지정하지 않는다.**

### 4.1 새 채널이 필요 없는 부분

AT-ST-001/004(제어 캔버스 진입)는 **기존 `athena__render_canvas` 계약을 그대로
재사용**한다. `chat.js`의 `pickCanvasTypes()`(`chat.js:108-116`)에 정규식만
추가하면 된다:

```js
if (/계좌|account/i.test(t)) picked.push('accounts');
if (/MCP|엠씨피/i.test(t)) picked.push('mcp');
```

`CANVAS_PLAN`(`chat.js:102-106`)에 `accounts`/`mcp` 항목을 추가하고, `canvas.js`의
`addCard(type)`(`canvas.js:112-116`)에 두 케이스를 추가하면 새 IPC 채널 없이
기존 왕복으로 끝난다. AT-ST-002/003/005/006(부모 카드 내부 시트)도 §1.3 근거대로
새 캔버스·새 채널이 아니라 카드 내부 DOM 상태 전환이라 기본적으로 채널이 필요 없다.

### 4.2 새 채널이 필요한 부분 — 비밀값이 렌더러를 벗어나는 지점

QO-0 Description 3: "OS 자격증명 저장소(DPAPI)에 암호화 저장한다 — 저장 후에는
화면·로그에 다시 나타나지 않는다." 1K3-0 Description 3: "입력값은 렌더러를 거치지
않고 메인 프로세스로 직행한다." **렌더러 프로세스가 값을 들고 있어서는 안 되므로**,
이는 진짜 새 IPC 왕복이 필요한 유일한 지점이다.

## 5. 하지 말아야 할 것 — `app/` 기존 규칙 + `ui/soul.md` 근거

1. **세 번째 최상위 창을 만들지 않는다.** `ui/soul.md` §8 탈락 조건: "창이 셋
   이상이다." 온보딩·설정·인증 전부 `chatWin` 또는 `canvasWin` 안에서 해결한다
   (§1 표 그대로).
2. **설정 진입로를 커맨드바 하나로만 묶지 않되, 커맨드바 경로를 없애지 않는다.**
   `ui/soul.md` §3: "설정도, 모델 지정도, 주기 설정도, 계좌 연결도 — 전부
   커맨드바로 부른다." §8 탈락 조건: "설정이 커맨드바가 아닌 다른 경로로만 접근

## 7. 열린 질문 — 스펙 자체가 모호하거나 서로 충돌하는 지점

1. **ID 체계 범례와 실제 사용의 불일치.** `8N-0`의 "화면 ID 체계" 패널은 SY/CH/CV
   세 타입만 정의한다("SY : 시스템", "CH : 대화 창", "CV : 캔버스 창"). 그런데
   AT-ST-\* 7개 화면의 "ST"는 이 범례에 없고, AT-CV-OAUTH 3개 화면은 CV(캔버스)
   접두사를 쓰면서도 스스로 "별도의 창이 아니라 대화 창이 확장된 상태"라고
   말한다(1J9-0) — CH여야 할 화면이 CV로 명명돼 있다. 둘 다 실제 `find_nodes`/`get_jsx`
   호출로 확인한 텍스트이며 매끄럽게 설명되지 않는다.
2. **온보딩 "1 / 3" 단계가 어디에도 없다.** AT-SY-002는 스스로 "단계 표기(2 /
   3)"라 하고 AT-SY-003은 "3 / 3 — 마지막 필수 단계"라 한다. `get_basic_info`가
   반환한 22개 아트보드 전체를 훑어도 "1 / 3"을 표기하는 화면을 찾지 못했다.
   부팅 화면(`1M-0`, AT-SY-001)은 자체적으로 "부팅 시퀀스"라는 4단계 타임라인을
   따로 갖고 있어 이것이 "1/3"과 같은 단계인지는 스펙에 명시되지 않는다.
3. **CLI 로그인 연동 방식이 스펙 스스로 미정이라고 적혀 있다.** EV-0 각주(빨간
   글씨, `#D40000`로 강조): "브라우저 로그인 연동 방식(OAuth 리다이렉트 / CLI
   로그인 명령 위임) 미정 — 협의 필요." §6 0단계가 이 결정에 막혀 있다.
4. **AT-CV-OAUTH(토큰 상태) 재진입 트리거가 이름이 없다.** "위치"는 "계좌 등록
   직후 1회 · 이후 재진입"이라고만 적혀 있고, 재진입을 유발하는 구체적
   동작(자연어 명령? 토큰 만료 토스트? AT-ST-001의 어떤 칩 클릭?)은 스펙 원문
   어디에도 없다.
5. **대화 창 너비 제한값이 스펙 자체에서 미확정인데 앱은 이미 숫자를 고정했다.**
   `BZ-0`(메인 구조) 자체가 빨간 글씨로 "※ 대화 창 너비 제한값(960 /
   1560px)은 제안치 — 협의 필요"라고 적어뒀다. 그런데 `app/main.js:24`의
   `DESIGN.chatW = 1560`은 이미 이 제안치를 확정값처럼 쓰고 있다. 이번 통합
   작업이 대화 창 콘텐츠(온보딩 등)를 더 채우기 전에, 너비가 실제로 최종
   확정됐는지 먼저 확인하는 편이 안전하다.
6. **AT-ST-001/004 제어 캔버스 카드의 전용 닫기 동작이 문서화돼 있지 않다.**
   여는 방법(자연어 트리거)은 스펙에 명시돼 있으나, 카드 하나만 닫는 동작은
   이번 추출 범위(Description·Note·Spec Strip 전체)에서 찾지 못했다. 현재 앱의
   유일한 문서화된 퇴장 경로는 캔버스 전체를 접는 전역 Esc뿐이다
   (`main.js:192`, `chat.js:263`).
7. **페이지 번호 "23"이 두 아트보드에 중복된다.** `1K3-0`("23 · AT-SY-003 온보딩
   계좌")과 `1FC-0`("23 · AT-CV-OAUTH 인증 토큰 상태") 둘 다 프레임 이름과
   Spec Panel의 "Page No" 필드가 "23"이다(`get_basic_info` 실제 좌표로 서로 다른
   아트보드임은 확인됨). AT-CV-OAUTH 3건(23/24/25)이 원본 문서에 나중에
   추가되면서 기존 페이지 번호와 재정렬되지 않은 것으로 보이나, 문서 자체가
   이를 설명하지 않는다.
