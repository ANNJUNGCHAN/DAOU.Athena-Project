### 결정 2의 정확한 경계

"주문 기능 전체 보류"를 고른 것이 **아니다.** 갈린 지점은 **자동 발동**이다.

| | |
|---|---|
| **없앤다** | 조건 도달 시 Athena가 **스스로 시장가를 쏘는** 감시 주문 |
| **남긴다** | 사용자가 주문 티켓(캔버스 #8)에서 **직접 집행**하는 주문. AI 제안이 프리필된 상태 |

즉 녹취 2의 *"감시 주문 걸어놓으면 어떻습니까"* 는 *"손절가 닿으면 알려드릴게요"* 로 바뀐다.
`enable_order_api`는 계속 끄고 시작하되, 수동 주문 단계에서 켠다.

### 결정 3이 지불하는 대가 — 명시

녹취 2의 핵심 시나리오는 *"일을 하느라 장 대응을 못 한다"* 이다.
**PC 토스트만으로는 사용자가 Athena가 돌아가는 그 PC 앞에 있어야 알림을 본다.**

→ 1단계에서 **핵심 시나리오가 부분적으로만 성립한다.** 이건 결함이 아니라 유예다.
2단계에서 외부 채널(텔레그램 등)을 붙이면 해소된다. **그 전까지는 "퇴근 후/외출 중 알림"을 기능으로 약속하지 않는다.**

## 1. 녹취 2가 바꾸는 것

녹취 1은 *어떻게* MCP를 붙이나였다. 녹취 2는 ***왜*** 붙이나에 답한다 — **원인 규명**.

> *"삼성전자가 5% 급등했는데, 그 오른 원인이 공시나 MCP 같은 거 다 뒤져서 봤을 때는 이런 것 같습니다"*

삼성전자 +5%는 키움이 알려준다. **왜 올랐는지는 키움이 원리적으로 못 알려준다.**
코드 조사로 확정: 키움 208개 TR 전체에 뉴스·공시·해외 데이터가 **0건**이다.

→ MCP는 부가기능이 아니라 **제품의 심장**이다. 그리고 [`mcp-실행계획.md`](mcp-실행계획.md) §3의 신규 캔버스 ③ **타임라인**(가격축 × 이벤트 핀)이 정확히 이 화면이다.

## 2. 사용자 회의론에 대한 답

> *"실시간으로 계속 정보를 받아가지고 AI가 왔다 갔다 할 수 있다, 이런 걸 본 적이 없어. 회의적이다."*

**절반은 맞다.** "AI가 항상 깨어서 시장을 본다"는 안 되고, 해서도 안 된다.
비용 때문이 아니다(범위 밖). **품질 때문**이다.

| | 매 주기 LLM을 부르면 |
|---|---|
| **지연** | 20종목 훑는 데 수십 초. 파수꾼은 WS 이벤트에 밀리초로 반응한다 |
| **알림 피로** | LLM은 *"특이사항 없음"*을 잘 못 한다. 매번 말할 거리를 찾아낸다. soul.md §6 정면 위반 |
| **재현성** | 임계값은 로그로 검증된다 — *"왜 안 불렀냐"*에 답할 수 있다. LLM 판정은 못 한다 |
| **정직성** | 매번 보면 매번 그럴듯한 인과를 만든다. **환각 인과.** 금융에서 최악의 실패 모드 |

**되는 구조: "AI가 항상 깨어있다"가 아니라 "AI를 깨우는 값싼 파수꾼이 항상 깨어있다".**

```
        WebSocket (0B·0D·1h)          MCP 뉴스/공시 툴
                 │                            │
            ┌────▼────┐                  ┌────▼────┐
            │ 시세    │                  │ 뉴스    │   ← 파수꾼 보드
            │ 파수꾼  │                  │ 파수꾼  │      LLM 0 · 결정론
            └────┬────┘                  └────┬────┘
                 └──────────┬─────────────────┘
                            ▼
                      ┌───────────┐
                      │  조사관   │  ← LLM. 파수꾼이 깨울 때만
                      │  (상관)   │     여러 MCP 교차검증 · 파급 추적
                      └─────┬─────┘
                    ┌───────┴───────┐
              중요 ─┤               ├─ 안 중요
                    ▼               ▼
                 알림(방해)      원장 적재(조용)
```

**조사관의 일은 요약이 아니라 상관(correlation)이다.**
시세 파수꾼이 *"삼성전자 +5%, 거래량 4배"*, 뉴스 파수꾼이 *"HBM 관련 신규 3건"* 할 때 **둘을 이어붙여야** 녹취가 요구한 인과가 나온다. 따로 놀면 알림 두 개다.

비용 제약이 없으므로 **얕은 감시 × 깊은 조사**가 최적점이다. 조사관은 아낄 이유가 없다 — 여러 MCP를 훑고, 상충 뉴스를 교차검증하고, 연관 종목 파급까지 추적한다.

## 4. 예산의 진실 — 설계문서 정정 2건 ★

코드 조사가 기존 설계문서의 오류를 두 건 찾았다. **[`ui/round-1R/answer.md`](../ui/round-1R/answer.md) 수정이 필요하다.**

### 정정 1 — `answer.md:105` "보유 20종목 스캔 = 4초" 는 **틀렸다**

레이트리미터의 per-API 키는 **TR ID 문자열 하나뿐**이고, 종목코드는 키에 안 들어간다.

```python
# rate_limiter.py:11-30 — per_api_rate=1, api_starts: defaultdict[str, deque]
# client.py:95 — acquire(api_id), api_id는 순수 tr_id
# lifespan.py:39 — RateLimiter(rate_per_second=5.0), per_api_rate는 기본값 1
```

→ `ka10008`처럼 종목코드 1개만 받는 TR로 20종목을 순회하면 **전역 5건/초와 무관하게 TR당 1건/초로 직렬화**된다. **4초가 아니라 약 20초다.**

### 해법 — 멀티코드 TR / 시장 전체 TR

| TR | 성질 |
|---|---|
| `ka10095` 관심종목정보 | **종목코드를 `\|`로 여러 개** (models.py:4020-4023). 현재가·등락율·거래량·체결강도·호가까지 한 방에 |
| `ka01301` 관심종목 그룹 상세 | 그룹ID 하나로 그룹 전체 |
| `ka10016/19/23/27/54` | `stk_cd` 자체가 없다. `mrkt_tp`만 받아 **시장 전체를 1콜로 스캔** |

→ **감시 배치는 "종목별 TR 20회"가 아니라 "멀티코드/시장전체 TR 1~2회"로 설계한다.**

**남는 하한 하나**: `ka10008`(투자자별 수급) 류는 멀티코드 TR이 없다. 보유종목 수급 디테일을 매 주기 갱신하려는 요구는 **구조적으로 20초/사이클 하한**을 갖는다. 사용자에게 명시할 트레이드오프다.

### 정정 2 — `answer.md:96` "WebSocket은 예산에 안 걸린다" 는 **정상 상태에서만** 참

```python
# ws_client.py:94-99  execute() → REG/REMOVE 전송 전 acquire(tr_id)
# ws_client.py:168    LOGIN도 acquire('LOGIN')
# ws_client.py:200-202 REAL 수신 경로에는 acquire 없음 ← push는 진짜 공짜
# ws_client.py:253-255 _restore_subscriptions() 재연결 시 구독마다 재소모
```

- **REAL push 수신** = 예산 0. 초당 다건이 쏟아져도 무관 ✅
- **구독 등록/해제(REG/REMOVE), LOGIN, 재연결 시 자동 재구독** = REST와 **같은 리미터를 먹는다**

→ **"캔버스를 자주 열고 닫으며 구독을 갈아끼우는 UX"는 REST 조회와 예산을 다툰다.** 구독 churn을 억제하는 설계가 필요하다(캔버스를 닫아도 구독은 잠시 유지하는 grace period).

## 5. 뉴스 파수꾼 — 결정론 필터가 LLM을 막는다

시세는 숫자라 임계값으로 끝난다. 뉴스는 비정형 텍스트라 "필요한 정보"를 가리는 건 판단이고, 판단은 LLM이다.
그래서 뉴스 파수꾼의 1단은 임계값이 아니라 **싸구려 결정론 필터**다.

| 층 | 하는 일 | LLM |
|---|---|---|
| 수집 | 게이트웨이가 MCP 뉴스 툴 직접 호출 | 0 |
| 필터 | 기사 해시 중복 제외 · **매체 재배포 중복 제거** · 보유/관심 종목·계열사·테마 키워드 매칭 | 0 |
| 판독 | 남은 것만 LLM. **요약 + 알림 판정을 한 번의 호출로** | 1 |
| 처리 | 중요 → 알림 / 안 중요 → 원장 적재 | 0 |

**"5분마다 뉴스를 부른다" ≠ "5분마다 LLM을 부른다".**
5분 간격이면 대부분의 주기에서 신규가 0건이거나 전부 중복이다. 그때 LLM은 안 깨어난다.

### 중복도 — 실측으로 부분 정정 (2026-08-15)

*"연합뉴스 하나가 수십 개 매체로 재배포되니 중복 제거가 가장 크다"* 고 썼는데, **파수꾼이 실제로 쓸 정렬에서는 그렇지 않았다.**
`search_news` "삼성전자" 100건 실측(`spike/captures/S2B-naver-news-*.json`):

| 정렬 | 고유 도메인 | 제목 중복 그룹 | 중복 아이템 |
|---|---|---|---|
| **`sort=date`** (파수꾼이 쓸 정렬) | 69/100 | **0개** | **0** |
| `sort=sim` | 51/100 | 7개 | 15 |

**`sort=date` 100건에서 재배포 중복이 0이었다.** 최신순은 서로 다른 시각에 발행된 기사가 나열되어 문구가 미세하게 달라 정확 매치가 안 걸린다.
`sort=sim`에서만 동일 제목 재배포가 관찰됐다 — 예: *"삼성전자 상반기 D램 점유율 39.4%…"* 가 조선비즈·연합뉴스·SBS 3사에 동일 제목으로.

**설계 귀결:**
- 중복 제거는 여전히 필요하지만 **1순위 필터가 아니다.** 1순위는 **이미 본 기사 해시 제외**다 — 5분마다 폴링하면 대부분이 직전 주기와 동일하다
- 제목 정규화 매치는 **작동한다**(실측 확인). 다만 구두점만 다른 케이스(`"55조 '역대 최대'"` vs `"55조…역대 최대"`)가 있어 **도메인 + 발행시각 근접도를 보조 신호로** 둔다
- 측정 기준이 "정규화 후 완전 일치"였다. **느슨한 유사도로 재면 더 나올 수 있다 — 미검증**

## 5-2. 조사관 — **인과를 단정하지 않는다** ★

선행사례 조사가 찾아낸 것(부록 A). 경쟁 분석이 아니라 **설계 문제**다.

Public.com · PortfolioPilot · TrendSpider · Danelfin 등 **최소 6곳이 "왜 움직였나"를 시도하다 완성형까지 안 갔다.** 태만이 아니라 의도적으로 멈춘 것일 가능성이 크다.

> **주가가 움직인 *뒤에* 뉴스에서 이유를 찾는 방식은 원래 신뢰도가 낮다.**
> 같은 헤드라인이 상승·하락 양쪽에 "원인"으로 붙고, 뉴스가 가격보다 늦게 나온다.

검증 없이 인과를 단정하면 **금융 저널리즘의 사후 정당화를 자동화·확대재생산할 뿐이다.**
LLM은 그럴듯하지만 틀린 인과 서사를 자신 있게 지어낸다. soul.md §8 **정직성 정면 위반**이다.

### 대응 1 — 인과 후보에 정량 게이트를 건다 (LLM 전에)

조사관이 뉴스를 읽기 **전에**, 결정론적으로 후보를 거른다. event study 최소 버전이다.

| 게이트 | 검사 | 탈락 시 |
|---|---|---|
| **선행성** | 뉴스 발행 시각이 가격 변동 **개시 시각보다 앞서는가** | 후행 뉴스는 "원인"이 아니라 "반응"으로 라벨 |
| **고유성** | 같은 시각 KOSPI·해당 업종(`0J`/`0U`)도 같이 움직였는가 | 시장/업종 동조면 **종목 고유 원인이 아니다** |
| **유의성** | 변동폭이 통상 변동(20일 표준편차 등) 대비 유의한가 | 평시 노이즈면 설명 대상이 아니다 |

**세 게이트는 전부 파수꾼이 이미 받는 데이터로 계산된다.** `0J 업종지수`·`0U 업종등락`이 고유성 판정에 그대로 쓰인다 — 19종 REAL에 이미 있다.

### 대응 2 — 표현 규범

조사관은 **"때문입니다"를 쓰지 않는다.**

| 금지 | 대체 |
|---|---|
| *"HBM 수주 때문에 급등했습니다"* | *"급등 12분 전 HBM 수주 공시가 있었습니다. 같은 시간 반도체 업종은 +0.3%로, 이 움직임은 종목 고유입니다."* |

**사건 · 시간 관계 · 고유성 · 신뢰도**를 제시하고 인과 판단은 사용자에게 남긴다.
이건 규제 회피가 아니다(범위 밖). **soul.md §8 정직성이다.**

### 대응 3 — 원장이 인과 적중도 기록한다

기존 원장의 피드백은 *"불렀나/말았나"* 만 다룬다. **인과가 맞았나는 안 다룬다.**
→ 조사관이 인과 후보를 낸 행에는 세 번째 피드백을 붙인다: `인과 맞음` / `인과 틀림` / `판단 불가`.

이게 없으면 조사관의 품질을 영영 측정할 수 없다. 그리고 측정 못 하는 환각은 고칠 수 없다.

## 6. 원장(Ledger) — "안 불렀다"를 기록하는 법

### 문제

부른 것만 적으면 *"왜 안 불렀냐"*에 답을 못 한다. 그런데 WS 틱마다 평가 결과를 다 적으면 하루 수십만 줄이다.

### 해법 — 조용했던 시간은 안 적는다. **근접 사건만** 적는다

| 판정 | 조건 |
|---|---|
| **발화** | 임계 초과 + 알림 나감 |
| **근접** | 임계의 일정 비율 도달했으나 미달 (임계 5%인데 3.8%) |
| **억제** | 임계 넘었으나 다른 규칙이 죽임 |

하루 수십~수백 줄. 사람이 훑을 수 있는 양이다.

### 컬럼

`시각 · 종목 · 트리거 · 관측값 · 임계값 · 판정 · 사유 · 피드백`

**`사유`가 핵심이다.** 억제면 왜 죽였는지 정확히:
*"쿨다운 2분 12초 남음"* · *"09:14 알림과 동일 원인"* · *"사용자 룰 R7: 장 초반 30분 억제"*
**이유 없는 침묵은 디버깅 불가다.**

**`피드백`은 행마다 두 버튼** — `불렀어야 했다` / `부르지 말았어야 했다`. 규칙 학습의 **유일한** 입력이다.

### "보수적으로 시작"의 함정 ★

보수적 = 임계 높게 = 덜 부른다. 맞다. **그런데 그러면 원장이 비어서 튜닝할 데이터가 없다.** 첫 주가 통째로 낭비된다.

> **관측은 넓게, 알림은 좁게.**
> 파수꾼은 **낮은 임계로 상시 평가** → 원장에 전부 기록.
> 알림은 **높은 임계**를 넘은 것만.
> 사용자는 원장에서 *기록됐지만 안 불린 것*을 보고 `불렀어야 했다`를 찍는다.

관측 임계와 알림 임계를 **분리**하는 순간, 보수적 시작과 첫날부터의 학습이 동시에 성립한다.

### 원장은 공통 테이블 캔버스의 인스턴스다 — 새 캔버스가 아니다

```
자유 캔버스     ← 형상 자체를 모름              (최후의 탈출구)
공통 테이블     ← 레코드인 건 알되 스키마 모름   ★ 기본값 · 원장이 여기 산다
전용 캔버스     ← 형상·스키마 다 앎 (랭킹/호가/타임라인/체결로그)
```

**`mcp-실행계획.md` §3 정정**: 거기서 "#3 랭킹 테이블 → 레코드 테이블로 일반화"라고 썼는데 방향이 반대다.
**공통 테이블이 부모고 랭킹 테이블이 자식이다.**

부수 효과가 크다 — **자유 캔버스 열림 빈도가 크게 준다.** soul.md §5-5가 *"자유 캔버스가 자주 열리면 캔버스 체계가 틀린 것"* 이라 경고했는데, 공통 테이블이 그 사이 층을 메운다.

단 **전부를 테이블로 밀지는 않는다.** 호가(양방향 막대) · 체결 로그(시간 흐름) · 랭킹(순위 변동 + 스파크라인)은 테이블처럼 생겼지만 형상이 다르다. **공통 테이블은 기본값이고, 형상을 알면 승격한다.**

## 7. 규칙 컴파일러 — 자연어로 입력, **조건식으로 저장**

자연어 그대로 저장하고 매번 LLM이 해석하면 파수꾼의 LLM-0 성질이 깨진다. 매 틱마다 LLM은 불가능하다.

**컴파일한다.** 규칙을 만들 때 **딱 한 번**만 LLM을 쓴다.

```
사용자: "장 초반 30분은 변동성 크니까 임계를 두 배로"
          ↓ LLM 컴파일 (1회)
Athena: 이렇게 이해했습니다
        if (09:00 ≤ t < 09:30) threshold *= 2
        적용 대상: 급등락 트리거 전체
        소급 시뮬레이션: 지난 30일 기준 발화 14건 → 6건
        [승인] [수정] [취소]
          ↓ 승인
        저장 → 파수꾼이 매 틱 결정론적으로 평가 (LLM 0)
```

**소급 시뮬레이션이 가능한 이유는 원장이 있기 때문이다.** 원장의 두 번째 용도다.
이게 없으면 사용자는 규칙이 무슨 일을 할지 모르는 채로 승인한다.

승인 카드의 형태는 녹취 2의 **"감시 계획 승인"** 과 동일하다 → **표면 하나로 둘 다 처리된다.**

## 9. CLI 구동 방식 — 해소됨 (결정 1)

적대적 검증이 찾아낸 것. **규제·비용과 무관한 순수 구조 문제다.**

`soul.md` §1의 *"자체 API 키를 쓰지 않는다"* 는 **LLM API 키**를 뜻한다(사용자 확인). 즉 구독 CLI로 돌린다.

**진짜 제약은 "API 키를 쓸 수 있냐"가 아니라 "`--bare`를 쓸 수 있냐"다.**

| 경로 | 성질 |
|---|---|
| `claude -p --bare` (스크립트용 공식 권장) | **OAuth 구독 로그인 불가. `ANTHROPIC_API_KEY` 필요** → 구독 노선에서는 봉인 |
| `claude -p` (구독 로그인) | 매 호출마다 로컬 컨텍스트 전체(훅·스킬·MCP·CLAUDE.md) 로드 + **트러스트 확인 없이 임의 훅 실행** |
| Python Agent SDK | Anthropic 권장. 단 API 키 전제 → 노선 밖 |

### 채택 — 구독 + Athena 전용 클린 프로파일

봉인의 부작용 중 위험한 것은 **"통제 밖의 훅이 하루 수십 번 실행된다"** 하나다. 이건 없앨 수 있다.

- Athena 전용 작업 디렉토리를 만들고 `CLAUDE.md`·훅·스킬을 **아예 두지 않는다**
- `--setting-sources`로 프로젝트 설정을 배제한다
- → 로드할 훅 자체가 존재하지 않는다

남는 건 컨텍스트 로드 오버헤드(지연)뿐이고, 비용은 범위 밖이므로 감수한다.
**soul.md §1 개정 불필요.**

이 완화는 [`mcp-실행계획.md`](mcp-실행계획.md) §W1-5의 헤드리스 신뢰 게이트 부재와 **뿌리가 같다** — 둘 다 "Athena가 직접 막는다"로 푼다.

### S3 스파이크 실측 결과 (2026-08-15) — **완화책 성립 확인**

산출물: `spike/cli-pipe/` · `spike/captures/S3-*.ndjson`. `claude` 2.1.220.

| 검증 | 결과 |
|---|---|
| 구독 로그인 헤드리스 인증 | **통과.** `apiKeySource: "none"` — CLI 자신이 OAuth 구독 인증임을 명시 |
| 클린 프로파일이 훅을 0으로 | **통과.** 훅 6→0, MCP 4→0, 플러그인 4→0, 스킬 388→14, 툴 129→27 |
| 호출당 지연 | 클린 ~2000ms, 대조군 2926ms. **시동 오버헤드 2.91s → 0.81~0.93s** |

> ### ★ 문법 함정 — 반드시 빈 문자열
> **`--setting-sources ""`** 로 줘야 한다. `--setting-sources "user"` 처럼 값을 하나라도 주면
> **대조군과 완전히 동일하게 훅·MCP·플러그인·스킬이 전부 로드되어 완화책이 무력화된다.**
> (이 환경은 모든 훅·MCP가 유저 스코프 `~/.claude/`에 등록돼 있다)

대조군에서 훅 6개가 **트러스트 확인 없이** 실행되어 컨텍스트에 텍스트를 주입하는 것을 실측 확인했다 — 막으려던 정확한 시나리오다. 클린 프로파일에서는 `hook_started` 이벤트가 0건이었다.

**부수 이득**: 시동 오버헤드 약 2초 절감. 이게 감시 루프의 반응속도 상한을 결정한다.

### MCP 보안 구멍은 **2층위**다 — 계획 정정

| 층 | 실측 결과 |
|---|---|
| **서버 프로세스 시작** | **무확인 실행.** `npx -y <패키지>` = 임의 코드 실행이 아무 확인 없이 벌어진다 ← 우려 확인 |
| **툴 호출** | **기본 권한 게이트로 막힘.** 헤드리스는 승인자가 없어 자동 거부(`non_execution_kind: "user-rejected"`) |

→ 감시 루프에 MCP를 붙이려면 **(a) 등록 서버 화이트리스트 + (b) `--allowedTools` 명시 목록**을 같이 써야 한다.
`--dangerously-skip-permissions`는 (a)가 깨지는 순간 바로 위험해진다.

### 후속 검증 필요

- **`--safe-mode`** — 훅·MCP·플러그인·CLAUDE.md를 전부 비활성화. `--help`에서 발견했으나 미실측.
  **클린 디렉토리를 따로 만들 필요 없는 더 단순한 대안**일 수 있다
- 지연 측정 n이 얇다(클린 n=2, 대조군 n=1). 경향은 뚜렷하나 통계적으로 얇음
- 프로젝트 간 `--resume`은 v2.1.223+ 요구, 설치본 2.1.220 → 판정 불가

### 부수 확인

`--max-budget-usd`는 v2.1.217+, 프로젝트 간 `--resume`은 v2.1.223+.
`--resume`으로 감시 루프를 계속 이어붙이면 컨텍스트가 누적된다. 다만 `/compact`·훅 기반 툴결과 필터링·서브에이전트 격리로 완화 가능하므로 **"무조건 stateless여야 한다"는 과장**이다(검증에서 반증됨).

## 10. 감시 주문의 구조적 리스크 ★

> *"손절 포인트는 이대로 잡고, 감시 주문 걸어놓으면 어떻습니까?"*

**키움 REST에 조건부/스탑 주문 TR이 존재하지 않는다.** 인벤토리 전수 확인 결과 주문 TR 12개는 전부 매수/매도/정정/취소뿐이다(`kt10000-3`, 신용 `kt10006-9`, 금현물 `kt50000-3`).

→ 사용자가 상상한 "걸어두면 알아서 체결"은 **거래소에 상주하는 진짜 스탑오더가 아니다.**
**Athena 프로세스가 WS(0B/0D)로 가격을 계속 지켜보다가 트리거 시점에 시장가를 직접 쏘는 구조**일 수밖에 없다.

**즉 Athena가 죽으면 손절이 발동하지 않는다.** 우회가 없다.

### 결정 2 — 자동 집행을 하지 않는다

자동 집행하면 *"걸어놨으니 안심"* 이라는 **기대치**가 생기는데, 실제로는 앱이 죽으면 아무 일도 안 일어난다.
경고 문구를 아무리 붙여도 **기대치와 실제의 간극 자체는 안 없어진다.** 그리고 그 간극이 벌어지는 순간은 정확히 돈을 잃는 순간이다.

**그래서 자동 집행을 뺀다.**

| | |
|---|---|
| Athena가 한다 | 조건 감시 → **"손절가 도달" 알림** |
| 사용자가 한다 | 주문 티켓(캔버스 #8)에서 직접 집행 |

앱이 죽으면 **알림을 못 받을 뿐, 잘못 체결되지 않는다.** 실패 모드가 "놓침"이지 "오집행"이 아니다.

여전히 고지할 것:
- 감시가 살아있는 동안 **앱 종료 경고**
- 노트북 뚜껑을 닫으면 `powerSaveBlocker`로도 절전을 못 막는다 → **뚜껑 경고**
- 장중 `powerSaveBlocker.start('prevent-app-suspension')` 활성화

### 이미 서 있는 안전장치 (그대로 유지)

규제 때문이 아니라 **중복 주문(= 돈)** 때문에 유지한다.

```python
config.py:27          enable_order_api = False           # 기본 비활성
dependencies.py:26-40 order API + local bearer + 전용 클라이언트 3중 요구
runtime.py:146-147    confirmation != 'true' → HTTP 428
runtime.py:154-212    Idempotency-Key → OrderState(PENDING/IN_DOUBT/COMPLETED), IN_DOUBT면 409
README.md:44-48       주문 클라이언트는 자동 재시도 비활성
```

## 11. 아침 브리핑 = 외부 MCP **필수 의존성**

## 12. 실행 웨이브 — MCP 계획과의 접합

```
W0 스파이크 ── S1 Electron   S2 MCP클라이언트   S3 CLI파이프(§9 딜레마 실측)
                                                        │
        ┌───────────────────────────────────────────────┤
        ▼                                               ▼
   W1 MCP 게이트웨이                              W2 Electron 셸
        │                                               │
        ├─────────────► W3 캔버스 계약 ◄────────────────┘
        │                    │
        │                    └── 공통 테이블 캔버스 ★ (원장·규칙·계획이 전부 여기 산다)
        ▼
   W2.5 파수꾼 엔진 ◄── 이 문서. W1과 병렬 가능 (MCP 무관, 키움 WS만 씀)
        │
        ├── 시세 파수꾼 (트리거 6종) — 백엔드 asyncio 주기 태스크
        ├── 원장 (근접/억제 포함 적재)
        └── 관측/알림 임계 분리
        │
        ▼
   W5 조사관 + 규칙 컴파일러  ◄── W1(MCP) + W3(캔버스) 둘 다 필요
        │
        ├── 상관: 시세 이벤트 × 뉴스 이벤트
        ├── 알림 → Electron 토스트 → 컨텍스트 복원
        └── 규칙 컴파일 + 소급 시뮬레이션
```

**W2.5는 W1과 병렬로 갈 수 있다.** 시세 파수꾼은 MCP를 안 쓰고 키움 WS만 쓴다.
그리고 원장이 먼저 쌓여야 W5의 소급 시뮬레이션이 성립하므로, **W2.5를 일찍 시작할수록 유리하다.**

### 배치 위치 — 백엔드

스케줄러는 Electron 메인 프로세스가 아니라 **Python 백엔드**에 둔다.
이미 WS 클라이언트·레이트리미터·스트림 라우트가 거기 있고(`ws_client.py`, `rate_limiter.py`, `api/stream.py`), **UI 크래시와 감시 로직을 분리**할 수 있다.
현재 코드베이스에 스케줄러 라이브러리는 없다(grep 0건) — asyncio 주기 태스크 또는 APScheduler 신규 도입.

### 놓친 주기 보정

**최근 미실행분 1회만 캐치업하고 나머지는 폐기한다.** 5분 감시가 6시간 밀렸다고 72번 몰아 실행하면 안 된다.

### 최대 위협 — OpenBB Workspace

*"An analyst describes what they need, the agent writes it… a functioning widget, a dashboard, or even a full app with multiple tabs… The artifact lives in the Workspace, governed by the same access controls."*

**B축을 실제로 구현했고 적대적 검증을 통과한 유일한 covered 판정이다.** MCP 네이티브 조직이라 D축을 클라이언트 방향으로 뒤집는 데 필요한 건 UX 결정뿐이다.

**단 KRX 커버리지 근거 전무**, 클라우드 SaaS, 무료 티어는 자체 API 키 사용 → E축과 정반대. 지금은 직접 경쟁이 아니고 **"가장 빨리 흉내 낼 수 있는 조직"** 이라는 의미의 위협이다.

### D축의 방향 반전 — 중요

OpenBB · Public.com · Unusual Whales 전부 **자신을 MCP 서버로 노출**한다(아웃바운드). 외부 AI가 그들 데이터를 소비하는 구조다.
**Athena는 반대다** — 사용자가 임의의 MCP 서버를 Athena에 등록한다(인바운드). 이 방향을 1급 UI 기능으로 가진 제품은 확인되지 않았다.

### 포지셔닝 — 정확한 문구

개별 축으로는 *"본 적이 없다"* 가 **틀렸다**. B는 OpenBB가, A는 Anthropic 데모가, C는 4~6곳이, D는 생태계가 이미 했다.

> **"이 조합을 한국 리테일 시장에 내놓은 곳은 아직 없다. 단 개별 요소는 이미 여러 곳에서 부분적으로 검증된 방향이다."**

전자는 검증으로 반박 가능하고, 후자는 방어 가능하다. **대외 발표에서 "unprecedented"를 주장하면 반박 리스크가 크다.**

### 방어 가능 vs 카피 가능

| | |
|---|---|
| **방어 가능** | F축(알람 원장 — 42건 전부 none) · **KRX 한국 리테일 특화**(42건 중 KRX 다루는 곳 0) |
| **카피 가능 (모트 아님)** | A축(UI 단순화는 제품 결정이지 기술 장벽이 아니다) · D축(MCP는 공개 프로토콜, 방향만 뒤집으면 됨) · E축(사업모델 선택) |
| **노출됨** | B축(OpenBB가 이미 함 — "발명했다"고 하면 거짓) |

### 조사의 한계 — 결론의 신뢰도

**WebSearch가 두 차례 모두 0회다.** 세션 공유 예산(10회)이 1차 조사 첫 에이전트에서 소진됐고, 2차에서는 시작 전부터 없었다. 전량 WebFetch로 조사했다.

미확인으로 남은 것 — **"없다"가 아니라 "막혔다"**:
- **씽크풀 AI매매신호** (C축 국내 최유력 후보) — 404 + jina 프록시 503
- **Fintel** — 직접 403 + 프록시 차단, 전 축 unknown
- **autopilot.trade** — ECONNREFUSED + 프록시 422
- Magnifi · Seeking Alpha 세부 · 인텔리퀀트(DNS 부재) · 크래프트테크(도메인 리셀)

도메인 함정도 있었다 — `alphasense.com`은 가스센서 제조사(정답은 `alpha-sense.com`), `fintool.com`은 microsoft.com으로 리다이렉트.

**§5-2의 "사후 인과는 신뢰도가 낮다"는 주장 자체도 라이브 소스 검증 없이 배경지식 기반이다.** 방향은 타당하나 대외 자료에 인용 근거 없이 쓰면 안 된다.
