# Athena 디자인 소울 — 사용자 발언 원장

> **이 문서가 디자인 결정의 원장(ledger)이다.**
> 앞으로 사용자가 디자인에 대해 말하는 모든 것은 여기에 기록된다. 발언 → 그 발언이 뜻하는 원리 → 적용된 곳 순으로.
> `soul.md`는 제품 철학(녹취 기반), 이 문서는 **취향과 재료에 대한 판단**이다. 충돌하면 나중 발언이 이긴다.

---

## 파악된 디자인 소울 — 한 문장

> **"유리는 진짜 유리여야 하고, 창은 살아 움직여야 하고, 화면은 조용해야 한다."**

세 개의 축이 반복해서 나타난다. 아래 모든 발언이 이 셋 중 하나로 수렴한다.

| 축 | 뜻 |
|---|---|
| **재료의 진정성** | 유리를 흉내내지 말고 유리로 만들라. 물리를 지켜라 |
| **창의 생명** | 창은 정적인 틀이 아니라 자라고 줄고 차오르는 것 |
| **정적(靜寂)** | 화면에서 소리를 내는 것은 하나여야 한다 |

---

## 축 1 · 재료의 진정성

### 발언 → 원리

**"우리는 리퀴드 글라스가 핵심이야"**
→ 리퀴드 글래스는 스타일이 아니라 **제품의 정체**다. 다른 모든 결정이 여기에 종속된다.
→ 적용: 라운드 1의 A~D 4안 전량 폐기. 유리를 안 쓰거나 잘못 쓴 안이었다.

**"캔버스도 모두 리퀴드 글라스여야해"**
→ Apple의 "콘텐츠 레이어에 유리 금지" 규범보다 **무드보드의 visionOS 이미지가 우선**한다. 모든 표면이 유리인 세계.
→ 적용: 창·캔버스 전부 유리로 전환. 대가(성능·위계)는 [soul.md](soul.md) §7에 명시.

**"화면이 밝은색이면, 글래스라는게 말그대로 유리니까, 유리의 특성을 살리면서 잘 보이는 그런게 있으면 좋겠어"**
→ **이 발언이 이 프로젝트에서 가장 중요한 교정이었다.**
→ 내가 낸 "유리를 불투명하게 해서 배경을 지운다"는 답은 가독성을 얻고 재료를 잃는 답이었다. 사용자는 **둘 다** 요구했다.
→ 원리: **어둡게 만들지 말고 두껍게 만들라.** 두꺼운 유리는 실제로 더 어둡다(흡수), 더 흩뜨린다(산란), 더 반사한다(specular). 전부 물리다.
→ 적용: `유리 · 밝은 배경 해법` 아트보드 C안. 흡수·산란·반사·각인 4요소.

**"밝은배경에 대한 부분이 좀 아쉬워. 검은색이 아니라 조금 더 다르게 해야할 거 같아. 마치 애플 비전 프로에서 하는 것과 동일하게"**
→ **두 번째 교정.** 나는 "두껍게"까지는 갔지만 여전히 **검정**으로 눌렀다. 그건 그늘이지 유리가 아니다.
→ 원리: **색조는 환경에서 가져오고 명도는 고정한다.** 따뜻한 배경 위에서는 따뜻한 토프 프로스트가, 차가운 배경 위에서는 차가운 슬레이트 프로스트가 된다. 배경이 밝을수록 알파를 올려 **같은 명도(L\* 30~36)에 착지**시킨다.
→ 그리고 어둡되 **빛을 받은 것처럼** — 거의 흰 상단 엣지, 내부 warm glow, 45° specular.
→ 실측: 양 극단이 모두 실패한다. 검정이면 재료를 잃고, 밝으면 등락 적/청이 죽는다.
→ 무드보드 3·7번 핀(visionOS)에서 유리가 방의 온기를 띠고 있던 게 처음부터 답이었다. **무드보드를 세 번째로 놓쳤다가 되찾은 셈.**

**"아이폰에서는 이렇게 문제를 푸는거 같아"** (iOS 26 홈 화면)
→ 레퍼런스로 C안을 검증. 독이 배경화면보다 어둡고(흡수), 라벨에 그림자가 있고(각인), **배지 채도는 안 죽는다**(정보색 보존).
→ 적용: 밝은 배경 유리 위 등락 적/청 실측 → 별도 색 불필요 확인.

**"배경색에 따라서 글자도 조금 다르게 해야할거 같기도 하고"**
→ 유리는 뒤에 있는 것에 반응해야 한다. 고정값이 아니다.
→ 적용: **유리 두께 = f(뒤의 정보 밀도, 뒤의 밝기).** 배경 밝기 감지 채택(결정됨).

### 도출된 규칙

1. 유리 두께는 고정값이 아니다 — 뒤의 밀도·밝기에 비례
2. 텍스트를 배경에 맞추지 않는다. **유리가 배경을 지운다**
3. 밝은 배경 대응 4요소: **흡수 · 산란 · 반사 · 각인**
4. 유리는 무채색. 색은 뒤에서 올라온다
5. 뒤에 굴절할 것이 없으면 그건 유리가 아니라 반투명 회색 사각형이다

## 축 2 · 창의 생명

### 발언 → 원리

**"커멘드 창하고 캔버스창하고 따로있다고 생각하면 돼"**
→ 한 창의 두 영역이 아니라 **OS 레벨에서 독립된 창 둘**. 각자 움직이고 각자 신축한다.
→ 적용: E1/E2/E3 전면 재설계.

**"E2가 맞긴한데 채팅창은 E1이 취지에 더 맞아보여"**
→ 배치(겹치지 않음)와 비례(가로로 낮음)를 분리해서 본다. 세로 기둥은 채팅 사이드바가 되어 "이력 최소화"를 배신한다.
→ 원리: **비례가 규율을 강제한다.** 204px 가로 띠에는 3턴 이상 못 쌓는다. 규칙이 아니라 형태가 절제를 만든다.
→ 적용: E3 상하 나란히.

**"창 리사이즈로 풀어줘"**
→ 이력을 훑는 문제를 새 창이 아니라 크기 변화로 푼다. 창은 끝까지 둘.
→ **부수 발견: E1은 틀린 안이 아니라 E3의 확장 상태였다.** 배치를 고르는 문제가 아니라 상태 전이를 설계하는 문제였다.

**"대화창을 줄이는게 맞아"** (확장 중 캔버스 조작 경로)
→ 제약을 감수한다. 우회로를 만들지 않는다.

**"부팅할 때, 뭔가 채팅창이 차오르는 느낌? 채팅창이 만들어지다가 딴 하고 시작되는거지"**
→ 부팅은 별도 스플래시가 아니라 **대화 창의 탄생**이다. 로고+게이지 카드를 폐기.

**"아래에서 위는 아니고 가로에서 세로로 쭉 차면서 딴!"**
→ 모션의 축까지 지정. 수평 → 수직 → 완성.

**"온보딩에서는 채팅창이 나오다가 온보딩창이 뜨고, 그 다음에 다시 채팅창으로 줄어드는 느낌"**
→ **온보딩은 세 번째 창이 아니다. 대화 창이 커진 것이다.**
→ 이게 "창은 둘"을 깨지 않고 온보딩을 넣는 유일한 방법이다. 리사이즈 문법의 재사용.

**"답변이 2줄 넘으면 두 줄 넘은채로 모두 보이게 해"**
→ 자르지 않는다. 접지 않는다. 창이 필요한 만큼 자란다.
→ 원리: **사용자가 방금 물어본 것에 대한 답을 감추지 않는다.**

### 도출된 규칙

1. 창은 둘. 새 창을 만들지 않는다 — 있는 창이 커지고 줄어든다
2. 창은 **위로만** 자란다. 입력줄은 자리를 지킨다
3. 부팅·온보딩·답변 확장이 **모두 같은 리사이즈 문법**을 쓴다
4. 비례로 규율한다 — 크기 제한이 곧 절제

## 축 3 · 정적(靜寂)

### 발언 → 원리

**"색깔같은 경우에는 AITS에 팔레트만 가져와서, 글래스는 유지하고 키움의 색을 지키는거지"**
→ 색을 새로 만들지 않는다. 계승한다. AITS는 구조를 버렸지 색을 버린 게 아니다.
→ 마젠타 `#ee137b`가 인터랙션 색으로 복귀. 다만 **유리는 여전히 무채색**이고 마젠타는 점 하나로만 존재.

**"AITS에서 키움증권 로고를 불러와. 이 로고의 모양을 가지고 프로그램 디자인에 특색을 세련되게"**
→ 로고를 화면에 붙이는 게 아니라 **기하를 추출해 재료에 넣는다.**
→ 도출: **45°는 이 제품의 각도다.** 유리의 specular가 로고 화살표와 같은 각도로 흐른다. 브랜드가 장식이 아니라 물성이 된다.
→ 도출: **무채색이 마젠타로 바뀌는 것이 "활성"** — 로고에서 K의 획이 화살표로 바뀌는 문법 그대로.

**"CLI 선택할 때 맨 처음에는 선택지 4개, 그 다음 연결, 그 다음 활성"**
→ 상태를 단계로 분리. 설치 감지 같은 기술적 사실을 사용자에게 보여주지 않는다.

**"활성으로가 아니라 활성 비활성으로 나눠줘"**
→ 애매한 동사("활성으로")를 명확한 상태 대립("활성/비활성")으로. **상태는 상태로 말한다.**

**"TR별로 한국어로 매핑되는 걸 프론트엔드단에 만들어서, ka~~ 이런식으로 화면에 뜨지 않게 해줘"**
→ **내부 식별자를 사용자에게 보여주지 않는다.** `ka10008`은 개발자의 언어이지 사용자의 언어가 아니다.
→ 원리: 정직성(근거를 감추지 않는다)과 내부 식별자 노출은 다른 문제다. **근거는 보여주되 그 근거를 사용자의 말로 번역한다.**
→ 적용: `ka10008` → `외국인 순매수 추이`, `ka10001` → `종목 기본정보`, `ka10004` → `호가`.
   프론트엔드에 매핑 테이블을 두는 것을 구현 요구사항으로 문서화(11페이지).
→ **이전에 내가 "TR 코드를 그대로 노출한다"를 정직성의 근거로 삼았던 것을 정정한다.** 정직한 것은 코드가 아니라 항목명이다.

**"호가도가 뭔지 모르겠어"**
→ 목업의 예시 문구도 실제 사용자가 칠 법한 완결된 문장이어야 한다. 잘린 말투는 설계서에서 읽히지 않는다.
→ 적용: `호가도` → `삼성전자 호가창도 띄워줘`

**"캔버스를 더 불투명하게"**
→ 유리 세계에서도 **데이터 가독성이 미감보다 위**다.

### 도출된 규칙

1. **한 화면에 마젠타는 한 곳.** 그 하나가 "지금 여기"
2. 유채색은 등락 적/청뿐 — 그건 액센트가 아니라 데이터 인코딩
3. 오류는 주황 `#ff9838` — 빨강은 이미 "상승"이다
4. 로고를 복제하지 말고 기하를 계승하라
5. 상태는 대립쌍으로 표기한다

## 이 소울이 거부하는 것

사용자 발언에서 반복적으로 **거부된** 것들:

- **유리를 포기하는 실용주의** — "그냥 불투명하게 하면 읽히잖아"는 두 번 거부됨
- **창을 늘리는 해결** — 이력 보기, 온보딩, 설정 전부 기존 창으로 흡수
- **정보를 감추는 것** — 답변 자르기, TR 코드 숨기기 거부
- **새로 만드는 것** — 색도 폰트도 로고도 전부 **계승**. 무에서 만들지 않는다
- **애매한 표현** — "활성으로" 같은 동사형을 상태형으로 교정
