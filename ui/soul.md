# Athena — soul.md

> 이 문서는 제품 철학 녹취([`plan/Athena 프로젝트.txt`](../plan/Athena%20프로젝트.txt))에서 추출한 디자인 영혼이다.
> 모든 시안, 모든 라운드, 모든 판정은 이 문서를 기준으로 한다.
> 시각적 결정이 이 문서와 충돌하면 문서가 이긴다.

---

## 1. 이 제품이 무엇인가

Athena는 **키움증권 REST API를 자연어로 조종하는 데스크톱 트레이딩 워크스테이션**이다.

사용자는 화면 이름을 외우지 않는다. TR 코드를 모른다. 메뉴를 찾지 않는다.
말을 하면, 화면이 만들어진다.

기술적으로는: 커맨드바에 자연어 입력 → AI가 호출할 키움 TR을 판단 → 데이터를 받아 →
그 데이터 형상에 맞는 **카드**(재사용 가능한 시각화 템플릿)를 선택 → 캔버스 창에 렌더.
AI는 로컬에 설치된 CLI(Claude Code / Codex / Gemini CLI)를 제어해서 동작한다. 자체 API 키를 쓰지 않는다.

---

## 2. 우리가 등지고 온 것

전작이 둘 있었고, 둘 다 무엇을 하지 말아야 하는지를 가르쳐줬다.

- **AITS** — 기능이 번잡했다. MCP를 계속 붙이다 보니 코드가 난잡해졌다. → *기능을 더하는 것으로 문제를 풀지 않는다.*
- **BTS** — 스크래치 기반 블록 조립. UI가 보기 그랬다. → *조립의 자유도가 곧 좋은 UX는 아니다.*

그리고 키움 HTS 그 자체. **화면이 288개다.**
사용법 설명이 "그 화면을 어떻게 띄우는가"부터 시작하는 순간, 그 제품은 이미 진 것이다.

> **288개의 화면을 카드 12종으로 접는다. 이것이 Athena의 존재 이유다.**

## 3. 첫 번째 철학 — 창은 두 개뿐이다

앱을 켜면 게이지가 차오르고, **창 하나**가 뜬다. 커맨드바다.

Athena의 전체 UI는 정확히 **두 개의 독립된 창**으로 이루어진다.
한 창 안의 두 영역이 아니다. **OS 레벨에서 분리된 별개의 창이다.** 각자 따로 움직이고, 따로 신축하고, 따로 닫힌다.

### 창 — 둘

| | | |
|---|---|---|
| **대화 창** (= 커맨드바) | 유일한 입력 지점 | 자연어 입력 + 최소 면적의 이력. 리퀴드 글래스. |
| **캔버스 창** | 유일한 출력 지점 | **카드**가 뜨고, 조합되고, 접히고, 펼쳐진다. 리퀴드 글래스 — 단 **데이터 위라서 가장 두꺼운 단계**(§7). |

> **"캔버스 창은 불투명"은 폐기된 서술이다** (2026-08-14, `liquid-glass.md:99`).
> §7 재료 규범이 "모든 표면이 유리다"로 확정했다. 실측상 두 창 모두
> `backgroundMaterial: 'acrylic'`이다(`app/main.js` `commonWinOpts`).
> 캔버스가 불투명해 보였다면 그건 재료가 달라서가 아니라 **유리가 두꺼워서**다.

두 창은 겹칠 수도 있고 나란히 놓일 수도 있다. 그 선택이 재료를 바꾼다 —
겹치면 유리가 **캔버스**를 굴절시키고, 나란하면 유리가 **데스크톱**을 굴절시킨다.

### 대화 창의 모드 — 새 창을 만들지 않는다 (2026-08-16 확정)

대화 창은 하나지만 **여러 모드**를 갖는다. 어느 모드도 새 창을 만들지 않는다.

| 모드 | 무엇을 하나 | 진입 |
|---|---|---|
| **대화** | 기본. 입력 + 최소 면적의 이력 | — |
| **온보딩** | CLI 연결 · 계좌 연결 | 최초 실행 시 1회 |
| **인증** | 토큰 상태 · 계좌 전환 | 계좌 등록 직후, 이후 재진입 |
| **설정** | 이력 보관 · 관측 주기 · 접근성 3종 · 활성 CLI·계정 전환 | **점(`#dot`)을 누른다.** 또는 커맨드바 |
| **주문 확인** | **주식 주문의 최종 집행 지점.** 감시는 알림까지만 하고 주문은 사람이 낸다(§6) | 주문 플로우 |

> 설정을 만지는 동안 사용자는 채팅을 치지 않는다. 주문을 확인하는 동안에도 마찬가지다.
> **두 기능이 시간을 다투지 않으면 면적을 나누지 않는다.**

**창은 둘이다. 예외 없다.**
부팅도, 온보딩도, 인증도, 설정도, 주문도 전부 대화 창이 변한 것이다.
새 창을 열고 싶어지는 순간이 오면 **모드로 풀 수 있는지 먼저 본다.**

**이력을 열람하는 것은 설정 모드가 아니라 대화 모드의 일이다.** 값을 정하는 곳과 내용을 보는 곳을 섞지 않는다.

설정도, 모델 지정도, 주기 설정도, 계좌 연결도 — **전부 커맨드바로 부를 수 있어야 한다.**
설정 아이콘을 찾아 헤매는 경험은 Athena에 없다. "모델 바꿔줘"라고 치면 같은 모드가 뜬다.
점은 *추가* 진입로다. **커맨드바로 못 가고 점으로만 갈 수 있으면 그건 탈락이다.**

> **현재 구현 (2026-08-16 실측, 브랜치 4종 병합 후):** 창은 둘이다 — `app/main.js`의
> `BrowserWindow` 생성은 워밍업(10×10 임시, 즉시 close)·캔버스·대화 셋뿐이고
> `dialog.*` / `showMessageBox` 호출은 0건이다.
>
> | 모드 | 상태 | 코드 |
> |---|---|---|
> | 대화 | 구현됨 | `app/chat.js` |
> | 온보딩 (CLI·계좌) | 구현됨 | `app/chat.js` `startOnboarding`, `app/lib/onboarding.js` |
> | 인증 (토큰 상태·계좌 전환) | 구현됨 | `app/chat.js` `showAuthConfirm`, `app/lib/auth-screen.js` |
> | 설정 (계좌·MCP 카드) | 구현됨 | `app/chat.js` `openSettings`, `app/lib/settings-cards.js` |
> | 주문 확인 | **미착수** | — |
>
> **모든 모드가 대화 창 안에 산다.** 각 모드는 `chat.html`의 형제 패널(`#onboard`,
> `#settings`)이고, 열리면 `#app`이 물러난다. 셋 다 같은 리사이즈 문법을 쓴다 —
> `chatMaxH`로 자라고 끝나면 `chatBaseH`로 돌아온다.
>
> `#dot`은 세 역할을 겸한다 — 상태 표시 · 캔버스 확장 중심점 · 설정 진입
> (`app/chat.html`의 `#dot` 버튼, `app/chat.js`의 `openSettings`). 커맨드바 진입로도
> 함께 있다(`SETTINGS_COMMAND`). Esc로 대화로 돌아온다.
> 용어 정의는 [`GLOSSARY.md`](../GLOSSARY.md) §1.
>
> 검증: `npm run verify` 검증 7·8이 "창이 늘지 않는가 / 모드가 뜨고 닫히는가"를,
> `npm run verify:settings-cards`가 카드 내부 상태들을 캡처로 남긴다.

대화 이력은 볼 수 있다. 하지만 **이력이 차지하는 면적은 최소여야 한다.**
Athena는 채팅 앱이 아니다. 채팅은 조종 수단이지 콘텐츠가 아니다.

## 4. 두 번째 철학 — 테슬라, 조종석이 아니라

> 비행기 조종석에는 버튼이 수백 개다. 정말로 그 기능들이 다 필요하기 때문이다.
> 테슬라에는 화면 하나뿐이다. 몰라도 되게 만들었기 때문이다.
>
> **Athena는 테슬라다.**

금융 앱의 관성은 조종석 쪽이다. 밀도가 곧 전문성이라는 착각. HTS 288화면이 그 결과다.
우리는 반대로 간다. 기본값은 극단적 미니멀. 색을 다 뺀다.

- **색은 정보다.** 장식이 아니다. 화면에 채도 높은 색이 있다면, 그것은 "지금 이걸 봐야 한다"는 뜻이다.
- 등락(빨강/파랑)과 단 하나의 주 액션(Accent)만 색을 가진다. 나머지는 전부 무채색 위 유리다.
- 화면에 동시에 존재하는 유채색 요소가 셋을 넘으면, 그 화면은 실패한 화면이다.

밀도가 필요한 순간은 온다. 그때는 **사용자가 명시적으로 켠다.** 기본값이 밀도인 일은 없다.

## 5. 세 번째 철학 — 카드는 언어다

> **용어 (2026-08-17 확정).** **캔버스는 창이다.** 그 창 안에 뜨는 표현 단위가 **카드**다.
> 이 절은 예전에 내용물도 "캔버스"라 불렀다 — 창과 내용물이 같은 이름을 쓰던 혼동을 걷어냈다.
> 정의는 [`GLOSSARY.md`](../GLOSSARY.md) §2.

카드는 "화면"이 아니라 **데이터 형상에 대응하는 문법**이다.

키움 TR을 화면 단위가 아니라 **데이터 형상 단위**로 접는다.
시계열, 랭킹 테이블, 호가 사다리, 스냅샷 스칼라, 분포, 이벤트 로그 —
288개 화면이 실제로 말하고 있는 것은 열몇 개의 문장 구조뿐이다.

### 카드는 Power BI / Tableau의 자리에 있다

**들어오는 데이터가 달라진다고 Tableau의 UI가 달라지지 않는다.**
막대그래프는 매출을 받든 기온을 받든 막대그래프다. 데이터가 컴포넌트에 들어가는 것이지,
데이터마다 컴포넌트를 새로 만드는 것이 아니다.

**카드도 정확히 그렇다.** TR이 288개든 301개든, 응답 스키마가 무엇이든,
카드는 **12종으로 고정**이고 데이터가 그 안에 들어갈 뿐이다.

> **따라서 "TR이 늘었으니 카드를 하나 더 만든다"는 언제나 틀린 판단이다.**
> 새 카드가 필요해 보이면 먼저 12종 중 어디에 접히는지 본다.
> 카드 종류가 TR 수를 따라 늘어나기 시작하면 그건 HTS 288화면으로 되돌아가는 길이다 (§2).

카드의 규칙:

1. **고정된다.** 12종. 데이터가 바뀌어도 카드 UI는 바뀌지 않는다.
2. **조합된다.** 카드 3개가 한 창에 동시에 살 수 있다. 서로를 밀어내지 않는다.
3. **신축한다.** 캔버스 창은 자유자재로 줄었다 늘었다 한다. 카드는 그 안에서 재배치된다.
4. **설명을 데리고 다닌다.** 카드 아래에는 AI의 해설이 붙는다. 숫자만 던지지 않는다.
5. **저장된다.** "이 창을 저장하시겠습니까?" → 사용자만의 창이 된다. 커스터마이징은 이 지점에서만 일어난다.
6. **모자라면 자유 카드.** 기성 12종으로 표현 못 하는 데이터가 오면 AI가 그 자리에서 그린다.
   자유 카드는 실패가 아니라 **설계된 탈출구**다. 하지만 자유 카드가 자주 열린다면 카드 체계가 틀린 것이다.

## 6. 네 번째 철학 — 조용한 감시자

Athena는 사용자가 안 볼 때도 일한다.

보유 종목 리스트를 주기적으로 훑고, 뉴스와 차트를 뒤지고, 이상 징후를 찾는다.
주기는 사용자가 정한다(5분 / 30분 / 1시간). 토큰을 쓰는 일이므로 사용자가 통제권을 갖는다.

**중요한 것만 알린다.** 중요하지 않으면 침묵한다.
알림은 방해가 아니라 신호여야 한다. 알림이 흔해지는 순간 알림은 죽는다.

침묵한 관측들도 버려지지 않는다. 전부 리스트로 쌓여, 사용자가 원할 때 돌아볼 수 있다.

> 인터페이스의 정적(靜寂)은 게으름이 아니라 **판단의 결과**다.

## 7. 미감 — 리퀴드 글래스

무드보드(`ui/moodboard/`)에서 뽑은 방향. Apple Liquid Glass(iOS 26 / visionOS) 계열.

### 재료 규범 (타협 불가)

리퀴드 글래스는 Athena의 핵심이다. 그리고 Apple이 정한 규범이 있다 — 이건 취향이 아니다.
전문은 [`ui/liquid-glass.md`](liquid-glass.md). 요약:

| | |
|---|---|
| **모든 표면이 유리다** | 두 창도, 창 안의 **카드**도 전부 |
| **유리는 무채색이다** | 색은 뒤에서 올라온다. 유리를 틴트하지 않는다 |
| **유리 뒤에는 반드시 굴절할 것이 있다** | 데스크톱이든 아래 캔버스든. 없으면 그건 반투명 회색 사각형이다 |
| **깊이는 값(value)으로 만든다** | 유리를 겹칠 때 테두리를 굵게 하지 말고 광량과 그림자를 다르게 준다 |
| **유리 두께는 고정값이 아니다** | **뒤에 있는 것의 정보 밀도와 밝기에 비례해 두꺼워진다.** 어두운 데스크톱 위 ~0.82, 데이터 캔버스 위 ~0.97, **밝은 배경화면 위 ~0.94 이상** |
| **텍스트를 배경에 맞추지 않는다. 유리가 배경을 지운다** | Athena는 다크 전용이라 라이트↔다크 플립을 쓸 수 없다. 대비는 유리 두께로 확보한다 |
| **Regular 변형 하나만 쓴다** | Clear와 섞지 않는다 |
| **액센트 색은 없다** | 강조는 굴절 강도와 광량으로 한다 |
| **접근성 3종은 직접 구현한다** | `prefers-reduced-transparency` / `prefers-contrast` / `prefers-reduced-motion` |

### Apple 규범에서 의도적으로 이탈하는 지점

Apple은 "콘텐츠 레이어에 유리를 두지 마라", "유리 위에 유리를 쌓지 마라"라고 명시한다.
**Athena는 이 두 규칙을 따르지 않는다.** 근거:

- 무드보드의 지배 이미지(핀 5 Vision Pro 스마트홈, 핀 7 visionOS 음악)는 **모든 패널이 유리이고 그것들이 한 화면에 동거한다.** visionOS는 실제로 그렇게 만들어져 있다
- Apple의 해당 규범은 iOS 앱 기준이다. Athena는 데스크톱 앱이고 자기 언어를 가진다

**대신 지불해야 할 비용을 명시한다:**

1. **성능** — 리퀴드 글래스는 GPU 집약적이며 자주 갱신되는 뷰에서 특히 그렇다. 실시간 체결·호가가 흐르는 캔버스에 유리를 얹으면 매 프레임 굴절을 재계산한다.
   → 완화책: 캔버스 유리는 **정적 프로스트**로 굽고, 실시간 데이터는 그 위에 별도 레이어로 그린다. 굴절 재계산을 데이터 갱신과 분리한다. 창 비활성 시 굴절 정지
2. **위계** — 전부 유리면 아무것도 튀지 않는다는 Apple의 경고는 유효하다.
   → 완화책: 유리의 **광량 단계를 3개로 고정**한다. 데스크톱 → 창 → 캔버스. 같은 단계끼리는 값이 같아야 한다
3. **가독성** — 유리 뒤 콘텐츠가 선명하게 비치면 서리유리가 아니다. 숫자가 겹쳐 읽히면 실패다

**추구하는 것**

- 깊은 어둠 위에 떠 있는 반투명 유리 표면. 배경이 유리를 통해 굴절되어 비친다.
- 빛은 데이터에서 나온다. 차트 라인이 발광하고, 그 빛이 유리 가장자리를 물들인다.
- 레이어는 z축으로 실재한다. 그림자와 굴절로 깊이를 만든다. 납작한 카드 나열이 아니다.
- 타이포는 극도로 절제. 넓은 자간의 소문자/대문자 대비. 숫자는 tabular figures, 흔들리지 않는다.
- 여백이 주인공이다. 요소 사이의 거리가 위계를 말한다.
- 모션은 물성을 따른다. 유리는 미끄러지고, 게이지는 차오르고, 창은 신축한다. 튀지 않는다.

**금지 — "AI 냄새" 목록**

원샷 프롬프트로 뽑은 화면들이 공유하는 특징. 하나라도 보이면 그 시안은 감점이다.

- 보라→분홍 대각선 그라디언트를 아무 데나 깔기
- 카드 3개를 균등 그리드로 늘어놓고 각각 아이콘 + 굵은 숫자 + 회색 캡션
- 이모지를 아이콘 대신 쓰기
- 근거 없는 둥근 모서리 남발, 모든 요소에 동일한 border-radius
- 의미 없는 글로우/네온 테두리 — 빛은 데이터가 있는 곳에만
- **유리를 장식으로 쓰기** — 반투명 회색 사각형을 여기저기 깔고 리퀴드 글래스라 부르기. 뒤에 굴절될 것이 없으면 그건 유리가 아니다
- **페이드로 등장하는 유리** — 리퀴드 글래스는 opacity가 아니라 굴절 정도의 변조로 나타나고 사라진다
- 대칭 강박. 모든 것이 가운데 정렬된 랜딩페이지 문법
- 실제로 존재하지 않는 기능을 암시하는 장식 UI

## 8. 판정 기준 (랭킹 루브릭)

각 시안은 아래 7개 축으로 채점한다. 각 5점.

| 축 | 질문 |
|---|---|
| **철학 부합** | 커맨드바 + 인터랙티브 창, 그 둘만으로 성립하는가? |
| **미니멀 강도** | 지울 수 있는데 남아 있는 요소가 있는가? 유채색이 셋 이하인가? |
| **카드 확장성** | 이 레이아웃에 다른 형상의 카드를 꽂아도 무너지지 않는가? |
| **정보 정직성** | 금융 데이터를 왜곡 없이, 오독 없이 보여주는가? 숫자가 읽히는가? |
| **물성** | 유리가 진짜 유리 같은가? 깊이가 가짜가 아닌가? |
| **AI 냄새 없음** | §7 금지 목록에 걸리는 것이 없는가? |
| **첫인상** | 켰을 때 "이거다" 싶은가? |

**탈락 조건 (점수와 무관하게 즉시 제외)**

- **창이 셋 이상이다.** 설정도 주문도 새 창이 아니라 **대화 창의 모드**다 (§3)
- 상시 노출되는 사이드바/탭바/툴바가 있다
- 설정이 커맨드바가 아닌 다른 경로로만 접근 가능하다
- §7 금지 목록 2개 이상 위반

## 9. 프로세스 (YC 방식)

[`plan/YC가 알려주는 AI로 디자인하는 법  스크립트.txt`](../plan/YC가%20알려주는%20AI로%20디자인하는%20법%20%20스크립트.txt) 절차를 따른다.

```
무드보드(Pinterest)  →  paper.design 셰이더/이펙트 선별  →  soul.md(이 문서)
                                    ↓
                          시안 N개 생성 (Paper 아트보드)
                                    ↓
                          랭킹: 별점 + 왜 좋고 왜 나쁜지 서술
                                    ↓
                          델타를 다음 라운드 프롬프트에 주입
                                    ↓
                              (6라운드 반복)
```

핵심은 생성이 아니라 **선별**이다.
라운드가 돌수록 좋아지는 게 아니라 **후진 게 하나씩 사라진다.**

그리고 골랐으면 반드시 **왜 골랐는지를 글로 남긴다.**
그 서술의 품질이 다음 라운드의 품질을 결정한다. 별점만 남기는 라운드는 낭비된 라운드다.
