# 답변은 어떻게 나오는가

Paper 아트보드: `답변 — 3상태`

---

## 원칙 — 답변은 두 창에 나뉘어 들어간다

녹취에 근거가 있다.

> "커멘드 바로는 모든 키움의 TR들을 다 제어를 하면서 내가 원하는 데이터를 이제 캔버스 창에 보여주고 **그 거기에 대한 설명을 이제 그 밑에다 이렇게 쭉쭉 달아주는 느낌**"

**긴 설명은 대화 창이 아니라 캔버스 밑에 붙는다.**

| | 담는 것 | 길이 |
|---|---|---|
| **대화 창** | 무엇을 했는지 확인 + 답변 본문 | **자르지 않는다** |
| **캔버스 창** | 데이터 + 캔버스 아래 긴 해설 | 길어도 된다 |

이유는 soul.md §3이다. 대화는 조종 수단이지 콘텐츠가 아니다.
따라서 답변 본문은 **짧게 쓰는 것을 지향하되**, 긴 설명은 캔버스 밑으로 보낸다.

### 답변을 자르지 않는다 (결정됨)

**2줄이 넘어도 자르거나 접지 않는다. 전부 보여준다.**

말줄임표나 "더 보기"는 쓰지 않는다 — 사용자가 방금 물어본 것에 대한 답을 감추는 것이기 때문이다.

**따라서 대화 창은 현재 턴을 담을 만큼 자동으로 자란다.**

- 리사이즈와 같은 방향으로 **위로만** 자란다. 입력줄은 자리를 지킨다
- 과거 턴은 위로 밀려 잘린다 — 최신 답변이 항상 온전하다
- 상한은 확장 상태 높이(~788px). 그보다 긴 답변은 애초에 캔버스 밑 해설로 갔어야 한다
- 사용자가 수동으로 줄이면 그 크기를 존중한다. 자동 성장은 사용자 조작을 덮어쓰지 않는다

> **분량 규칙은 두지 않는다. 대신 배치로 유도한다** — AI가 긴 설명을 쓰려 하면 그건 캔버스 해설로 갈 내용이라는 신호다.

## 3상태

### 1 · 판단 중
질문 직후. AI가 어떤 TR을 부를지 정하는 구간.

- 흰 점 하나 + `어떤 TR을 부를지 고르는 중`
- 입력줄이 `답변 중…`으로 잠기고 `ESC 중단`이 뜬다
- **스피너를 쓰지 않는다.** 액센트 색이 없는 시스템이므로 진행은 빛(점)과 글자로만 표시

### 2 · 호출·렌더 중
TR을 실제로 부르는 구간. 여러 개를 순차/병렬로 부른다.

- **TR 코드를 그대로 노출한다** — `ka10008`, 진행 바, `수급 추이 불러오는 중`
- 끝난 것은 오른쪽에 흔적으로 쌓인다 — `ka10001 ✓  공시 ✓`
- 캔버스는 **준비되는 대로 캔버스 창에 하나씩 뜬다.** 전부 끝날 때까지 기다리지 않는다

> 왜 TR 코드를 보여주나: AI가 무엇을 근거로 답했는지가 곧 신뢰다. 금융 데이터에서 출처를 감추면 답변을 검증할 수 없다.
> C안(Phosphor REPL)에서 유일하게 살아남은 아이디어이기도 하다.

### 3 · 완료
진행 줄이 접히고 **흔적만 남는다** — `ka10008 · ka10001 · 1.4s` (우측, 저대비)

- 답변 본문 한 문장
- 그 아래 **캔버스 칩** — `수급 추이` `공시 목록` + "캔버스 창에 띄웠습니다"
- 입력줄이 다시 열린다

**캔버스 칩의 역할**: 이 답변이 캔버스 창의 어느 캔버스를 만들었는지 잇는다. 창이 둘로 분리돼 있으므로 이 연결이 없으면 두 창이 서로 무관해 보인다. 클릭하면 캔버스 창의 해당 캔버스가 강조된다.

## 스트리밍

텍스트는 토큰 단위로 흘러 들어온다. 다만 **대화 창의 답변은 1~2줄이므로 스트리밍이 짧다.**

- 캔버스는 스트리밍하지 않는다. 데이터가 다 오면 한 번에 뜬다
- 부분적으로 그려지는 차트는 오독을 만든다. 금융 데이터에서 이건 정직성 문제다
- 캔버스가 뜨는 순간은 **리퀴드 글래스의 등장 규칙**을 따른다 — 페이드가 아니라 굴절 변조 ([liquid-glass.md](../liquid-glass.md) §1)

## 호출 예산 — 초당 5건

**키움 TR은 1초에 5건이다.** 이건 성능 제약이 아니라 **UI 설계 제약**이다.

### 답변 하나에 미치는 영향

TR 2~3개짜리 답변은 1초 미만이라 진행 표시가 거의 안 보인다 — 상태 1·2가 순식간에 지나간다.
문제는 **복합 질의**다. "보유 종목 전부 수급 봐줘"가 20종목이면 4초 이상 걸린다.

→ 상태 2의 진행 표시는 **남은 호출 수를 드러내야 한다.** 진행 바만으로는 4초가 멈춘 것처럼 보인다.
`ka10008 · 7/20` 형태로 분모를 노출한다. 시간이 아니라 **건수**를 보여준다 — 예산이 건수 단위이기 때문이다.

### 모자이크 캔버스 수의 상한이 여기서 나온다

캔버스가 여러 개 열려 있고 각각 REST로 갱신하면 **열린 캔버스 수가 곧 초당 예산을 먹는다.**

- 실시간 시세는 **WebSocket 19종**(0B 체결, 0D 호가잔량, 0J 업종지수)으로 받는다. 예산에 안 걸린다
- REST TR은 **스냅샷·조회 전용**. 폴링하지 않는다
- 폴링이 불가피한 캔버스(랭킹, 수급 추이 등)는 **갱신 주기를 스스로 늘려야 한다**

→ **모자이크에 캔버스를 많이 띄울수록 각 캔버스의 갱신이 느려진다.** 이건 감출 수 없는 트레이드오프다.
캔버스마다 마지막 갱신 시각을 표시해서 사용자가 신선도를 알 수 있게 해야 한다. 오래된 숫자를 최신인 척 보여주는 건 정직성 위반이다([soul.md](../soul.md) §8).

### 조용한 감시자

보유 20종목 스캔 = 4초. 주기가 5분이면 예산의 1.3%만 쓴다 — 여유롭다.
다만 **감시자와 사용자 질의가 예산을 공유한다.** 사용자가 입력하는 순간 감시자는 양보해야 한다.
사용자를 기다리게 하는 배경 작업은 실패한 배경 작업이다.

## 실패는 어떻게 보이는가

- TR 호출 실패 / **레이트리밋 초과**
- AI가 부를 TR을 못 고르는 경우
- 데이터는 왔는데 맞는 캔버스가 없는 경우 → **자유 캔버스로 간다** ([plan/canvas-taxonomy.md](../../plan/canvas-taxonomy.md))

### 오류 색 — 해결됨

`--color-warn` **`#ff9838`(주황)** 을 쓴다.

AITS 팔레트에서 `--color-bad`는 `#ff5c5c`인데 이건 `--color-up`(상승)과 **같은 값이다.**
차트 옆에서 오류를 그 빨강으로 칠하면 "상승"으로 읽힌다. 주황은 국내 시세 화면에서 가격 의미를 갖지 않으므로 충돌이 없다.
근거와 전체 매핑은 [palette.md](../palette.md).

## 미해결

- **답변이 2줄을 넘으면?** 캔버스 밑 해설로 밀어내는 규칙이 필요하다. 그 경계를 누가 정하나 — AI인가 규칙인가
- **답변에 캔버스가 없는 경우** (단순 사실 질문). 캔버스 칩이 없는 답변은 어떻게 끝나나
- **오류 색**
- 진행 표시의 모션 — 정지 시안으로 판정 불가
