**현재 유력안: `E3 — 두 창 · 상하 나란히`** — 단, 치수·유리 값은 **정정 3(2026-08-18)**,
대화 창의 치수·구조는 **정정 4(2026-08-19)**, 창 이동은 **정정 5(2026-08-19)**가 우선한다.

## 정정 5 — 창 이동은 네이티브 캡션이다 (2026-08-19)

사용자 실사용 지시: "평범한 윈도우 데스크탑 앱처럼, 적어도 클로드 데스크탑처럼
창이 움직였으면 좋겠다. 본문을 잡아 끄는 게 이상하다."

**① 손잡이.** 본문(이력·입력줄·설정 배경)은 더 이상 창 이동 손잡이가 아니다 —
본문에서는 텍스트 선택이 된다. 손잡이는 크롬만이다: 대화 창 **컨트롤 스트립**
(점·필 행)과 **설정/주문 헤더**, 캔버스 창 **상단 14px 스트립**(#dragStrip,
보이지 않는 순수 히트 영역 — 장식 유리 금지). CSS `-webkit-app-region: drag`
선언이고, 그 안의 실기능(점·필·grip·창 버튼)은 `no-drag` 구멍이다.

**② 이동 주체.** 구판의 커서 폴링(`athena:window-drag`, 16ms setBounds)은 폐기.
이동은 OS(DWM)가 수행한다 — 네이티브 타이틀바와 같은 감각이고, **가장자리 끌기
스냅(Aero Snap)이 함께 생겼다**(Win+방향키 재구현과 별개로). 구판의 DPI 크기
성장 버그(5e0a9ab)는 경로 자체가 사라져 소멸.

**③ 짝 의미론.** OS는 잡힌 창 하나만 옮기므로, 놓는 순간(디바운스 120ms)
`handleForeignArrange`의 순수 이동 분기가 상대 창을 같은 델타로 정착시킨다 —
**창 짝은 한 몸으로 이동한다**(Win+←/→ 스냅이 짝 전체를 정착시키는 기존 문법의
확장). 구판의 "대화 창만 따로 끌기"는 사라졌다 — 두 창의 상대 배치는 배치
엔진(placeWindows)만 바꾼다. 검증11(창 이동 표준화)이 캡션/구멍 계약과 짝
팔로우를 단언한다.

## 정정 4 — 대화 창은 전폭 바가 아니라 커맨드 카드다 (2026-08-19)

사용자 실사용 지시(Claude Desktop 입력 카드 스크린샷 참조): "채팅창이 딱 저 정도
크기였으면 좋겠고, 채팅 바뿐 아니라 설정하는 기능들도 있으면 좋겠다."

**① 치수.** 부팅 기본 1560×204 → **900×248**. 폭이 canvasW(1560)와 달라졌으므로
대화 창은 **캔버스 창 폭의 중앙**에 정렬한다(`main.js` `chatOriginX`,
`window-placement.js` — "짝으로 움직인다"의 계약이 "x 동일"에서 "캔버스 폭 중앙"으로
일반화됐다. 구판의 x 동일은 chatW==canvasW의 특수 사례였다). 자유 리사이즈(정정 3)와
auto-grow 가동 범위(248~788)는 유지. E3의 "가로 띠는 못 쌓는다" 논지도 유지된다 —
248px 안에 3턴 이상 담기지 않는다.

**② 구조.** 입력 영역이 1행(점+입력줄 64px)에서 **2행 스택(입력줄 52 + 컨트롤
스트립 48)**이 됐다. 스트립에는 **실기능만** 올린다(soul.md §7 장식 UI 금지):

| 컨트롤 | 역할 |
|---|---|
| 점(`#dot`) | 기존 3역할 그대로 — 상태 표시 · 확장 중심점 · 설정 진입 |
| CLI 필 | 실행기(claude -p) 표시 · 클릭=설정 모드 |
| 모델 필 | `athena:model-get` 실상태 표시 · 클릭=인라인 팝오버(검증15 API 재사용) |

넣지 않은 것: +첨부·마이크·Cowork 토글 — 존재하지 않는 기능이다. 팝오버는 창 안
오버레이라 "창은 둘"을 위반하지 않고, 유리 사다리(창 0.30 · 팝오버 0.45+blur)와
"마젠타는 점 하나"(입력 캐럿도 무채색으로 정합)를 지킨다. 1020px 읽기 컬럼(E3
조정)은 900px 폭에서는 성립하지 않으므로 폐기 — 이력은 카드 폭 전체를 쓴다.
시각 사양은 Paper `47 · AT-CH-001R 커맨드 카드 개편` 보드가 정본이다.

Paper 아트보드: `E1 — 두 창 · 겹침` · `E2 — 두 창 · 나란히` · `E3 — 두 창 · 상하 나란히` (데스크톱 포함)

E(캔버스 모자이크)가 승자로 확정된 뒤 두 건의 사양 정정을 반영한 결과물이다.

## 정정 1 — 창은 두 개의 **독립된 창**이다

내가 한 창 안에 떠 있는 바로 만든 것이 틀렸다. 녹취 원문:

> "우리는 커멘드 바가 있고 두 번째로는 이제 그 뭔가 서브 창이 하나 나가. (…) 그러한 시각적인 정보를 담는 창 하나 그리고 여기에 있는 커멘드 바 하나 이렇게 있다라고 보면 됩니다."

OS 레벨에서 분리된 창 둘이다. 각자 따로 움직이고 따로 신축한다.

| 창 | 역할 | 내용 |
|---|---|---|
| **캔버스 창** | 출력 | 모자이크. 시계열 / 호가 사다리 / 분포 / 관측 |
| **대화 창** | 입력 | 자연어 입력 + 최소 면적 이력. 지난 턴은 흐려진다 |

이 정정으로 **대화 이력의 거처가 정해졌다.** 이전 안(E)에는 이력이 아예 없었다.

## 정정 2 — 모든 표면이 유리다

캔버스 창도, 그 안의 캔버스도, 대화 창도 전부 리퀴드 글래스.
Apple 규범 2건(콘텐츠 레이어 유리 금지 / 유리 위 유리 금지)에서 **의도적으로 이탈**한다.
근거와 지불 비용은 [`soul.md`](../soul.md) §7 참조. 요약: 무드보드의 지배 이미지(visionOS 핀 5·7)가 전면 유리이고, Apple 규범은 iOS 기준이다.

**광량 3단계 고정** — 데스크톱 → 창 → 캔버스. 같은 단계끼리는 값이 같아야 한다. 이게 전면 유리에서 위계를 유지하는 유일한 장치다.

## 정정 3 — 치수는 부팅 기본값이고, 유리는 훨씬 얇다 (2026-08-18)

사용자 실사용 지시 2건이 아래 두 결론을 뒤집었다.

**① 창 크기는 고정이 아니다.** "채팅창과 캔버스창이 가로 크기가 고정되어 있는데, 창 크기는
유동적이어야 한다 — 무조건 가로세로 모두 조정 가능해야 한다." E3 치수(캔버스 1560×800,
대화 1560×204~788)는 이제 **부팅 기본값**이다. 두 창 모두 OS 모서리 리사이즈로 가로·세로
자유롭게 조절된다(`app/main.js` — min=max 잠금 제거, 하한만 유지: 캔버스 480×320, 대화
480×160). 204~788px는 자동 성장(auto-grow)의 가동 범위로만 남는다. Win+←/→ 스냅 정착은
반절 스냅 기하 판별(`looksLikeOsSnapHalf`)로 사용자 리사이즈와 구분한다.

**② 유리 두께 전체 하향.** "리퀴드 글래스 느낌이 안 들어. 그냥 검은 창 같아. 최대한 뒷
배경이 비치도록." 아래 §E3-확장의 0.82→0.97 스케일은 acrylic 위에서 사실상 불투명 검정으로
읽혔다 — 굴절 대상이 안 보이면 유리가 아니다. 가독성 블러는 네이티브 acrylic·카드
backdrop-filter가 담당하므로 틴트 알파를 내린다. "두께는 뒤 정보 밀도에 비례" 규칙은 유지 —
**스케일만 내려갔다**:

| 표면 | 구판 | 현행 |
|---|---|---|
| 대화 창 · 기본(뒤=데스크톱) | 0.82 | **0.30** |
| 대화 창 · 확장(뒤=캔버스) | 0.97 | **0.55** |
| 캔버스 창 표면 | 0.92~0.97 | **0.50** |
| 카드 | 0.55 + blur 14px | **0.45** + blur 14px |

> **2026-08-19 승격.** 이 표가 공식 **유리 사다리**다(soul.md §7 완화책 2 개정 —
> 질의응답 결정 "문서를 현실에 맞게 개정"). 값의 SSOT는 `app/styles/tokens.css`
> `--glass-window/-card/-canvas/-window-max`이고, verify 검증16이 순서
> (window < card < canvas < window-max)와 표면 렌더 일치를 단언한다.

아래 E3-확장·"결정된 것" 2의 구판 수치는 이 표가 대체한다. 삭제하지 않는 이유는 이
문서의 관례대로 — 무엇을 왜 바꿨는지가 기록이기 때문이다.

## E1 — 겹침

대화 창이 캔버스 창 **위에 떠 있다.** 유리 아래로 매물대 막대와 관측 텍스트가 굴절되어 지나간다.

- **강점**: "내가 방금 부른 데이터 위에 손을 얹고 말을 건다"는 감각. 유리의 존재 이유가 화면 안에서 자족적으로 증명된다. 한 화면 안에서 완결
- **약점**: 대화 창이 캔버스를 가린다. 매물대 캔버스가 절반 이상 덮였다. 창이 셋 넷으로 늘면 관리 부담이 커진다
- **판정 질문**: 가리는 대가를 치를 만큼 겹침이 주는 것이 있는가

## E2 — 나란히

두 창이 데스크톱 위에 나란히. 유리 뒤에 **데스크톱**이 온다.

- **강점**: 아무것도 가리지 않는다. 그리고 [무드보드](../moodboard/moodboard.md)의 1순위 DNA — *"유리 뒤에 진짜 환경이 있다"(8장 중 6장)* — 가 **문자 그대로** 성립한다. 유리 뒤가 UI가 아니라 실제 데스크톱이다
- **약점**: 굴절 대상이 데스크톱 배경뿐이라 굴절이 은은하다. 사용자 배경화면에 따라 유리가 완전히 달라 보인다 — 통제 불가능한 변수
- **치명적 결함 — 대화 창의 비례**: 오른쪽 세로 기둥(396×874)이 되면서 **채팅 사이드바처럼 보인다.** 상단 2/3가 비고, soul.md §3의 "이력 칸은 최대한 최소화"와 정면으로 어긋난다. 배치는 맞았지만 대화 창이 틀렸다

## E3 — 상하 나란히 ✅

**E2의 배치(겹치지 않음) + E1의 대화 창(가로로 넓고 낮음).** 둘을 다 살리는 배치는 이것 하나뿐이다.

| 창 | 크기 | |
|---|---|---|
| 캔버스 창 | 1560 × 800 | 위. 모자이크가 최대 폭을 갖는다 |
| 대화 창 | 1560 × 204 | 아래. 이력 3줄 + 입력 한 줄. 그게 전부 |

- **왜 이게 맞는가**
  - 대화 창의 비례가 **구조 자체로 "이력은 최소"를 강제한다.** 204px 안에 3턴 이상 담을 수 없다. 세로 기둥은 무한히 쌓이지만 가로 띠는 못 쌓는다
  - 아무것도 가리지 않는다(E2 유지) + 무드보드 1순위 DNA인 "유리 뒤 진짜 환경"도 유지
  - 모자이크가 1560px 전폭을 쓴다. 캔버스 12종을 담아야 하는 창에 이게 크다
- **조정한 것**: 이력 텍스트를 1020px 읽기 컬럼으로 묶었다. 1560px 전폭에서는 타임스탬프가 본문과 끊겨 보였다

## E3-확장 — 대화 창 리사이즈

**아트보드: `E3-확장 — 대화 창 리사이즈`**

이력을 길게 훑는 문제는 **창 리사이즈로 푼다.** 창을 새로 띄우지 않으므로 soul.md §3(창은 둘)을 위반하지 않는다.

대화 창의 위쪽 모서리를 잡아 끌면 창이 **위로 자란다.** 아래(입력)는 고정, 위로만 자란다 — 입력이 손 아래 그대로 있어야 하기 때문이다.

| 상태 | 높이 | 유리 뒤 | 이력 |
|---|---|---|---|
| **기본** | 204px | 데스크톱 | 3턴 |
| **확장** | ~788px | **캔버스 창** | 7턴+ |

### 이 해법이 밝혀낸 것

**E1은 틀린 안이 아니었다. E3 대화 창의 확장 상태였다.**

기본 상태에서 유리 뒤는 데스크톱이지만, 확장하면 창이 캔버스 창 위로 올라타면서 **유리 뒤가 캔버스로 바뀐다.** E1에서 좋아 보였던 "내가 방금 부른 데이터 위에 손을 얹고 말을 건다"는 감각이 여기서 정확히 돌아온다.

즉 **두 안은 한 창의 두 상태였다.** 배치를 고르는 문제가 아니라 상태 전이를 설계하는 문제였다.

### 재료가 상태에 따라 달라진다

이건 리퀴드 글래스의 정의와 정확히 맞는다 — 재료가 "아래 콘텐츠에 따라 연속적으로 적응한다"는 것.

- **기본**: 뒤가 데스크톱(저밀도) → 유리를 얇게. 다크 알파 ~0.82
- **확장**: 뒤가 캔버스(고밀도 데이터) → 유리를 **훨씬 두껍게**. 다크 알파 ~0.97

**작업 중 이걸 실측으로 배웠다.** 기본 상태 값(0.82)을 확장에 그대로 쓰니 뒤 차트·호가 숫자·관측 텍스트가 전부 읽혀서 서리유리가 아니라 깨진 오버레이로 보였다. 굴절층도 0.46 → 0.17로 낮췄다 — 서리유리 뒤의 차트는 붉은 덩어리가 아니라 **저대비 유령**이다.

> **규칙**: 유리의 두께는 고정값이 아니다. **뒤에 있는 것의 정보 밀도에 반비례한다.**
> 이걸 `soul.md` §7 재료 규범에 넣어야 한다.

### 남은 미검증

- **자라는 애니메이션** — 창이 커질 때 유리 두께가 0.82 → 0.97로 전이해야 한다. 이 전이가 자연스러운지는 모션에서만 판정된다
- 확장 중 캔버스 창을 조작해야 하면? 대화 창을 다시 줄이는 것 외의 경로가 없다 — 그게 맞는 제약인지
