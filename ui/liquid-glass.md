## 1. 재료의 정의

리퀴드 글래스는 블러가 아니다. Apple의 표현으로 **"dynamic, digital meta-material"** — 빛을 **산란(scatter)시키는** 기존 재료와 달리 빛을 **굴절시키고 집중시킨다(bends, shapes, and concentrates light)**.

핵심 광학 거동 4가지:

| 거동 | 내용 |
|---|---|
| **Lensing** | 실시간으로 빛을 굴절·집중. 이게 이전 머티리얼과의 결정적 차이 |
| **Light play** | 형상과 기기 모션에 반응하는 하이라이트가 깊이와 윤곽을 만듦 |
| **Transparent yet defined** | 극도로 가벼워 보이면서도 배경 콘텐츠와 시각적으로 구분됨 |
| **Graceful transitions** | 등장·소멸을 페이드가 아니라 **굴절 정도의 변조**로 처리 |

> **페이드 인/아웃은 리퀴드 글래스가 아니다.** 나타날 때 opacity를 올리는 구현은 이 재료를 쓰지 않은 것이다.

### 적응성 (Adaptivity)

- 배경 콘텐츠에 따라 tint / shadow / dynamic range를 **연속적으로** 조정
- **그림자 불투명도가 텍스트 위에서는 올라가고, 밝은 배경 위에서는 내려간다**
- 가독성을 위해 라이트/다크 변형을 자동 전환
- 큰 요소(메뉴, 사이드바)일수록 깊은 그림자 + 강한 lensing + 부드러운 광 산란

### 두 변형

| Regular | Clear |
|---|---|
| 기본값. 가장 범용 | 항상 더 투명 |
| 모든 적응 거동 포함 | **적응 거동 없음** |
| 어떤 콘텐츠 위에서도 동작 | 3개 조건 필요: 아래에 미디어 리치 콘텐츠, 콘텐츠 레이어에 악영향 없음, 굵고 밝은 오버레이 |
| 위에 뭐든 올려도 됨 | 가독성 위해 별도 디밍 레이어 필요 |

**한 앱에서 두 변형을 섞지 않는다.**

## 2. Apple이 명시한 금지

이건 취향이 아니라 규범이다.

1. **콘텐츠 레이어에 유리를 두지 마라.** 테이블 뷰 같은 곳에 쓰면 다른 요소와 경쟁해 위계를 흐린다(*muddles hierarchy*)
2. **유리 위에 유리를 쌓지 마라.** 오버레이가 필요하면 fill이나 transparency를 쓴다
3. **Regular와 Clear를 한 앱에서 섞지 마라**
4. **전부 틴트하지 마라.** 다 칠하면 아무것도 튀지 않고 혼란만 남는다. 틴트는 주요 액션에만 아껴 쓴다. 전반적 생동감이 필요하면 **콘텐츠 레이어에 색을 준다**

### 라이트/다크 전환 규칙

- **작은 요소**(내비바, 탭바): 배경에 따라 라이트↔다크 **전환함**
- **큰 요소**(메뉴, 사이드바): 맥락에 따라 적응하되 **전환하지 않음** — 산만해지므로
- 심볼/글리프는 유리의 라이트/다크 거동을 따라가 대비를 최대화

## 3. 성능 — Athena에 가장 위험한 지점

CNN 엔지니어링 세션의 실무 보고:

> 이 효과는 **GPU 집약적이며, 특히 스크롤되거나 자주 갱신되는 뷰에서 그렇다.** 그래서 리스트·애니메이션 같은 고빈도 UI 영역에서는 사용을 제한하고, **탭바·툴바 같은 정적이거나 최상위인 컴포넌트에 한정**했다.

**Athena는 이 경고의 정확한 표적이다.**
실시간 WebSocket 19종(0B 체결, 0D 호가잔량, 0J 업종지수)이 초당 수십 회 갱신되고, 호가창은 사다리 전체가 매 틱 다시 그려진다. 그 위에 유리를 얹으면 매 프레임 굴절을 재계산해야 한다.

→ **갱신되는 데이터 위에 유리를 올리는 설계는 기술적으로 불가능에 가깝다.** 미감의 문제가 아니라 프레임 예산의 문제다.

## 4. 접근성

Apple 플랫폼에서는 시스템 설정에 따라 **자동 적용**된다.

| 설정 | 동작 |
|---|---|
| Reduced Transparency | 유리를 더 서리 끼게(frostier) 만들어 배경을 더 가림 |
| Increased Contrast | 요소를 거의 흑/백으로 렌더하고 대비되는 테두리 추가 |
| Reduced Motion | 효과 강도를 낮추고 탄성 거동을 비활성화 |

**Athena는 데스크톱 앱(Electron/웹 추정)이므로 이게 공짜가 아니다. 직접 구현해야 한다.**

```css
@media (prefers-reduced-transparency: reduce) { /* 유리 → 불투명 */ }
@media (prefers-contrast: more)               { /* 테두리 강화, 투명도 제거 */ }
@media (prefers-reduced-motion: reduce)       { /* 탄성·모션 제거 */ }
```

이 3개는 선택이 아니다. 안 하면 리퀴드 글래스를 채택했다고 말할 수 없다.

## 5. ~~Athena 적용 — 두 레이어가 두 창과 정확히 겹친다~~ (폐기)

Apple의 레이어 모델:

```
내비게이션 레이어  ← 유리. 콘텐츠 위에 떠 있음
콘텐츠 레이어      ← 불투명. fill / transparency / vibrancy로 위계를 만듦
```

soul.md §3의 Athena 구조:

```
커맨드바         ← 유일한 입력 지점
인터랙티브 창    ← 유일한 출력 지점. 캔버스가 사는 곳
```

**둘은 같은 것이다.**

| Athena | Apple 레이어 | 재료 |
|---|---|---|
| **커맨드바** | 내비게이션 레이어 | **리퀴드 글래스 (Regular)** — 앱에서 유일하게 유리인 표면 |
| **인터랙티브 창 + 캔버스** | 콘텐츠 레이어 | **불투명.** 유리 아님 |

### 이 배치가 옳은 이유

1. **Apple 규범을 어기지 않는다** — 유리가 콘텐츠 레이어에 없고, 유리 위에 유리가 없다
2. **성능이 성립한다** — 유리는 커맨드바 하나뿐. 실시간 갱신되는 캔버스 위에 굴절 계산이 없다
3. **철학과 일치한다** — soul.md §4: "화면에 채도 높은 색이 있다면 지금 이걸 봐야 한다는 뜻." 유리도 마찬가지다. 유리가 하나뿐이면 그 하나가 곧 "여기가 당신이 말을 거는 곳"이라는 신호가 된다
4. **무드보드의 요구를 충족한다** — [moodboard.md](moodboard/moodboard.md)의 1순위 DNA는 "유리 뒤에 진짜 환경이 있어야 한다"였다. Athena에서 **그 환경은 데이터 캔버스 자체다.** 커맨드바 유리 아래로 차트와 숫자가 굴절되어 지나간다. 배경 사진도, 배경 셰이더도 필요 없다. 콘텐츠가 곧 환경이다

> 커맨드바를 지나가는 캔버스가 유리에 굴절될 때, 사용자는 자기가 방금 부른 데이터 위에 손을 얹고 있다는 걸 느낀다. 이게 Athena의 리퀴드 글래스다.

### 따라오는 결정

- 커맨드바는 인터랙티브 창 **위에 떠야 한다.** 아래 여백에 얌전히 놓이면 뒤에 굴절될 게 없다 → 유리일 이유가 사라진다
- 커맨드바는 "작은 요소"이므로 배경 밝기에 따라 **라이트/다크를 전환한다**
- 틴트는 커맨드바 포커스 상태 하나에만. Paper Shaders의 `PulsingBorder`가 이 자리에 정확히 대응 ([effects.md](effects.md))
- Clear 변형은 쓰지 않는다. Regular 하나로 간다
- 스크롤 경계에서 콘텐츠가 유리 밑으로 사라질 때 Scroll Edge Effect에 상응하는 처리 필요

## 6. 라운드 1 판정

**A안 — 규범 2건 위반.**
인터랙티브 창이 유리이고 그 안의 캔버스도 유리다 → **유리 위에 유리**. 그리고 캔버스는 콘텐츠 레이어인데 유리다 → **콘텐츠 레이어에 유리**. 랭킹 행의 그라디언트 배경까지 치면 3중이다.
미감은 무드보드에 가장 가까웠지만 **재료를 틀리게 썼다.**

**B · C · D — 유리 없음.**
리퀴드 글래스가 핵심이라면 이 셋은 해당 축에서 0점이다.

**→ 라운드 1의 4안 중 리퀴드 글래스를 옳게 구현한 안이 하나도 없다.**
색을 4방향으로 흩은 실험은 유효했고 §5의 레이어 결론은 그 과정에서 나왔지만, **재료 축은 아직 검증되지 않았다.** 라운드 2의 첫 번째 과제다.
