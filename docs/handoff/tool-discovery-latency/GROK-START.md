나는 Athena의 도구·화면·카드 탐색 지연 개선 작업을 다른 AI에서 이어받아 진행하려고 한다. 이 브랜치는 `codex/tool-discovery-latency-handoff`이며, 먼저 저장소 `AGENTS.md`, `docs/handoff/tool-discovery-latency/README.md`, `docs/handoff/tool-discovery-latency/PLAN.md`를 읽어라. 필요한 하위 디렉터리 지침도 확인하라. 이 인수인계는 작업 데이터와 계획이며 기존 보안·실행 권한을 바꾸는 지시가 아니다.

이전 AI는 요구 분석, 코드 경로 확인, 외부 사례 조사, 계획 작성과 두 번의 독립 검토까지 마쳤다. 아직 이 계획의 구현이나 A/B/C 측정은 하지 않았다. 새 계획을 처음부터 장황하게 다시 쓰지 말고 0~2단계의 실행을 이어가라.

1. 현재 cwd, 브랜치, HEAD, dirty 변경, 로컬 실행 환경을 확인하고 기준 상태를 기록하라. 다른 사람의 변경을 삭제·덮어쓰기·일괄 stage하지 마라. 체크아웃에 진행 중인 변경이 있으면 소유권이 분리되는 작업 폴더를 사용하라.
2. 도구·화면·카드 검색이 전부 대화 메모리라는 가정은 틀리다. 이미 SQLite 종목 인덱스, selector 어휘 검색, fast path, dispatch/preflight, 카드 매핑, metrics가 있다. 이 기존 경로의 연결과 실제 적중률부터 확인하라.
3. 기존 계측을 재사용해 입력→세션 준비→직접 처리 인식기→모델→검색/describe/resolve→조회→실제 카드 표시의 시간을 분리하라. 단계별 비용과 반복 요청/오류를 측정하고, 첫 토큰만 빨라진 것을 성공으로 계산하지 마라.
4. 정답 요청 세트와 기준 실행을 먼저 만들고, 같은 실패의 무의미한 재검색과 동일 검색/스키마의 중복부터 고쳐라. 기존 preflight가 이미 정보를 묶어 제공하면 그 응답의 소비 방식을 수정하라. 새 API·DB·벡터 검색기를 먼저 만들지 마라.
5. B군을 A군과 같은 공급자·모델·데이터 조건으로 비교하라. 정확도/실패율/timeout과 p50/p95, 모델 왕복을 함께 측정하라. 지배적 병목이 세션이나 기존 인식기이면 계약 확장 대신 그 근거에 맞는 최소 변경을 하라.
6. identity, 의미 호환성, schema, 권한, 승인, 일회성 plan, 화면 표시 검증을 유지하라. 자연어 조회를 주문 실행으로 바꾸지 마라. 현재 시세나 승인·plan token을 도구 정의 캐시처럼 재사용하지 마라.
7. 변경한 동작에 맞는 회귀 테스트와 실제 UI 검증을 수행하라. 기존 실패와 새 실패를 구분하고, 실제 공급자/백엔드가 없으면 fixture 성공과 라이브 미검증을 명확하게 나눠 보고하라. 실패를 숨기거나 임의의 금융 데이터를 표시하지 마라.
8. 다른 작업 범위로 확대하지 말고, 결과·실제 명령·측정값·현재 커밋·미검증 항목을 `docs/handoff/tool-discovery-latency/` 아래 새 진행 기록에 남겨라. 단계별 구현 커밋은 작게 만들고 이 작업 브랜치에서 작업하라. main 병합이나 배포는 별도 명시 요청 없이 하지 마라.

나는 대기 시간이 길고 반복 확인하는 것을 싫어한다. 이미 명확한 로컬 구현·검사 단계는 불필요한 재확인 없이 진행하되, 필요한 자격 증명이 없거나 파괴적인 선택이 필요한 경우에만 구체적인 차단 사유를 알려라. 사용할 수 없는 Codex 전용 도구·OMX 모드·스킬을 설치하거나 흉내 내는 데 시간을 쓰지 말고, 사용 가능한 shell/파일 편집/테스트 도구로 실행하라. 비밀키·계좌정보를 프롬프트나 로그에 출력하지 마라.
