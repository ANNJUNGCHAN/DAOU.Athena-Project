# Athena 도구·화면·카드 탐색 지연 개선 계획

작성일: 2026-09-09 / 범위: 계획 수립. 구현·성능 실험·배포는 아직 수행하지 않음.

## 1. 결정

**기존 레지스트리와 검증기를 재사용하면서, 모델이 반복해서 탐색하는 구간부터 줄인다.**

순서는 `측정 → 중복 탐색 차단 → 검색·스키마·카드 정보 묶음 → 제한된 직접 연결 → 캐시 최적화 → 단계적 적용`이다. 처음부터 새 RDB, 벡터 DB, 검색 서버를 도입하지 않는다. 인덱스 조회가 실제 병목으로 확인될 때만 저장소 변경을 검토한다.

화면 버튼과 카드 액션은 기능 ID가 명확하므로 직접 연결 대상으로 우선 검토한다. 자유로운 자연어는 검색과 모델 판단을 유지한다. 주문·취소 등 상태 변경 작업을 자연어 규칙만으로 자동 실행하는 범위 확대는 하지 않는다. 기존 승인·권한·실행 검증 계약은 모든 경로에서 유지한다.

## 2. 성공의 정의

- 사용자 기준: 같은 요청의 반복 검색이 사라지고, 올바른 데이터·대상·기간의 카드가 더 빨리 표시된다.
- 성능 기준: 첫 상태 메시지가 아니라 **사용자 입력부터 검증된 카드 표시 완료까지** 측정한다. 화면 이동은 목적 화면의 사용 가능 시점을 측정한다.
- 정확도 기준: 올바른 기능 선택, 인자, 데이터 출처, 단위, 카드, 필요한 확인 질문까지 평가한다.
- 종료 조건: 독립 검토, 회귀 검사, 비교 실험, 실제 UI 확인, 되돌리기 검증을 모두 마친 기능만 적용한다. 데이터 공급자 미연결은 미검증으로 남긴다.

초기 제안 목표는 B군의 p50 30% 이상, p95 20% 이상 단축이다. 이는 실측치나 보장 수치가 아니다. 기준 측정에서 탐색이 차지하는 비중과 표본 수를 확인한 뒤 목표를 확정하고, 후보 구현 결과를 본 후 유리하게 바꾸지 않는다. 외부 API 대기가 지배하면 탐색 시간 개선과 전체 체감 개선을 별도로 보고한다.

## 3. 근거와 아직 모르는 것

현재 대화에서 확인한 코드:

- `app/lib/main/live-prompt.js`: search → describe → resolve 지시와 Grok의 도구 검색 계층이 존재한다. 스키마 확인을 단순 생략했을 때 재시도가 늘었다는 과거 주석이 있다. 주석의 과거 수치를 현재 성능으로 사용하지 않는다.
- `app/main.js:4558`: live 요청 진입점과 타이머. `:4643`에는 이미 SQLite 기반 종목 인덱스가 있고, `:4648`, `:4678` 이후에는 차트·시세 등 직접 처리 경로가 모델 호출보다 앞에 있다. 메모리만으로 검색하는 구조가 아니다.
- `app/lib/main/selector-fast-path.js:166`: 기존 빠른 경로와 deadline/correlation 검증, durationMs가 있다. 새 라우터를 병렬로 만들지 않고 이 경로를 재사용한다.
- `backend/athena_api/selector/service.py:156`, `:462`, `:556`: search/describe/resolve. `backend/athena_api/selector/ranking.py:499`에는 이미 어휘 기반 검색과 catalog version이 있다.
- `backend/athena_api/card_surface_contract.py:468`, `:600`: operation과 카드 계약의 기존 연결. `app/lib/main/provider-runtime-metrics.js:139` 이후에는 기존 측정 집계가 있다. 이 계약과 계측을 우선 확장한다.
- 구조 검토에서 `backend/athena_api/api/canvas_push.py:1548`의 selector dispatch와 `:1846`의 부작용 없는 preflight를 확인했다. preflight는 이미 search/describe/required_arguments를 묶는다. 별도 묶음 API를 신설하기 전에 공급자 경로가 이 응답을 사용하는지 확인한다.
- 현재 main 작업 트리에 공급자 세션, selector, 카드 관련 동시 변경이 많다. 실험 기준은 브랜치 이름만이 아니라 HEAD와 적용된 변경 내용으로 고정한다.

아직 모르는 것은 단계별 실제 지연, 중복 호출 원인, 공급자별 동일 경로 사용 여부, 빠른 경로의 실사용 적중률, 카드 표시 완료 신호의 실효성이다. 진입점에서 여러 인식 경로를 순서대로 시도하는 비용도 측정하되 병목이라고 미리 단정하지 않는다. 캡처의 시간들을 단순 합산해 순차 실행 시간으로 단정하지 않는다. 위 줄 번호는 동시 변경에 따라 달라질 수 있어 착수 시 재확인한다. 계획 작성 시 확인한 HEAD는 `5b5256ac7d898fcdd301fb942e30418dfac10cbf`이며 dirty 변경이 있어 HEAD만으로 현재 상태를 재현할 수 없다.

외부 근거:

- [Anthropic Tool Search](https://www.anthropic.com/engineering/advanced-tool-use): 필요한 도구만 로드하며 자주 쓰는 도구는 미리 제공한다. 검색 자체는 추가 단계를 만든다. 공개된 토큰·정확도 개선은 업체 내부 평가로 Athena 성능 보장이 아니다.
- [Anthropic Code Execution + MCP](https://www.anthropic.com/engineering/code-execution-with-mcp): 도구를 파일처럼 탐색하고 중간 처리를 코드로 묶는다. 토큰 절감률을 지연 단축률로 바꾸어 해석하지 않는다.
- [OpenAI Tool Search](https://developers.openai.com/api/docs/guides/tools-tool-search): 애플리케이션이 검색을 담당하고 필요한 도구 정의를 반환하는 경로를 지원한다. API 기능 지원이 현재 Codex/Grok/Claude CLI 전송 계층 지원을 뜻하지는 않는다.
- [MCP Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools): 도구 목록·스키마·변경 알림과 권한별 가용성에 맞춰 캐시한다.

## 4. 목표 처리 구조

```text
사용자 입력 / 카드 액션
  → 구조화된 화면 상태·종목 ID·행동 종류 확인
  → 명시적 액션 ID 또는 검증된 단일 조회 문법이면 기존 빠른 경로
  → 그 외에는 기존 레지스트리에서 후보 검색
      → 후보별 입력 스키마·지원 카드·제약을 함께 제공
      → 모델이 필요한 선택과 인자 해석 수행
      → 불명확하면 제한적 재검색 또는 짧은 확인 질문
  → 공통 서버 검증: 의미 호환성·인자·권한·실행 계획
  → 데이터 조회와 호환 카드 렌더링
  → 표시 완료 신호 확인
```

검색 결과는 선택 후보이고 실행 권한이 아니다. 검색 순위·유사도만으로 실행하지 않는다. 카드 후보가 있다는 사실도 실제 데이터가 표시됐다는 증거가 아니다.

## 5. 단계별 실행 계획

### 0단계 — 기준과 변경 소유권 고정

- 진행 중인 selector·provider·card 작업의 실제 파일과 핸드오프를 확인한다. 이 계획의 코드 변경과 다른 작업을 섞지 않는다.
- 비교 기준 HEAD, 관련 파일 해시/패치, 레지스트리 버전, 공급자·모델·설정, 계정 권한 범위를 기록한다. 동시 변경이 들어오면 기준을 다시 고정한다.
- 민감정보를 제거한 재현 요청을 수집하고, 구현 전에 기대 기능·인자·카드·질문/실패 결과를 확정한다.
- 산출물: 기준 manifest, 정답 요청 세트, 변경 책임 범위. 이후 단계의 선행 조건이다.

### 1단계 — 지연과 중복의 원인 측정

- 기존 provider-runtime-metrics와 진입점 타이머를 확장하고 하나의 trace ID로 입력 수신, 각 직접 처리 인식기, 공급자 세션 준비, 모델 요청, 도구 검색, 스키마 확인, resolve, 외부 데이터 응답, 렌더 요청, 표시 완료를 연결한다.
- 각 span은 시작·종료와 부모 관계를 기록한다. 병렬 span을 합산하지 않고 실제 임계 경로를 구한다.
- 모델 호출 수, 토큰 수(공급자가 제공할 때), 정규화된 도구 요청 fingerprint, 오류 종류, 캐시 적중, 재시도 사유를 기록한다. 제공되지 않는 지표는 추정값 대신 미지원으로 표시한다.
- 제품 UI에는 간단한 진행·실패 정보만 표시하고 내부 상세 로그는 진단용으로 둔다. 비밀키·원문 계좌정보를 로그에 남기지 않는다.
- 산출물: 공급자별 cold/warm p50·p95, 병목 구성, 캡처와 유사한 반복 검색의 실제 원인.

### 2단계 — 중복 탐색과 불필요한 모델 왕복 축소 (B군)

- 같은 턴·권한·레지스트리 버전에서 동일한 읽기 전용 검색/스키마 요청은 진행 중 요청을 공유하거나 결과를 재사용한다. fingerprint는 정규화 질의, intent, candidate/preferred/detail, 인자, 계정·권한 범위, catalog/stock-master version을 포함한다. 서로 다른 요청을 과도한 정규화로 합치지 않는다. 데이터 조회·주문을 무조건 중복 제거하지 않는다.
- 먼저 기존 dispatch/preflight 묶음 응답이 각 공급자 경로에서 사용되는지 확인한다. 이미 충분한 정보가 있다면 연결·소비 방식만 고친다. 측정에서 중복 조회가 확인되고 정보가 부족한 경우에만 기존 계약을 확장해 후보의 정확한 스키마·상세 기능·카드 정보를 함께 제공한다. 별도 병렬 API를 만들지 않는다. 결과 크기를 제한하고 큰 스키마는 필요할 때 읽는다.
- 현재 describe가 수행하는 정보 조회 외 검증·증거 생성이 있다면 공통 서버 경로에 보존한다. 프롬프트의 describe 생략 지시는 새 계약과 테스트가 준비된 뒤에만 바꾼다.
- backend unavailable, authorization denied, unsupported capability 등 오류를 구분한다. 같은 상태·같은 실패에는 검색어만 바꿔 반복하지 않는다. 가용성이 바뀌면 새 요청에서 다시 확인한다.
- 기본적으로 증거가 추가된 후보 확대/인자 수정만 1회 허용한다. 외부 API의 일시 오류 재시도와 탐색 재시도는 별도로 관리한다. 상태 변경 호출은 일반 재시도 대상으로 넣지 않는다.
- 산출물: 기존 외부 인터페이스와 호환되는 묶음 조회, 중복 방지, 실패 처리, 대응 회귀 검사. 프로바이더 전송 계층마다 실제 도구 로딩 방식이 달라도 서버 계약은 공유한다.

### 3단계 — 제한된 직접 연결 (C군)

- 1순위: 화면 버튼·카드 새로고침·이미 선택된 종목의 명시적 차트 액션. 2순위: 대상과 행동이 유일하게 해석되는 단일 조회 문장.
- 기존 fast path를 확장한다. 모든 경로가 동일한 instrument identity와 selector 검증기를 사용하게 한다.
- 미지정 종목, 복수 대상, 부정문, 이전 대화 참조, 조회/주문 혼동, 지원하지 않는 기간은 억지로 기본값을 채우지 않고 기존 해석·질문 경로로 보낸다.
- 먼저 shadow 모드에서 선택 결과만 비교한다. 후보 경로가 데이터 조회·렌더·주문을 추가 실행하지 않도록 한다.
- 산출물: 기능별 allowlist, 직접 연결 정확도와 적용 비율, fallback 사유, 독립 검토 결과.

### 4단계 — 캐시와 검색 인덱스 최적화

- 2단계의 턴 내 재사용과 별개로, 도구 정의·스키마·카드 매핑의 세션 간 재사용을 검토한다.
- 키에 서버/플러그인 식별자, 레지스트리·스키마 버전, 유효 사용자/테넌트/권한 범위를 반영한다. 종목 해석을 포함한 파생 결과는 종목 마스터 버전과 정규화된 대상·행동·문맥도 포함한다. 토큰 원문을 캐시 키나 로그에 저장하지 않는다.
- 목록 변경, 로그인·권한 변경, 플러그인 재연결 때 무효화한다. 변경 알림이 불완전한 서버는 재검증/TTL 규칙을 둔다. 실행 권한은 매번 서버에서 확인한다.
- 실행용 일회성 plan token, 승인, nonce, 현재 시세는 도구 정의 캐시로 재사용하지 않는다.
- 기존 자료에서 생성한 이름·동의어·도메인·행동 인덱스로 먼저 실험한다. 별도 카탈로그 수작업 관리로 원본을 이중화하지 않는다. 별도 RDB/FTS/벡터 검색은 병목 또는 후보 누락이 측정될 때만 비교한다. 새 의존성은 별도 범위 결정 대상이다.
- 산출물: 캐시 무효화 검사, stale-cache/권한 변경 검사, 인덱스 유효성, cold/warm 비교.

### 5단계 — 공급자별 검증과 단계적 적용

- Claude·Codex·Grok 각각에서 A/B/C를 같은 모델·설정으로 비교한다. 서로 다른 모델의 차이를 검색 구조의 효과로 해석하지 않는다.
- 직접 연결은 기능·공급자별로 켜고 끈다. 초기 적용은 검증된 읽기 전용 작업부터 시작한다.
- flags를 끈 뒤 이전 경로로 정상 복귀하는지 확인한다. 복귀 시 캐시/일회성 실행 계획을 그대로 재사용하지 않으며 이미 성공한 작업을 재실행하지 않는다.
- 산출물: 비교 보고서, 실제 화면 증거, 적용/보류 기능 목록, rollback 결과. 구현 중 나온 미해결 실패가 있으면 해당 범위를 완료로 표시하지 않는다.

## 6. 평가 세트와 실험 설계

초기 정답 세트는 6개 범주 각 50건, 총 300건으로 시작한다. 충분한 통계적 검정력을 보장하는 표본 수는 아니므로 기준 분산과 신뢰구간에 따라 증설한다.

1. 명시적 화면·카드 액션과 정확한 이름의 단일 조회.
2. 한국어 띄어쓰기·동의어·오타·바꿔 말하기.
3. 유사하지만 다른 대상/행동: 금현물·금 ETF·금 뉴스·시장가 매수, 가격·호가·차트.
4. 문맥 참조·부정·다중 요청·확인이 필요한 모호함.
5. 미지원 기능·백엔드 장애·타임아웃·권한 부족.
6. 스키마/권한 변경·오래된 캐시·재연결·일회성 계획 재사용 방지.

별도 튜닝 세트와 holdout을 의도/문장 계열 단위로 분리한다. 동일 문장의 표현만 바꾼 예제가 양쪽에 섞이지 않게 한다. 정답은 실행한 모델 자신이 사후 판정하지 않고 독립 검토한다.

- 1차: 동일한 데이터 fixture로 라우팅·인자·카드 계약을 비교한다. 실제 서비스 성공으로 주장하지 않는다.
- 2차: 동일 환경의 실제 읽기 전용 조회로 데이터와 카드 표시 완료를 확인한다. 주문 관련 정답은 계획/검증 경계에서 검사하며 실제 주문하지 않는다.
- A/B/C 실행 순서를 교차·무작위화하고 충분히 반복한다. cold와 warm, 기능별/공급자별 결과를 분리한다. 공급자 세션 구현 변경은 별도 변수로 고정한다.
- 실패·타임아웃도 분모와 지연 보고에 포함한다. 성공 요청만 남겨 빨라 보이게 하지 않는다. 완료 시간 분포와 timeout rate를 함께 보고한다.

## 7. 적용 판정과 중단 조건

| 항목 | 판정 기준 |
|---|---|
| 잘못된 직접 실행 | holdout에서 잘못된 기능·대상으로 실행 0건. 0건 관찰이 실제 오류율 0의 증명은 아님을 명시 |
| 권한·승인·계획 계약 | 우회/일회성 계획 재사용/추가 상태 변경 0건. 1건이라도 해당 경로 적용 중단 |
| 최종 정확도 | 기존 대비 새로운 미해결 회귀 0건. 비열등 한계는 전체 성공률 -1%p로 제안하며 짝지은 비교의 95% 신뢰구간으로 평가. 표본 부족이면 입증 부족으로 보류 |
| 후보 검색 | 후보 정답 포함률과 직접 연결 precision/coverage를 함께 보고. 전체 평균으로 특정 기능의 누락을 감추지 않음 |
| 지연 | 기준 측정 후 고정한 p50/p95 목표 충족. 주요 기능·공급자군의 p95가 10% 넘게 악화되면 해당 군 보류 |
| 실패 처리 | 동일 상태의 동일 실패 재탐색 0회. 새 증거가 없는 재시도 금지 |
| 실제 UI | 데이터 출처·종목·기간·단위·표/차트 의미 확인 및 표시 완료 신호와 화면 일치. visiblePaintAt만으로 hydration/차트 데이터 표시 완료를 인정하지 않음 |
| 되돌리기 | 기능별 flag 해제 후 원래 경로 복귀와 중복 실행 방지 검사 통과 |

## 8. 대안과 선택 이유

- **프롬프트만 줄이기:** 구현은 작지만 검증 정보가 빠져 재시도가 늘 수 있다. 보조 작업으로만 채택한다.
- **벡터 DB 전면 도입:** 표현 다양성에는 유리할 수 있으나 검색·재정렬 비용과 의미상 오선택 위험이 추가된다. 지금은 보류한다.
- **전체 결정적 라우팅:** 명확한 액션에는 유리하지만 자유로운 자연어와 문맥의 recall을 희생한다. allowlist 범위로 제한한다.
- **선택안 — 기존 레지스트리 + 묶음 조회 + 제한적 직접 연결:** 기존 계약을 유지하며 단계별 효과를 분리 측정하고 되돌릴 수 있다. 단점은 fallback 경로를 계속 유지·검증해야 한다는 것이다.

## 9. 작업 분담과 진행 순서

첫 착수 범위는 **0~2단계**로 고정한다. B군의 효과를 확인하기 전 C군과 저장소 교체를 한 번에 넣지 않는다. 1단계에서 지배적인 지연이 공급자 세션 준비나 기존 인식기 순서에 있고 묶음 정보는 이미 활용되고 있다면, 불필요한 계약 확장은 생략하고 그 측정 결과에 맞춰 최소 변경안을 먼저 비교한다.

- 구현 담당: 공통 selector 계약·묶음 조회·중복 처리. UI 표시 완료 계측은 파일 소유권을 분리할 수 있을 때 병렬 진행한다.
- 공급자 담당: Claude/Codex/Grok 어댑터의 계약 전달과 계측. 세션 최적화 자체는 별도 변경으로 유지한다.
- 평가 담당: 구현과 독립적으로 정답 세트·실험 runner·결과 판정.
- 검토 담당: 실행 경계·정확도 회귀·UI 의미 검토. 작성자가 같은 패스에서 자기 결과를 승인하지 않는다.

완료 시에는 코드 존재, 테스트 통과, 실제 연결 검증, 사용자 화면 확인을 구분해 보고한다. 이 문서는 계획 산출물이며 자동 실행·commit·push·배포 지시가 아니다.
