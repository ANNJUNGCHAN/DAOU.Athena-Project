# 알람 메인 카드 선택과 두 목적지

사용자 요청: 알람을 만들 때 채팅에서 관련 카드를 제안하고 사용자가 동의한 카드를 알람의 메인 카드로 저장한다. 알람 팝업에서는 대화창의 해당 카드 또는 해당 알람의 에이전트 화면으로 이동한다.

## 완료 조건

- 새 채팅 알람 초안은 검증된 조회 operation과 인자를 카드 후보로 제안한다. 모델은 카드 확인을 대신 실행할 수 없다.
- 카드 질문의 명시적 확인 버튼 또는 현재 대화의 유일한 대기 질문에 대한 긍정 답변만 선택을 확정한다. 후보 변경, 다른 대화, 여러 대기 질문에는 이전 동의가 적용되지 않는다.
- 후보와 확정 카드는 루틴에 영속화한다. 카드 확인은 알람 활성화와 별개이며, 후보가 있는 알람은 카드 확인 전에 활성화하지 않는다.
- 팝업은 `대화창에서 카드 보기`, `에이전트로 이동`, 닫기를 제공한다. 카드 미설정 알람은 임의의 카드를 대신 표시하지 않는다.
- 카드 목적지는 새 대화에서 저장된 operation을 다시 조회하고 정식 카드 하나만 표시한다. 기존 대화의 카드를 지우거나 다른 대화에 늦게 도착한 결과를 표시하지 않는다.
- 에이전트 목적지는 해당 루틴을 선택한다. 단순 닫기는 읽음 처리를 하지 않는다.

## 구현 경계

저장하는 것은 `main_card_candidate`와 사용자 확인 후의 `main_card` 및 확인 시각이다. 후보는 `{operation_ref, args, title}`이며 카드 정체성은 정식 operation/card registry로 검증한다. 일회용 실행 계획 토큰, 과거 시세 봉투, 주문 실행 operation은 저장 대상으로 허용하지 않는다.

기존 카드 없는 루틴은 그대로 불러온다. 새 MCP 초안은 후보를 요구하고, 모델 프롬프트에도 카드 제안 및 확인 단계를 명시한다. 카드 확인 API는 후보 일치 여부를 검사해 오래된 질문의 승인을 거절한다.

## 검증

1. 백엔드: 직렬화와 재시작, 후보/확정 분리, 이전 후보 확인 거부, 조회 operation 및 종목 검증, 기존 루틴 호환.
2. 메인 프로세스: 저장된 후보 외 임의 조회 차단, 선택 operation 단일 실행, 오류 처리, 대화 범위 검사.
3. 렌더러: 카드 동의/거절과 활성화 게이트, 두 목적지, 카드 미설정, 여러 알람, 대화 전환 중 응답 격리.
4. Electron: 넓은 창과 좁은 창의 팝업, 실제 버튼 동작과 한 카드 표시를 격리된 테스트 데이터로 검증.
5. 작성과 별개 검토자가 변경 및 검증 결과를 확인한다. 실서비스 데이터 검증이 불가능하면 그 범위를 구분해 보고한다.
