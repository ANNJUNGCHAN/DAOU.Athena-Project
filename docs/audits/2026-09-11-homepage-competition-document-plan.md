# 현재 Athena 홈페이지에 추가할 대회용 문서

2026-09-11 · 외부 고객용 AI 서비스 부문 · 홈페이지 직접 열람 기준

## 답부터: 기술 설명을 더 늘리기보다, 여섯 가지 증거 문서를 작성해야 한다

현재 홈페이지는 **무엇을 만들었고 어떻게 작동하는지**를 설명하는 구성이 갖춰져 있다. 만점을 목표로 보완해야 할 부분은 **고객이 왜 필요로 하는지, 얼마나 잘 해결하는지, 실제로 쓸 수 있는지, 어떻게 사업으로 이어지는지**의 근거다.

추천하는 문서는 다음 여섯 개다. 이는 공식 필수 제출 문서 여섯 개라는 뜻이 아니라, 공식 평가 항목을 빠짐없이 뒷받침하도록 묶은 작성 단위다. 문서만 작성하면 만점이 보장되는 것도 아니다. 관찰·측정·시연으로 채워야 하며, 없는 결과는 미검증으로 남겨야 한다.

| 우선순위 | 작성할 문서 | 홈페이지 공개 방식 | 가장 직접적으로 보강하는 점수 |
|---|---|---|---|
| P0 | **고객 문제와 사용 사례 보고서** | ‘사용 사례’에 익명 요약 공개 | 고객 가치·문제 정의: 서류 25 / 온라인 20 |
| P0 | **Athena 실측 성능·고객 효과 검증 보고서** | Tech와 연결되는 ‘검증 결과’ 공개 | 혁신성 25, 고객 가치, 본선 핵심 성과·완성도 35 |
| P0 | **실제 구동 시연과 구현 범위 명세서** | 실제 데모·지원 범위 공개 | 프로토타입: 서류 25 / 온라인 20 |
| P0 | **고객 확장·사업화 및 비용 계획서** | 고객에게 필요한 제공 방식만 공개, 상세는 심사용 | 시장성·사업화 25, 본선 파급력 25 |
| P1 | **외부 고객 운영·신뢰 문서** | ‘시작하기·지원 범위·데이터와 권한’ 공개 | 사업화 가능성, 본선 운영 지속성 10 |
| P0 | **15분 심사 발표자료와 증거 색인·Q&A** | 홈페이지와 별도 제출 | 온라인 발표 10, 본선 발표·Q&A 30 |

한 문서가 여러 항목의 증거로 쓰일 수 있다. 표에 반복된 배점을 합산해 총점으로 계산하면 안 된다. 본선은 예선과 달리 핵심 성과·완성도 35, 발표·Q&A 30, 파급력 25, 운영 지속성 10을 평가한다.

## 홈페이지를 보고 확인한 현재 상태

검토 대상은 현재 Edge에 열려 있던 [Athena 로컬 홈페이지](http://localhost:3001/)다. 공개 배포 사이트를 확인한 결과는 아니다. 메인, 기능 종합, Tech 목록과 세 기술 본문을 브라우저에서 확인했다. 여섯 기능 상세 페이지 전체와 다운로드 파일·앱 실제 실행은 이번 범위에 포함하지 않았다.

| 확인한 페이지 | 현재 제공하는 내용 | 추가로 연결하면 좋은 근거 |
|---|---|---|
| [메인](http://localhost:3001/) | 제품 방향, 여섯 모드의 소개·시연 요소, 세 기술 문서로 이동 | 고객 사례와 검증 결과로 바로 가는 진입점 |
| [기능 종합](http://localhost:3001/features) | 각 모드의 역할, 시작 순서, 다운로드 진입점 | 기능을 함께 사용하는 실제 고객 여정과 지원 범위 |
| [Tool Use](http://localhost:3001/tech/01-tool-selection) | 도구 검색·분류·검증과 API 호출 방식 | 정답 도구 선택률, 과업 성공률, 오류·응답 시간 실측 |
| [Agentic Memory](http://localhost:3001/tech/02-investment-memory) | 관심과 보유 사실 구분, 출처·명시성, 중복 대상 정리 | 잘못 저장된 사실·관계의 비율과 정정 효과, 기억 사용 전후 비교 |
| [RAG](http://localhost:3001/tech/03-graph-retrieval) | 대상 식별, 관계·원문 근거 조회, 군집화 | 근거 회수·정확성, 대상 혼동, 일반 기록 검색 대비 결과 |

특히 기능 페이지의 시작 안내는 **CLI 계정 연결 → 키움 앱키·시크릿 키 등록**을 요구하고, **현재는 모의계좌만 지원**한다고 안내한다. 시작 과정 애니메이션은 입력값과 연결 상태가 시연용이라고 명시한다. 따라서 홈페이지의 시연 화면 존재를 실제 설치·인증·실거래 검증 결과로 확대할 수 없다. 이 차이를 문서로 명확하게 보여주는 것이 시제품의 신뢰도를 높인다.

현재 확인한 주요 탐색 경로는 기능과 Tech 중심이다. 아래 문서가 사이트의 다른 비공개 경로나 외부 자료에 이미 있다면 새로 중복 작성하기보다 홈페이지와 심사 자료에서 연결하면 된다.

## 1. 고객 문제와 사용 사례 보고서

**추천 제목: 「투자자는 어디에서 흐름을 잃는가 — Athena 고객 문제와 사용 사례」**

이 문서가 답할 질문은 ‘그런 기능을 만들 수 있다는 것은 알겠는데, 누구에게 왜 필요한가?’다. 현재의 ‘투자의 시야’, ‘경험이 쌓이는 지능’ 같은 제품 방향을 실제 고객의 상황으로 설명한다.

권장 분량: 본문 3~5쪽과 익명 원자료 부록. 최소 목차:

1. 첫 목표 고객: 투자 경험, 사용 도구, 반복 과업, 이 집단을 선택한 이유.
2. 실제 불편: 정보를 찾고 판단을 기록하고 다시 확인하는 과정에서 발생한 사례와 고객 발언.
3. 기존 방식: 고객이 현재 어떤 화면·메모·도구로 해결하는지.
4. Athena 사용 과정: 기능 이름 대신 고객의 시작 상황과 원하는 결과를 중심으로 기술.
5. 관찰 결과: 완료 여부, 걸린 시간, 도움 요청, 다시 쓰려는 이유와 쓰지 않으려는 이유.
6. 조사 한계: 참가자 수·선정 기준·날짜·관찰 기간과 미확인 가설.

**완료 조건:** 주장마다 인터뷰나 관찰 기록이 연결돼야 한다. 개발자 내부 사용만 했다면 외부 고객 검증으로 표기하지 않는다. 참가자의 신원과 민감한 투자 정보는 공개 요약에서 제거한다.

홈페이지에는 사례 하나를 ‘사용 전 → Athena에서 한 일 → 관찰된 변화’로 짧게 보여주고 원문 보고서를 연결한다. 측정 전에는 가상 수치가 들어간 성공 사례를 만들지 않는다.

## 2. Athena 실측 성능·고객 효과 검증 보고서

**추천 제목: 「Athena는 같은 투자 과업을 얼마나 잘 해결하는가 — 비교 실험과 한계」**

세 기술 문서는 작동 원리를 설명한다. 추가 문서는 그 기술이 실제 효과를 내는지 보여줘야 한다. 참고 논문의 성능 수치를 Athena 성능으로 사용하면 안 된다.

권장 분량: 요약 2쪽, 방법·결과 3~5쪽, 익명 과업별 원자료 별첨.

| 실험 | 동일하게 맞출 조건 | 보고할 지표 |
|---|---|---|
| 기존 사용자 방식과 Athena | 과업, 조회 기준 시점, 필요한 결과 | 완료율, 소요 시간, 화면 전환, 도움 요청 |
| 개인 기억 사용과 미사용 | 모델, 도구, 데이터, 질문 | 과거 판단 재탐색 성공률, 누락·잘못 연결 비율 |
| 일반 대화 기록 검색과 그래프 조회 | 같은 기록과 정답·근거 기준 | 근거 정확성, 대상 식별 실패, 필요한 근거 회수 |
| 실제 요청의 자원 사용 | 실행 환경과 제공자 조건 명시 | 호출·재시도, 토큰 또는 제공자 사용량, 비용, 지연 |

필수 기록은 과업 정의, 정답 판정 기준, 표본 수, 실행 날짜·버전, 전체 시도와 실패, 평균뿐 아니라 분포, 비용의 실측/추정 구분이다. 작은 테스트로 전체 투자자의 효과나 모든 요청의 정확성을 단정하지 않는다.

**완료 조건:** 다른 사람이 같은 입력과 조건으로 결과를 확인할 수 있고, 실패 사례가 빠지지 않아야 한다. 데이터가 없다면 먼저 측정 계획으로 작성하고 결과 보고서와 구분한다.

홈페이지에는 핵심 결과를 표본 수·측정일·조건과 함께 요약하고, 각 Tech 문서 마지막에 해당 실험을 연결한다. 새 기술 소개 글을 늘리는 것보다 이 연결의 우선순위가 높다.

## 3. 실제 구동 시연과 구현 범위 명세서

**추천 제목: 「질문에서 기억과 알림까지 — Athena 실제 구동과 현재 지원 범위」**

고객 한 명이 하나의 과업을 끝내는 흐름을 실제 앱으로 보여준다. 홈페이지의 모드별 설명과 별도로 기능들이 연결되는 증거가 필요하다.

권장 구성: 3~5분 실제 구동 영상, 2~3쪽 설명, 기능별 지원 표.

- 대표 여정: 질문 → 출처 있는 결과 → 해당 결과 후속 질문 → 기억 확인·정정 → 지원되는 감시 설정 → 이벤트 알림 → 원래 근거로 복귀.
- 단계별 증거: 입력, 예상 결과, 실제 결과, 시각, 앱 빌드, 사용 데이터·계정 환경.
- 지원 범위: 현재 동작 / 조건부 동작 / 모의 환경 제한 / 개발 예정.
- 실패 복구: 연결 실패·데이터 없음·지원하지 않는 요청·재실행·세션 복귀.
- 데모 구분: 실제 앱 녹화 / 설명용 애니메이션 / 녹화 또는 재생 데이터.

**완료 조건:** 기능 소개 문장마다 현재 구동 증거나 명시된 제한이 있어야 한다. 연결되지 않은 단계는 완성된 흐름으로 연출하지 않는다. 모의계좌 지원을 실거래 지원으로 표현하지 않는다. 주문은 초안·사용자 실행·접수 결과를 구분한다.

현재 홈페이지 시작 애니메이션은 시연용임을 이미 밝히고 있다. 이를 유지하고 실제 설치부터 첫 결과까지의 별도 영상과 테스트 결과를 추가하는 방식이 적합하다.

## 4. 고객 확장·사업화 및 비용 계획서

**추천 제목: 「Athena의 첫 고객과 확장 경로 — 제공 방식·원가·사업 가설」**

이 문서가 시장성·사업화 25점에 직접 답한다. 공식 기준은 매출만이 아니라 고객 확장 가능성도 평가하므로, 아직 유료 가격을 정하지 않았다면 임의 가격표를 만드는 대신 고객 확장 가설과 검증 계획을 제시한다.

권장 분량: 3~5쪽. 목차:

1. 첫 고객 집단과 도달 가능한 유입 경로.
2. 설치·연결을 마치고 첫 가치를 경험하게 하는 방법.
3. 반복 사용의 이유와 활성화·재방문 지표 정의.
4. 고객 직접 계정 이용형 또는 서비스 제공자 부담형 등 우선 제공 방식과 비용 부담.
5. 과업당·사용자당 모델·데이터·서버·지원 비용, 사용량 증가 시나리오.
6. 다음 서비스·계열사 적용 경로, 재사용할 부분, 추가 연결·운영 비용.
7. 근거가 있는 내용, 검증 중 가설, 다음 의사결정 조건.

**완료 조건:** 고객 유입→첫 사용→반복 사용→비용 부담이 하나의 설명으로 이어져야 한다. 제휴·도입·시장 규모·지불 의향은 확인한 범위만 쓴다. CLI·데이터 계정의 사용 조건과 외부 고객 제공 가능 범위는 실제 계약 및 담당 조직의 검토 상태를 기록한다.

홈페이지에는 지원 대상, 필요한 계정, 현재 제공 범위와 체험 경로를 공개한다. 내부 원가·미확정 제휴·민감한 사업 계획은 심사용 자료로 관리한다.

## 5. 외부 고객 운영·신뢰 문서

**추천 제목: 「Athena 시작하기와 신뢰 안내 — 데이터·권한·오류·지원」**

개발자용 운영 기록을 외부 고객이 이해하는 내용으로 바꾼다. 현재 시작 안내를 확장하는 문서이므로 별도의 중복 설치 가이드를 만들 필요는 없다.

공개 안내와 내부 운영 부록으로 구성한다.

| 공개 안내 | 내부 운영·검토 부록 |
|---|---|
| 지원 OS·계정·설치 및 로그인 순서 | 깨끗한 PC에서의 첫 사용 검증 결과 |
| 어떤 데이터가 어디로 전달되는지 | 제공자별 데이터 흐름과 계약 검토 상태 |
| 기억 확인·정정·삭제 및 권한 철회 방법 | 보존·삭제 정책과 실제 삭제 검증 |
| 데이터 지연·결측·연결 오류 시 행동 | 장애 감지·대응·복구·지원 담당자 |
| 사용량·비용 부담·지원 한계 | 사용량 제한, 원가 관측, 제공자 장애 대응 |
| 정보 제공·판단 지원·주문 실행의 구분 | 보안·개인정보·준법 검토 담당자와 미완료 항목 |

**완료 조건:** 계정과 키를 가진 첫 사용자도 안내만 보고 첫 유효 결과에 도달하고, 실패 시 다음 행동을 알 수 있어야 한다. 원문 키·계좌·개인정보를 예시나 로그에 공개하지 않는다. 법률 문구를 임의로 확정하기보다 관련 검토 상태를 표시한다.

## 6. 15분 심사 발표자료와 증거 색인·Q&A

**추천 제목: 「Athena 외부 고객용 AI 서비스 — 고객 가치와 구현 증거」**

홈페이지와 별개로 제출해야 하는 발표자료다. 고객 사례·기술·데모가 사이트에 흩어져 있어도 심사자가 15분 안에 평가 항목별 답을 찾을 수 있어야 한다.

권장 구성: 12~15장 내외의 PPT/PDF, 15분 대본, Q&A, 증거 색인. 장수는 자체 제안이며 공식 제한이 아니다.

내용 순서는 고객 문제→대표 시연→AI 차별성과 비교 결과→고객 효과→사업화→운영·확산→완료 범위로 잡는다. 슬라이드마다 근거 문서·영상 시점·측정 날짜를 연결한다. 외부/내부 심사위원 각 40%, 심사 AI 20%가 읽기 쉽게 주장과 증거를 명시하되 심사 AI를 조작하려는 지시문을 넣지 않는다.

Q&A에는 일반 챗봇과의 차이, 재사용 이유, 기억 오류 정정, CLI 등록 부담, 모의계좌 제한, 비용 부담, 데이터 이용 범위, 실제 구현과 계획, 다른 계열사 확장 비용을 포함한다.

신청서 기본 정보, 팀 역할, 2026년 착수 근거, AI·오픈소스·외부 API 사용 목록, 마스킹한 실제 데모도 이 묶음에서 관리한다. 공식 필수 제출물은 신청서·15분 분량 발표자료·데모 자료이며, 홈페이지 단독으로 대체할 수 있다고 해석하지 않는다.

이 묶음의 별도 산출물로 **신청서 입력 원고·완성본과 제출 체크리스트**를 작성한다. 신청서, 발표 파일, 데모 각각에 대해 작성 완료·파일/링크 접근 확인·실제 제출 여부를 구분한다. 아직 접수하지 않았다면 제출 완료로 표시하지 않는다.

증거 색인에는 다음 **100점 평가항목-증거 매트릭스**를 필수로 넣는다. 아래는 앞으로 작성할 증거의 배정이며 충족 판정이 아니다. 제출본 작성 때 각 행에 실제 문서 쪽수·영상 시점·실험 기록 ID와 미확인 사항을 기입해야 한다.

## 홈페이지에 배치할 방법과 오늘 작성 순서

현재 ‘기능 / Tech’ 구조는 유지하고, **사용 사례 / 검증 결과 / 시작하기·신뢰 안내**를 추가하는 구성이 적합하다. 아래는 신규 제안이며 실제로 생성된 페이지가 아니다.

- 메인: 대표 고객 사례 1개와 실제 검증 결과를 요약해 연결한다.
- 기능 종합: 실제 연결 시연과 지원 범위를 연결한다.
- Tech 세 본문: 대응하는 실험 방법·결과·한계를 연결한다.
- 시작하기: CLI·모의계좌 조건, 첫 사용 가이드, 오류 도움말을 확장한다.
- 심사용 별도 묶음: 사업화 상세, 증거 색인, 발표자료·Q&A를 관리한다.

첨부 대회 문서 기준으로 **오늘 9월 11일이 접수 마감일**이다. 마감 시각과 변경 여부는 이번 조사에서 확인하지 않았다. 마감 후 자료 교체와 추가 제출이 제한되므로 큰 문서를 모두 완성한 다음 발표자료를 만드는 순서는 피한다.

**오늘은 6번 제출 덱의 골격을 먼저 만들고, 1번 고객 관찰·2번 최소 비교 실측·3번 실제 데모·4번 사업화 가설을 병행해 그 안에 넣는 순서가 적합하다.** 5번은 현재 지원 범위·비용 부담·데이터와 권한·미완료 검토 상태의 최소 안내를 포함한다. 실제 결과가 없는 항목은 미측정 또는 계획으로 표시하며, 측정하지 않은 효율·정확도·고객 수를 채워 넣지 않는다.

이번 결과는 추가 문서의 작성 명세다. 여섯 증거 문서를 실제 완성하거나 홈페이지를 수정·공개한 결과는 아니다. 문서량 자체가 아니라, 각 점수 항목에 확인 가능한 근거가 붙는 것이 완료 조건이다.
