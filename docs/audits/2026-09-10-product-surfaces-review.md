## 1. 이번 보고서의 결론

제품 소개의 단위는 **“어떤 데이터를 제공하나”보다 “이 창에서 사용자가 무엇을 하고, 다음 행동으로 어떻게 이어지나”**여야 한다. 차트·시세·수급을 나열하면 아고라의 대화 경험이 사라진다. 그래프를 관계 분석 하나로 묶으면 요약창·군집 지도·선택 노드 패널의 차이가 사라진다. 아이기스도 자동화라는 한 단어보다 작업·알람·실행 결과·제안창의 역할을 각각 보여주는 편이 맞다.

이번에는 코드 모듈의 존재를 곧바로 제품 기능으로 취급하지 않고, **화면 계획 → 현재 UI → 클릭/대화의 실제 처리 경로 → 소개 문구** 순서로 대조했다. 각 메인은 큰 이미지 하나로 설명할 수 있는 작업 경험이고, 서브는 그 경험을 깊게 만드는 구체적인 조작이다.

| 제품 | 메인 수 | 서브 수 | 소개의 중심 |
|---|---:|---:|---|
| 아고라 | 3 | 3 | 말로 창을 열고, 결과를 두고 묻고, 주문을 검토한다 |
| 메티스 | 4 | 5 | 요약 → 기본 군집 → 선택 노드와 대화 → 확인·정정 |
| 아이기스 | 4 | 3 | 작업 → 알람 → 실행 결과 → 성향 기반 제안 |
| 에르가네 | 3 | 5 | 도구를 발견하고, 기능을 허용하고, 변경을 관리한다 |
| 팔라스 | 5 | 3 | 기법 → 편집 → 노드 대화 → 실행 결과 → 개선 |
| 글로우 | 4 | 5 | 축소 상태 → 알림 → 작은 대화 → 미니 결과 |
| 합계 | 23 | 24 | 서브는 모두 홀수 · 아고라는 최신 지정에 따라 메인/서브 각 3개 |

**이 표는 추천 편성안이다.** 아고라의 범용 “이 창에 질문하기”와 아이기스 라이브 진행률처럼 보강이 필요한 부분까지 전부 구현됐다는 뜻은 아니다. 아래에서 현행과 제안을 분리한다.

### 이전 원고에서 바꾼 판단

1. 아고라의 메인을 금융 데이터 종류별로 나누지 않는다. 창 호출·창을 대상으로 한 대화·주문 대화가 중심이다.
2. 메티스는 요약창·군집 지도·선택 노드 대화·확인 카드를 따로 설명하고, 군집 펼침 계획의 현재 연결 여부도 구별한다.
3. 아이기스의 대표 기능에서 **“나만의 조건을 코드로 감시”를 제거한다.** 사용자의 최신 제품 구분에 따라 직접 코드를 작성하고 검증하는 경험은 팔라스에서 설명한다.
4. 서브는 3개 또는 5개만 사용한다. 아고라는 최신 사용자 지정에 따라 메인/서브를 각 3개로 두고, 나머지 페이지는 메인과 서브 수를 다르게 한다.
5. 코드나 과거 Paper에서 찾은 기능이라도 현재 제품 구분과 다르면 그대로 홍보하지 않는다.

## 2. 조사한 자료와 판정 방법

### 코드와 Paper의 서로 다른 역할

- **현재 코드:** `app/shell.html`, `chat.js`, `canvas.js`, `main.js`, `orb.js`, 모드별 `app/lib`와 연결되는 API/MCP·서비스를 추적했다. UI가 무엇을 전달하고 어느 핸들러가 처리하는지 확인했다.
- **저장소의 Paper 화면 원장:** `backend/ref/paper-ledger/manifest.json`의 전체 450개 항목을 역할·페이지별로 분류했다. 현재 목록은 screen 86, card_template 101, mini_card 192, mini_template 11, card_spec 8, contract 14, record 17, reference 11, retired 10이다. 원장을 전수 분류한 것과 모든 보드를 실앱에서 실행 검증한 것은 구별한다.
- **화면 계획과 운영 문서:** `.omc/state/paper-screens.md`, `PAPER_APP_PARITY.md`, `docs/ui/paper-19-window-ui-inventory.md`, `docs/ui/paper-6-integrated-card-inventory.md`, `docs/handoff/agent-dual-control/` 및 모드별 화면 원장을 대조했다.
- **현재 Paper 직접 확인:** 연결된 Athena 파일의 페이지 구성과 에이전트 13개 보드 목록을 읽었다. 그래프 요약·선택 노드 패널, 에이전트 알람 센터·라이브 관제·프로액티브의 실제 디자인 스크린샷을 확인했다. 여기에 표시된 금액·건수·진행률은 디자인 예시이며 운영 수치가 아니다.
- **전수 검토의 경계:** 여섯 제품과 공통 화면을 빠짐없이 분류하고 주요 사용자 경로를 확인한 정적 조사다. 모든 소스 줄 정독, 모든 API 실행, 모든 Paper 보드의 시각 대조를 완료했다는 주장은 하지 않는다. 제품 코드·Paper는 수정하지 않았다.

### 상태 표기

| 표기 | 의미 |
|---|---|
| 코드 연결 | 화면과 실제 이벤트/서비스 경로가 있다. 현재 외부 계정·피드에서 성공했다는 뜻은 아니다. |
| 일부 연결 | 핵심 일부가 제한돼 있거나 화면의 일부가 샘플이다. 제한을 함께 읽어야 한다. |
| 디자인 계획 | Paper에 보이지만 대응 경로를 이번 조사에서 입증하지 못했다. |

| 제품 구분 조정 | 코드/Paper의 기존 배치와 최신 사용자 지정이 다르다. 최신 지정으로 원고를 구성한다. |

**자료 간 차이도 발견했다.** 과거 대응표의 “444개 보드”와 현재 저장 원장의 450개 항목은 다르다. 현재 Paper에는 백테스트 백업 페이지가 있고 저장 원장에는 과거 구현 현황 페이지가 있다. 따라서 과거 대응표의 적용·미구현 판정을 현재 결과로 복사하지 않는다.

### 추천 메인 3개

| 메인 | 페이지 제목·본문 | 이미지 장면 | 현행/목표 구분 |

Q2는 사용자가 제시한 아고라의 핵심 방향이므로 원고에서 없애지 않는다. 대신 **제품의 중심 기능으로 완성할 구현 과제**로 명확히 둔다. 이 기능이 일반화되면 차트·호가를 갖췄다는 설명보다 아고라의 정체성을 훨씬 잘 보여준다.

### 계획과 최신 제품 구분이 충돌하는 부분

현재 Paper의 에이전트 페이지와 코드에는 「새 알람 — AI가 감시 함수를 만든다」「알람 노드·흐름」「활성 코드 알람」이 남아 있다. 이는 이번에 직접 읽은 보드 목록과 현재 `agent-canvas.js`에서 확인한 사실이다. 그러나 **이번 사용자의 지시에서는 직접 코드를 다루는 조건 작성 경험을 팔라스로 구분했다.**

따라서 이번 제품 원고는 최신 지시를 따른다. 아이기스에는 이 항목을 넣지 않고, 팔라스에서 기법 코드·노드·검증 경험을 설명한다. 코드 경로와 Paper 보드를 실제로 옮기거나 제거하는 작업은 별도 구현 범위이며, 이 보고서만으로 이동을 완료했다고 주장하지 않는다.

## 10. 구현 아이디어의 우선순위

우선순위는 새 기능의 수보다 **현재 제품의 고유한 화면 경험을 얼마나 명확하게 만드는가**로 정했다.

1. **아고라: 이 창에 질문하기.** 사용자가 가장 먼저 제시한 차별점이며, 메티스·팔라스에 이미 있는 선택 대상 대화를 일반 금융 결과로 확장하는 방향이다. 카드 헤더의 질문 동작, 참조 칩, 조회시점·선택값 전달, 답변의 대상 표시를 한 묶음으로 구현한다.
2. **아이기스: 라이브 관제의 실제 데이터 연결.** Paper가 표현하는 현재 진행과 향후 일정은 매력적이지만 샘플을 그대로 홍보할 수 없다. 실제 작업 상태·다음 발화·연결 장애를 붙여 화면의 약속을 완성한다.
3. **아고라: 여러 창 비교와 대화형 화면 수정.** 카드 참조가 준비된 다음 두 창 비교, 특정 행·구간 질문, 기존 창의 지원 설정 변경으로 확장한다. 한 번에 모든 자유형 요청을 지원하려 하지 말고 대상과 변경 결과가 확인되는 것부터 만든다.
4. **에르가네: 질문에 필요한 도구 후보와 권한 비교.** 추천 마켓 화면을 실제 설치 후보·연결 가능 조건·필요 권한에 연결한다. 설치 제안과 허용·적용은 계속 구별한다.
5. **글로우: 명시적인 대화 넘기기.** “이 대화를 큰 화면으로” 동작이 선택한 글로우 세션과 결과를 실제로 열도록 만든다. 현재의 창 전면 표시와 다른 신규 기능이다.

메티스와 팔라스는 **이미 있는 선택 → 대상 대화 → 근거/코드 확인 → 변경 검토**를 정확한 장면으로 보여주는 것이 우선이다. 메티스의 군집 펼침을 별도 주요 화면으로 유지하려면 앞서 확인한 진입 경로의 공백도 함께 해결해야 한다.

### 실제 소개 페이지로 옮기는 방법

- 큰 이미지마다 하나의 질문과 그 질문으로 열린 창 또는 바뀐 상태를 보여준다. 관련 없는 창 여러 개를 합쳐 실제로 동시에 가능한 화면처럼 만들지 않는다.
- 메티스는 요약·기본 지도·선택 노드·확인 카드를 다른 컷으로 구성한다. 선택 노드와 그 노드에 관한 채팅은 같은 컷에 담는다. 군집 펼침 컷은 진입 동작 연결 후 추가한다.
- 아이기스는 작업 목록·알람·실행 결과·제안의 네 이미지를 사용한다. 라이브 샘플 진행률은 현재 기능을 증명하는 이미지에서 제외한다.
- 팔라스는 편집기와 노드를 별도 이미지로 사용한다. 노드 이미지는 참조 칩과 질문까지 보여줘야 단순 그래프와 다른 기능이 드러난다.
- 글로우는 접힌 모습·알림·대화·미니 결과의 크기와 정보 밀도 차이를 보여준다.
- 메인과 서브를 같은 문구로 반복하지 않는다. 메인은 창의 역할, 서브는 첨부·중단·필터·제안 확인·빈도 조절 같은 구체적 조작으로 쓴다.

## 12. 검증 범위

제품 코드와 Paper는 읽기만 했다. 보고서는 현재 코드 경로·Paper 계획·사용자의 최신 제품 구분을 대조한 결과다. 실제 계정·시세·주문·외부 플러그인의 실기 검증은 수행하지 않았다. 특히 금융 데이터를 꾸며 이미지 소재로 사용하거나 검증을 위해 주문을 실행하지 않았다.

작성 뒤 별도 검토자가 화면 소유권, 디자인 계획과 구현의 혼동, 범용 카드 질의 주장, 라이브 샘플을 점검했다. 메티스 군집 펼침의 진입 경로 부재를 반영한 뒤 정적 보고서 검토를 통과했고, 52개 로컬 근거 링크의 존재를 확인했다.

후속 사용자 요청에 따라 아고라 서브 원고를 파일·폴더 자료, 목표·계획 모드, 모델·사고 정도의 3개로 개정했다. 이 문구 개정에 따른 추가 구현 검증은 수행하지 않았다. 현재 6페이지 모두 메인은 2~5개, 서브는 3개 또는 5개이며, 아고라는 메인/서브 각 3개, 나머지 페이지는 메인/서브 수가 다르다. 합계는 메인 23개·서브 24개다. 이 보고서는 이전 기능 목록식 원고를 대체하는 제품 기획 기준이다.
