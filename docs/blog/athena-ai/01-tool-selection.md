## 1. “삼성전자 차트 보여줘”가 화면이 되기까지

사용자는 한 문장만 말합니다. 하지만 ATHENA는 종목, 기간, 계좌 필요 여부를 확인하고 알맞은 API를 골라야 합니다.
ATHENA는 질문을 곧바로 차트로 바꾸지 않습니다. **Tool Use / Function Calling** 구조 안에서 명확한 요청은 규칙으로 처리하고, 후보가 모호할 때만 LLM이 도구와 인자를 분류합니다. 이어서 사용할 수 있는 도구인지 확인한 뒤, 사용자가 원하는 값을을 화면에 그립니다.

## 2. 이름이 비슷해도 조건이 다르면 고르지 않습니다

도구가 많아지면 LLM에 모든 API 설명을 한꺼번에 주기 어렵습니다. [ToolRerank](https://aclanthology.org/2024.lrec-main.1413/)는 이 문제를 검색과 재정렬의 두 단계로 나눕니다.

![ToolRerank의 전체 후보 검색·재정렬 구조](C:/Projects/DAOU.Athena/docs/blog/athena-ai/assets/toolrerank-figure-2-original.png)

*Zheng et al., 2024, 「ToolRerank」, Figure 2, p. 16265(PDF 3쪽) 원본 크롭 · © 2024 ELRA Language Resource Association · [CC BY-NC 4.0](https://creativecommons.org/licenses/by-nc/4.0/) · [논문 원문](https://aclanthology.org/2024.lrec-main.1413/)*

먼저 **Dual Encoder**가 질문과 API 설명을 벡터로 바꿔 넓게 후보를 찾습니다. **Adaptive Truncation**은 학습에서 본 도구와 처음 보는 도구에 서로 다른 후보 범위를 적용합니다. 이어 **Cross Encoder**가 질문과 각 API를 함께 읽어 관련성을 다시 계산합니다. 마지막으로 **Hierarchy-aware Reranking**이 단일 도구 질문에는 한 도구의 API를 집중시키고, 복수 도구 질문에는 서로 다른 기능을 남겨 상위 *k*개를 LLM에 전달합니다.

도구 선택 과정을 설명하기 위해 ToolRerank의 후보 검색·재정렬 구조를 참고했습니다. ATHENA는 학습된 재정렬 모델 대신 **어휘 기반 후보 검색, 요청 유형 검사, Schema Validation, 제한된 LLM 분류**로 이 과정을 구체화합니다. 예를 들어 ‘차트’, ‘주가 흐름’, ‘일봉’처럼 가까운 표현에 점수를 주고, API 호출 조건이 부족한 후보는 실행 대상으로 인정하지 않습니다.

![단어 점수와 조건 검사를 거치는 후보 선택](C:/Projects/DAOU.Athena/docs/blog/athena-ai/assets/beginner-02.svg)


## 3. 후보를 하나로 좁히기 어려우면 두 분류기를 병렬 실행합니다

규칙만으로 결정하기 어려우면 같은 질문을 두 분류기가 함께 봅니다. 각 분류기는 최대 3개 후보 안에서 답하고, 형식 검사까지 먼저 통과한 결과 하나만 채택합니다. 동시에 실행되는 분류 작업은 전체 4개를 넘지 않습니다. 이를 **First-valid Hedging**[^1]과 **Bounded Parallelism**[^2]이라고 설명할 수 있습니다. 이후, **Decision Cache**[^4]로 반복되는 도구 선택 판단을 재사용합니다.

선택이 끝나면 서버가 실제 가격 배열을 받아 차트를 만듭니다. 언어 모델이 가격 숫자를 새로 쓰지는 않습니다.

![두 분류기와 서버 차트 생성 흐름](C:/Projects/DAOU.Athena/docs/blog/athena-ai/assets/beginner-03.svg)


## 4. 먼저 검증된 답을 선택하고, API는 한 번만 호출합니다

이를 통해 ATHENA는 한 분류기의 응답이 늦어 전체 도구 선택이 함께 지연되는 문제를, **두 결과를 제한적으로 경쟁시키고 먼저 형식 검사를 통과한 하나만 채택하는 방식**으로 해결했습니다. 후보 밖의 도구나 잘못된 인자 형식은 먼저 도착해도 거절하며, 실제 API 호출은 한 번만 보냅니다. 동시에 실행할 분류 작업의 전체 수를 제한하고 반복 판단은 캐시에서 재사용해, 병렬 호출이 계속 늘어나는 문제도 함께 제어합니다.

[^1]: **First-valid Hedging**은 같은 질문을 두 분류기에 보내고, 단순히 먼저 도착한 답이 아니라 **후보·인자·스키마 검사를 먼저 통과한 답**을 채택하는 방식입니다. 각 분류기는 최대 3개 후보 안에서 답하며, 채택된 결과에 해당하는 실제 API만 한 번 호출합니다.

[^2]: **Bounded Parallelism**은 병렬 작업이 무한히 늘지 않도록 상한을 두는 방식입니다. ATHENA는 한 번의 도구 선택에서 분류기 두 개를 사용하고, 전체에서 동시에 실행되는 분류 작업을 최대 4개로 제한합니다. 여러 사용자의 요청이 겹쳐도 분류 요청 수가 계속 증가해 시스템을 압박하지 않도록 하는 장치입니다.

[^3]: **Self-consistency**는 하나의 문제에 대해 서로 다른 추론 경로를 여러 번 생성한 뒤, 답을 집계해 가장 일관된 결과를 고르는 기법입니다. 예를 들어 같은 계산 문제를 여러 방식으로 풀게 한 뒤 가장 자주 나온 답을 선택합니다. ATHENA는 두 분류 결과를 다수결로 모으거나 추론을 합치지 않고, 먼저 검증을 통과한 결과 하나를 사용하므로 이 기법을 적용한 구조가 아닙니다. 자세한 방법은 [Wang et al., 2022](https://arxiv.org/abs/2203.11171)에서 확인할 수 있습니다.

[^4]: **Decision Cache**는 정규화한 사용자 질문과 도구 선택 판단을 짧은 기간 재사용하는 캐시입니다. 같은 요청이 반복되면 분류기를 다시 호출하지 않고 이전 선택 결과를 사용해 불필요한 판단 비용을 줄입니다. 캐시는 TTL이 지나면 만료되고, 저장 한도를 넘으면 먼저 들어온 항목부터 제거됩니다.
