01 · Tool Use

한 문장이 차트가 되기까지

사용자는 “삼성전자 차트 보여줘”라고 말합니다. Tool Use / Function Calling 구조 안에서 명확한 요청은 규칙으로 처리하고, 후보가 모호할 때만 LLM이 도구와 인자를 분류합니다. 제공자가 돌려준 값은 서버가 화면에 그립니다.

02 · Tool Routing

검색하고, 다시 읽고, 필요한 도구만 남깁니다

도구가 많아지면 LLM에 모든 API 설명을 한꺼번에 주기 어렵습니다. ToolRerank는 이 문제를 후보 검색과 정밀한 재정렬의 두 단계로 나눕니다.

Zheng et al., 2024, ToolRerank, Figure 2, p. 16265(PDF 3쪽) 원본 크롭 · © 2024 ELRA Language Resource Association · CC BY-NC 4.0 · 논문 원문

먼저 Dual Encoder가 질문과 API 설명을 벡터로 바꿔 후보를 찾습니다. Adaptive Truncation은 학습에서 본 도구와 처음 보는 도구의 후보 범위를 다르게 잡습니다. 이어 Cross Encoder가 질문과 API를 함께 읽어 점수를 다시 계산합니다. 마지막으로 Hierarchy-aware Reranking이 단일 도구 질문에는 한 도구의 API를 집중시키고, 복수 도구 질문에는 서로 다른 기능을 남겨 상위 k개를 LLM에 전달합니다.

도구 선택 과정을 설명하기 위해 ToolRerank의 후보 검색·재정렬 구조를 참고했습니다. ATHENA는 학습된 재정렬 모델 대신 어휘 기반 후보 검색, 요청 유형 검사, Schema Validation, 제한된 LLM 분류로 이 과정을 구체화합니다. API 호출 조건이 부족한 후보는 실행 대상으로 인정하지 않습니다.

03 · First-valid Hedging

후보를 하나로 좁히기 어려우면 두 분류기를 병렬 실행합니다

두 분류기가 최대 3개 후보를 함께 보고 형식 검사를 먼저 통과한 결과 하나를 채택합니다. 이는 다수결이 아닌 First-valid Hedging[1]이며, Bounded Parallelism[2]으로 동시 실행 수를 제한합니다. 이후, Decision Cache[4]로 반복되는 도구 선택 판단을 재사용합니다.

04 · 해결한 문제

먼저 검증된 답을 선택하고, API는 한 번만 호출합니다

이를 통해 ATHENA는 한 분류기의 응답이 늦어 전체 도구 선택이 함께 지연되는 문제를, 두 결과를 제한적으로 경쟁시키고 먼저 형식 검사를 통과한 하나만 채택하는 방식으로 해결했습니다. 후보 밖의 도구나 잘못된 인자 형식은 먼저 도착해도 거절하며 실제 API 호출은 한 번만 보냅니다. 전체 동시 분류 수를 제한하고 반복 판단은 캐시에서 재사용해 병렬 호출이 계속 늘어나는 문제도 제어합니다.

기술 용어 자세히 보기

[1] First-valid Hedging은 같은 질문을 두 분류기에 보내고, 단순히 먼저 도착한 답이 아니라 후보·인자·스키마 검사를 먼저 통과한 답을 채택합니다. 각 분류기는 최대 3개 후보 안에서 답하며 실제 API는 한 번만 호출합니다.

[2] Bounded Parallelism은 병렬 작업 수에 상한을 두는 방식입니다. 한 번의 도구 선택에는 분류기 두 개를 사용하고, 전체 동시 분류 작업은 최대 4개로 제한합니다. 요청이 겹쳐도 분류 작업이 계속 늘어나는 상황을 막습니다.

[3] Self-consistency는 서로 다른 추론 경로를 여러 번 만든 뒤 답을 집계해 가장 일관된 결과를 고르는 기법입니다. ATHENA는 두 결과를 다수결로 모으지 않고 먼저 검증된 하나를 사용하므로 이 기법을 적용한 구조가 아닙니다. 자세한 방법은 Wang et al., 2022에서 확인할 수 있습니다.

[4] Decision Cache는 정규화한 질문과 도구 선택 판단을 짧은 기간 재사용합니다. 같은 요청이 반복되면 이전 판단을 사용하고, TTL이 지나면 만료되며 저장 한도를 넘으면 먼저 들어온 항목부터 제거합니다.

01 · Agentic Memory

“배당주가 궁금해요”는 보유 사실이 아닙니다

‘삼성전자 배당이 궁금하다’는 관심 표현이고, ‘삼성전자 10주를 보유하고 있다’는 투자 사실입니다. ATHENA는 Agentic Memory[1]를 지식 그래프로 구성해 사람·종목·관심사를 노드로, 그 사이의 의미를 관계로 저장합니다. 대화에서 읽은 관심과 계좌에서 확인한 보유 정보를 처음부터 서로 다른 기억으로 다룹니다.

02 · Structured Extraction

같은 관계에도 출처와 명시성을 따로 기록합니다

대화는 LLM이 정해진 JSON 형식으로 개체와 관계를 뽑는 Structured Extraction[2]을 거칩니다. 체결·보유 데이터는 LLM의 해석 없이 정해진 규칙으로 그래프에 옮깁니다. 각 관계에는 Provenance[3]를 붙이고, EXTRACTED·INFERRED·AMBIGUOUS로 원문에 얼마나 분명히 드러났는지 기록합니다.

이 구조는 그래프에서 읽어낸 사실과 추론을 구분하고 관계에 근거를 남기는 설계를 투자 맥락에 맞게 적용한 것입니다. ATHENA는 명시성과 출처를 한 점수로 합치지 않습니다. 사용자가 직접 고친 내용과 체결·보유에서 확인한 사실을 대화 추론보다 먼저 적용하고, 요청 ID와 원문 지문이 맞을 때만 추출 결과를 저장합니다.

03 · Entity Resolution

다른 표현이 같은 대상을 가리키면 하나로 정리합니다

‘반도체 산업’, ‘반도체 업종’, ‘반도체’처럼 표현은 달라도 같은 관심사를 가리킬 수 있습니다. ATHENA의 Entity Resolution[4]은 정확한 별칭을 먼저 찾고, 이름 토큰의 Jaccard 유사도가 0.6 이상이거나 이웃 관계의 유사도가 0.8 이상인 후보를 연결합니다. 이웃 관계는 두 대상 모두 연결된 이웃이 2개 이상일 때 비교합니다. 연결된 후보는 Union-Find로 한 묶음을 만든 뒤 관계 수, 별칭 수, 생성 순서에 따라 대표 노드를 고릅니다.

종목은 이름이 비슷하다는 이유로 합치지 않고 종목코드로 구분합니다. 투자자 프로필도 자동 병합에서 제외해, 잘못된 병합이 보유 사실이나 개인화 기준을 다른 대상에 옮기는 일을 막습니다.

04 · 해결한 문제

대화의 관심과 실제 투자 사실을 섞지 않고 기억합니다

이를 통해 ATHENA는 사용자의 질문을 보유 사실로 잘못 기억하거나, 대화만 보고 보유 종목이나 수량을 잘못 기억하는 문제를 출처별 입력 경로와 우선순위 규칙으로 해결했습니다. 같은 관심사가 여러 이름으로 나뉘는 문제는 별칭·이름·이웃 관계를 차례로 비교해 하나의 대표 노드로 정리합니다. 정리된 그래프는 메티스에서 근거와 함께 확인하고, 아고라의 다음 대화와 아이기스의 맞춤 감시에 다시 사용합니다.

기술 용어 자세히 보기

[1] Agentic Memory는 에이전트가 이전 대화와 활동을 다음 작업에 다시 사용할 수 있도록 구조화해 저장하는 방식입니다. 단순히 대화 전문을 길게 붙이는 대신, 누구와 무엇이 어떤 관계인지 작은 단위로 나눕니다. ATHENA는 이 기억을 투자자·종목·관심사와 그 관계로 이루어진 지식 그래프에 저장합니다.

[2] Structured Extraction은 LLM의 자유로운 문장 대신 미리 정한 필드를 가진 결과만 받는 방법입니다. ATHENA는 개체, 관계, 명시성, 근거를 JSON 스키마에 맞춰 추출합니다. 요청 ID와 원문 지문이 다르거나 형식 검사를 통과하지 못한 결과는 그래프에 저장하지 않습니다.

[3] Provenance는 한 기억이 어디에서 왔는지 추적할 수 있게 남기는 정보입니다. ATHENA는 대화, 체결, 보유, 사용자 수정처럼 출처를 구분하고 관계를 만든 원문과 시점을 함께 보존합니다. 그래서 같은 대상에 서로 다른 정보가 들어와도 어떤 근거를 먼저 적용할지 결정할 수 있습니다.

[4] Entity Resolution은 표현이 다른 두 항목이 실제로 같은 대상인지 판단하는 과정입니다. Jaccard 유사도는 두 집합에서 공통된 항목 수를 전체 항목 수로 나눈 값입니다. 이름에서 나눈 단어나 연결된 이웃이 얼마나 겹치는지 이 값으로 비교합니다. Union-Find는 같은 대상으로 판정된 항목들을 하나의 묶음으로 관리하는 방법으로, A와 B가 같고 B와 C가 같으면 A·B·C를 한 묶음으로 정리합니다. ATHENA는 묶음마다 고정된 규칙으로 대표 노드를 선택합니다.

01 · Entity Retrieval

질문 속 이름을 그래프의 한 점과 연결합니다

“삼성에 관해 예전에 무슨 이야기를 했지?”라는 질문에서 ‘삼성’은 여러 기업을 가리킬 수 있습니다. RAG(검색 증강 생성)는 답변에 필요한 자료를 먼저 찾아 LLM에 근거로 전달하는 방식입니다. ATHENA는 먼저 질문의 대상을 지식 그래프의 한 점과 연결하는 Entity Resolution[1]을 수행합니다.

먼저 화면이 넘긴 ID로 직접 찾고, ID가 없으면 FTS5/BM25[2]로 이름과 별칭 후보를 최대 5개 검색합니다. 정확히 일치하는 이름이 하나이거나 후보가 하나뿐일 때만 대상을 확정합니다. 여러 후보가 남으면 임의로 고르지 않고 사용자가 선택할 목록을 보여줍니다.

02 · Graph Retrieval

답만 꺼내지 않고 연결된 근거까지 찾습니다

대상이 정해지면 ATHENA는 그 점과 연결된 관계, 방향, 저장 시점, 판단 이유와 원문을 함께 조회합니다. 관계마다 rationale과 provenance를 남겨, 그래프의 선이 어떤 기록에서 만들어졌는지 되짚을 수 있게 했습니다.

이처럼 검색한 사실을 출처 원문에 다시 연결하는 과정을 Evidence Grounding[3]이라고 합니다. 예를 들어 ‘반도체 → 삼성전자’라는 관계만 보여주는 대신, 그 연결을 만든 대화나 기록의 발췌문을 함께 돌려줍니다.

03 · Community Detection

복잡한 관계를 클러스터로 묶고 짧은 이름을 붙입니다

점과 선이 많아지면 관계를 하나씩 읽는 것만으로 전체 맥락을 파악하기 어렵습니다. ATHENA는 Greedy Modularity[4]로 서로 촘촘하게 연결된 점들을 클러스터로 묶습니다. 클러스터 번호는 크기와 노드 ID를 기준으로 정해 같은 그래프의 표시가 불필요하게 흔들리지 않게 합니다.

각 클러스터에서는 연결 수가 높은 대표 점을 최대 12개 골라 LLM에 전달하고, 탐색에 쓸 짧은 이름을 생성합니다. 클러스터 구성과 라벨링 프롬프트가 같으면 저장해 둔 이름을 재사용합니다.

04 · 해결한 문제

대상을 찾고, 연결의 근거까지 함께 가져옵니다

이를 통해 ATHENA는 이름이 비슷한 다른 대상을 답에 섞는 문제를, ID 우선 조회와 제한된 후보 확인으로 해결했습니다. 대상이 정해진 뒤에는 관계와 원문을 함께 가져와 답의 연결 이유를 확인할 수 있게 합니다. 복잡한 그래프는 결정적인 클러스터 배정과 재사용 가능한 LLM 라벨로 정리해, 같은 기억을 다시 탐색할 때도 일관된 구조에서 시작합니다.

기술 용어 자세히 보기

[1] Entity Resolution은 질문에 등장한 이름이 실제로 어떤 대상을 뜻하는지 식별하는 과정입니다. 예를 들어 ‘삼성’이라는 표현을 삼성전자, 삼성화재 같은 후보와 비교합니다. 후보가 하나로 좁혀지지 않으면 추측하지 않고 선택을 요청합니다.

[2] FTS5/BM25는 SQLite의 전문 검색 색인과 문서 순위 계산을 함께 사용하는 방식입니다. 질문에 들어 있는 단어가 이름이나 별칭에 얼마나 잘 맞는지 점수로 계산해 가까운 후보를 먼저 보여줍니다. ATHENA는 이 결과를 최대 5개로 제한한 뒤, 정확히 하나로 확정할 수 있는지 다시 검사합니다.

[3] Evidence Grounding은 생성된 설명을 검색된 근거에 연결하는 방법입니다. ATHENA는 관계의 한 줄 판단 이유뿐 아니라 해당 관계가 나온 원문 발췌와 출처 ID도 함께 조회합니다. 사용자는 그래프의 선이 왜 생겼는지 원래 기록까지 거슬러 확인할 수 있습니다.

[4] Greedy Modularity는 클러스터 안의 연결은 많고 클러스터 사이의 연결은 적도록 노드를 차례로 묶는 그래프 알고리즘입니다. ATHENA는 NetworkX의 결정적인 클러스터 결과를 사용하고, 클러스터 크기와 노드 ID로 표시 순서를 고정합니다. 연결이 없는 점은 억지로 하나의 클러스터로 만들지 않고 미분류로 둡니다.
