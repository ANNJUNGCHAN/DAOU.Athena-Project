   지목한 바로 그것을 우리도 갖고 있었다 — `runner.py`가 `warmup_bars=0`을 넘겼다.
   `compile_signals_with_warmup()`이 지표 프레임에서 센 실제 값을 넘긴다.
2. **`POST /runs`가 사용자를 영구히 가둘 수 있었다** (§11-9 휴장일 함정).
   `allow_partial` 출구 + 결과 플래그.
3. **`profit_factor`의 무한대가 전송 중에 `null`이 됐다.** 손실 0인 전략의 "∞"가
   화면에서 "모름(—)"으로 뒤집혔다 — 정직하려던 선택이 직렬화에서 무너진 사례다.
   `_json_safe`가 `<이름>_infinite` 플래그로 구분을 지킨다.
4. **백엔드 미기동 시 사용자에게 `fetch failed`가 그대로 보였다.** `status: 0`을
   손쓸 수 있는 문장으로 옮긴다.

### 10.6 배포의 실주문 연결 — 남은 것이 아니게 됐다 (2026-09-04)

이 자리에 있던 **"이 층은 신호와 한도 판정까지만 만든다"**는 더 이상 사실이 아니다.
2026-09-04 사용자 결정으로 **승인된 기법을 `auto` 모드로 배포하고 무장(armed)하면 사람 클릭
없이 주문이 나간다.** 집행 지점은 하나뿐이고 `backend/athena_api/backtest/deploy_orders.py`다.

**바뀐 것은 그 한 경로뿐이다.** 배포를 만드는 것도, 무장 토글을 켜는 것도, `activate`도
`backfill`도 여전히 사람 클릭이고 §10.2 표 그대로 **MCP 표면에 없다** — 모델은 그중 무엇도
부를 수 없다. 자동이 되는 것은 사람이 이미 세 번 눌러 세워 둔 상태(승인 → auto 배포 → 무장)
에서 신호가 났을 때의 **주문 제출 한 걸음**이다. `is_armed_for_auto()`가 그 셋을 한자리에서
읽는다: `mode == "auto"` **and** `armed` **and** `status == "active"`.

**두 번째 주문 경로를 만들지 않는다는 규율은 그대로다.** 그것이 원래 결정의 핵심이었고 지금도
유효하다. `deploy_orders.py`는 주문 티켓과 같은 것을 공유한다 — 같은 payload 모양
(`dmst_stex_tp/stk_cd/ord_qty/trde_tp`, 시장가 `3`. `app/lib/order-ticket.js`
`buildOrderPayload`와 한 글자도 다르지 않다), **같은** 멱등 예약 캐시
(`app.state.order_idempotency_cache`), 같은 무재시도 규율(실패는 실패로 남긴다). 캐시를 따로
뒀다면 티켓이 낸 주문과 자동이 낸 주문이 서로를 못 보고 중복 판정이 갈렸을 것이다.

**멱등키가 이 경로의 안전장치다.** 키는 `(배포 id, 신호 시각, 방향)`으로 **결정적으로**
만든다. 스케줄러가 같은 봉을 두 번 보더라도(재기동·중복 tick·시계 흔들림) 두 번째 호출은 첫
예약을 그대로 만나 새 주문이 되지 않는다. 임의 키를 썼다면 tick 한 번이 주문 하나가 된다.

**나가는 곳은 모의서버뿐이다.** `config.py:315`의 `validate_runtime_safety`가
`kiwoom_base_url`이 키움 모의 도메인이 아니면 **부팅 자체를 거부한다.** 이 자동 경로도 그
하드락 안쪽에 있다.

표면: `POST /api/v1/backtest/deployments/{id}/arm`(멈춘 배포에 무장하면 409, 없는 배포 404) ·
`GET /deployments`의 `armed`(사람이 켠 스위치)와 `auto_armed`(셋 다 참일 때만 참 — 화면은 이
값 하나만 읽는다) · `GET /deployments/{id}/signals`와 `POST /deployments/{id}/evaluate`가
같이 싣는 `order_no`·`qty`.
