# Paper 19개 통합 창 UI 내역서

- 상태: Paper 실제 19개 창 반영 완료 · 프런트엔드 구현 전 기준안
- 대상: Athena Canvas, Selector, Kiwoom REST/WebSocket 연동
- 관련 문서: [19개 Capability 전환 계획](../architecture/19-capability-window-plan.md), [19개 Capability API 내역](../api/19-capability-api-inventory.md)
- Paper 기준 화면: [19 통합 창 페이지](https://app.paper.design/file/01M0VGPX92K1TER4ZV9PWGQJJZ/6-1)

## 1. 목적

299개 Kiwoom 내부 호출 단위를 사용자에게 299개의 서로 다른 카드로 노출하지 않는다. Selector는 질문을 19개 `capability_id` 중 하나와 target·mode·parameter로 해석한다. 세부 `operation_ref`는 서버의 deterministic Capability Resolver만 선택하고, Canvas는 Capability마다 고정된 창을 즉시 마운트한다. REST 응답은 해당 창의 정해진 섹션에 투영하고, 실시간을 지원하는 mode·section은 최초 스냅샷 조회 직후 별도 사용자 명령 없이 자동 등록한다.

이 문서는 19개 창의 정보 구조, 공통 상태, 실시간 합성 규칙과 Paper 기준 화면을 정의한다. Paper에는 각 Capability의 실제 1440×900 기준 화면까지 반영했다. 프런트엔드 Runtime 구현과 response-field 자동 커버리지 검증은 후속 단계다.

## 2. 현재 구조와 목표 구조

| 구분 | 현재 | 목표 |
|---|---|---|
| 렌더 선택 기준 | `card_title` 중심의 16개 렌더러 | `capability_id` 중심의 19개 고정 창 |
| API와 UI 관계 | 호출 결과마다 카드 형태를 다시 선택 | Capability 창을 먼저 마운트하고 섹션만 채움 |
| 실시간 | 별도 의도·별도 등록 흐름 | 지원 창은 최초 조회 직후 자동 lease 생성 |
| 호가 | 여러 TR/실시간 결과가 분산될 수 있음 | 호가 관련 31개 operation을 한 호가창의 모드·섹션으로 합성 |
| 오류 표시 | 카드 전체 실패로 번지기 쉬움 | 섹션별 오류와 마지막 정상 데이터 유지 |
| 주문 | 조회·주문 결과의 경계가 불명확해질 수 있음 | 주문 창은 초안·확인·접수·체결 상태를 명시적으로 분리 |

## 3. 공통 창 골격

모든 창은 아래 순서를 공유한다.

1. 헤더: 창 이름, 대상 종목·계좌, 시장 세션, 실시간 상태
2. 컨텍스트 바: 기준일·주기·시장·계좌 등 현재 질의 조건
3. 모드 탭: 동일 Capability 안의 조회 목적 전환
4. 주요 콘텐츠: 차트, 호가 사다리, 표, 순위, 요약 지표 등
5. 보조 섹션: 최신성, 출처 시각, 누락·지연·재연결 안내
6. 액션 영역: 새로고침, 종목 변경, 주문 초안 확인 등 허용된 행동

Canvas는 라우팅이 끝나면 데이터보다 먼저 `CapabilityWindowShell`을 렌더한다. 로딩 중에도 창의 크기와 레이아웃을 고정해, LLM이 응답 필드에서 즉석으로 카드 디자인을 생성하지 않도록 한다.

### 공통 컴포넌트

- `CapabilityWindowShell`: 19개 창의 공통 프레임과 모드 전환
- `RealtimeStatus`: 연결 중, 실시간, 지연, 재연결, 장 마감 표시
- `SectionFreshness`: 섹션별 스냅샷·실시간 최종 시각
- `AsyncSectionBoundary`: 한 섹션 실패가 창 전체를 막지 않도록 격리
- `MarketSessionBadge`: 장 전·장중·장후·휴장 상태
- `ReceiptTimeline`: 주문 초안부터 접수·체결·실패까지의 진행 상태
- `VisibleRowsSubscriptionBoundary`: 관심종목·검색 결과에서 화면에 보이는 종목만 자동 구독

기존 `ChangeBadge`, `QuoteHeader`, `TabSwitcher`, `ProportionalBar`, `RangeBar`, `RankedRow`, `TwoLineRow`, `StatusPill`, `LadderRow`는 새 창 내부의 표현 primitive로 재사용한다.

## 6. 실시간 자동 등록 UI 계약

실시간 지원 창에서 사용자는 등록 버튼을 누르지 않는다. 표준 흐름은 다음과 같다.

1. Selector가 사용자 질문을 `capability_id`, target, mode, parameter로 resolve한다.
2. Canvas가 빈 Capability 창을 즉시 마운트하고 REST 스냅샷 요청을 시작한다.
3. Capability Resolver가 내부 `operation_ref`와 mode·section realtime profile을 결정한다.
4. 스냅샷 반환 직후 서버가 window lease를 생성하고 필요한 실시간 채널을 등록 큐에 넣는다.
5. UI는 `connecting` 상태로 스냅샷을 먼저 표시한다.
6. 등록 ACK를 받으면 `live`로 바꾸고 이벤트를 기존 섹션에 병합한다.
7. 창이 닫히거나 대상이 바뀌면 소유 lease를 해제한다. 동일 물리 구독을 다른 창이 사용 중이면 서버 참조 수만 줄인다.

### 병합 규칙

- 스냅샷보다 실시간 이벤트가 먼저 도착하면 버퍼링한다.
- 늦게 도착한 REST 값이 더 최신인 실시간 값을 덮어쓰지 못한다.
- 종목·탭 변경은 전체 해제 후 재등록이 아니라 필요한 채널 차이만 반영한다.
- 네트워크 복구 후 서버의 `stream_epoch`과 `cursor`를 확인한다.
- 이벤트 공백이 확인되면 해당 섹션을 새 스냅샷으로 재설정한다.
- 한 실시간 등록을 여러 창이 공유할 때 실제 Kiwoom 등록·해제는 서버 참조 수의 `0→1`, `1→0` 전이에서만 수행한다.
- `live_error`에서도 마지막 정상 데이터와 그 시각을 유지한다.

## 7. 창별 핵심 UI 원칙

### 호가

호가 관련 31개 operation은 서로 다른 카드를 만들지 않는다. 하나의 호가 창에서 일반·통합·시간외·금 모드를 전환하고, 매도 잔량·가격·매수 잔량을 한 축에 정렬한다. 중앙 현재가를 기준으로 가격대가 움직이며 체결이 발생한 행은 짧은 색 변화로 갱신을 알린다. 숫자가 움직여도 행 위치와 열 폭은 유지해 읽기 흐름을 보존한다.

### 차트

창은 주기만 전환하고 전체 구조는 유지한다. 데이터 수신 전에도 축과 차트 영역을 먼저 표시한다. 과거 봉은 REST 스냅샷을 사용하고, 현재 봉만 실시간 체결로 갱신한다. 조회 구간이 잘렸다면 최근 구간임을 사용자 언어로 표시한다.

### 주문

주문 문장은 주문 창을 띄울 수 있지만 즉시 실행하지 않는다. `초안 → 사용자 확인 → 접수 → 체결/거부`를 `ReceiptTimeline`으로 구분하고, 수량·가격·매수/매도·계좌를 확인 전 단계에서 고정 표시한다. 재전송은 동일 idempotency key를 사용하며 결과가 불명확한 상태를 성공으로 표현하지 않는다.

### 관심종목·탐색

대량 종목 전체를 구독하지 않는다. 현재 viewport에 보이는 행과 짧은 선행 구간만 구독하고, 스크롤하면 구독 대상을 교체한다. UI에는 최대 동시 구독 수와 지연 상태를 노출하지 않되, 상한 초과 시 다음 행은 스냅샷 모드로 안전하게 유지한다.

## 8. 반응형·접근성

- 데스크톱: Canvas 영역에서 최대 2열, 주문·호가·차트는 필요 시 전체 폭 사용
- 900px 미만: 1열, 우측 채팅 패널과 Canvas의 우선순위를 명확히 전환
- 실시간 상태 변화는 색상만으로 표현하지 않고 텍스트·아이콘을 함께 사용
- 상태 영역은 `role="status"`, 중요한 주문 결과는 적절한 live region 사용
- 숫자 열은 자릿수 변화에도 흔들리지 않도록 tabular 숫자와 고정 정렬 사용
- `prefers-reduced-motion`에서는 체결 flash와 이동 애니메이션을 축소하거나 제거
- 키보드로 탭·모드·행을 이동할 수 있고, 포커스가 실시간 갱신으로 강제 이동하지 않음

## 10. 데이터 표현 범위와 검증 상태

- operation-level: `backend/ref/kiwoom-capability-assignment.json`에서 OAuth 제외 299개 `mapping_id`가 19개 창에 정확히 한 번 귀속되고, 자동 테스트가 unassigned 0, duplicated 0을 검증한다.
- Paper-level: 19개 실제 창이 모두 존재하며 공통 헤더, mode, 실제 본문, `DATA SURFACE`를 가진다.
- response-field-level: canonical manifest에는 field occurrence 3,705개, 고유 alias 1,877종이 있다.
- 최종 보장 조건: 모든 semantic field가 primary, secondary, detail 또는 `SemanticDetailSheet`로 접근 가능하고 fixture render coverage가 100%여야 한다.
- 현재 blocker: 의미가 `Extra Item`으로만 정의된 `951`, `924`, `1279` 세 필드는 공식 의미 확인 전까지 임의 표시하지 않는다.

따라서 19개 창은 299개 API를 수용하는 정보 구조와 실제 UI를 제공한다. 다만 “모든 응답 필드를 손실 없이 이미 표현한다”는 Runtime field registry와 자동 커버리지 게이트가 통과한 뒤에만 완료로 선언한다.

## 11. 프런트엔드 적용 지점

## 12. 완료 기준

- Selector가 모든 299 operation을 정확히 하나의 `capability_id`로 매핑한다.
- Canvas가 19개 외의 임의 카드 레이아웃을 생성하지 않는다.
- 실시간 지원 창은 최초 스냅샷 직후 자동으로 `connecting`을 거쳐 `live`가 된다.
- 동일 구독은 여러 창에서 공유되고 마지막 소유자가 해제될 때만 실제 해제된다.
- 스냅샷 전용 창에는 허위 실시간 상태를 표시하지 않는다.
- 주문 창은 사용자 확인 전 주문 실행을 발생시키지 않는다.
- 호가 31개 operation이 하나의 호가 창에서 모드·섹션으로 표현된다.
- Paper 기준 화면과 API 내역서의 19개 분류·명칭·실시간 정책이 일치한다.
- 모든 semantic response field의 렌더 접근률이 100%이며 diagnostic-only semantic field가 0개다.
